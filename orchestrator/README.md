# LangGraph: скелет оркестратора

Рабочая заготовка по обсуждению 20 октября 2026 года. Здесь описаны состояния,
узлы и переходы; реальные модели, поиск, парсер, БД и Go API не подключены.
Это не утверждённый HTTP-контракт и не готовый сервис. Основной план проекта
остаётся в harness; этот файл описывает только содержимое каталога.

## Файлы

- `graphs.py` — State, линейные связи EDGES, развилки BRANCHES, сборка графов.
- `tests/test_graphs.py` — проверки маршрутов на подставных операциях.
- `requirements.txt` — единственная прямая зависимость. Диапазон версии
  предварительный; совместимость установленной версии ещё не проверена.

## Потоки

| Граф | Вход | Результат |
| --- | --- | --- |
| `event` | Материал из общего/отраслевого потока либо адресного поиска | Проверенное событие и задания для компаний-кандидатов |
| `company` | Одна версия события, одна компания и роль | Решение о соответствии, карточка, фоновое задание отчёта либо ожидание клика |
| `open` | Доверенный пользовательский контекст, компания, событие, роль | Сохранённый отчёт, статус задания либо отказ в доступе |
| `report` | Задание подготовки отчёта с версиями исходных данных | Проверенный отчёт либо сохранённый статус недостаточности оснований |
| `chat` | Контекст пользователя, диалог, вопрос и версия отчёта | Ответ с основаниями, уточняющий вопрос либо сообщение о нехватке данных |

`event` выделен из оценки одной компании, чтобы общий материал не загружался
заново для каждой компании. `dispatch_company_jobs` создаёт задания `company`,
а `enqueue_report` передаёт задания в общий граф `report`. Их фактический
диспетчер ещё нужно реализовать: эти узлы сами по себе не запускают другой граф.
Конкретный брокер, сервер и планировщик здесь не выбираются.

### Событие и персонализация

Проверка входа → дедупликация/версия → сохранение → компании-кандидаты →
задания на компанию. Некорректный материал сохраняется с причиной; дубль
заканчивает проход; при отсутствии кандидатов персонализация не запускается.

Для каждой компании: контекст → численная оценка соответствия → карточка →
отдельное решение о приоритете. Нерелевантность и неопределённость сохраняются
раздельно. Топ-отчёт ставится в фон; остальные ждут открытия. Пороги,
шкала оценщика и правила выбора кандидатов не заданы. Обезличенный ID компании
не означает совпадения с реальным названием в новостях.

### Открытие

Проверка доступа → проверка наличия и актуальности отчёта. Готовый возвращается;
для выполняющегося возвращается статус. Для отсутствующего или устаревшего
атомарно создаётся задание, если его ещё нет. Повторный клик использует то же задание.

### Подготовка отчёта

Загрузка версий входов → получение оснований → оценка достаточности.
При необходимости: внешний поиск → проверка источников → повторная оценка.
Далее: черновик → проверка утверждений/ссылок/дат → сохранение или ограниченная
доработка. Исчерпание бюджета и недостаточность оснований ведут к отдельному
результату `save_insufficient_report`; они не превращаются в успешный отчёт.

### Чат

Доступ → загрузка диалога и отчёта → выбор: ответ по имеющимся данным,
внутренний retrieval, внешний поиск или уточнение. После получения новых
оснований проверяется их достаточность. Ответ проходит проверку и сохраняется.
Недостаточность тоже сохраняется в диалоге. Чат не перезаписывает отчёт;
версия отчёта фиксируется в контексте разговора.

## Подключение операций

`build_graphs(handlers, checkpointer=...)` возвращает словарь с пятью графами.
Каждый handler — синхронная функция `state -> dict` с частичным обновлением
состояния. Имя функции в словаре соответствует имени узла в EDGES/BRANCHES.
Зависимости можно передать через замыкание; клиенты и секреты в State не кладутся.

Узел развилки обязан вернуть поле решения и одно из значений, перечисленных
в BRANCHES. Поле нужно возвращать при каждом вызове: старое решение из State
не заменяет новый результат. Неподключённый узел поднимает NotImplementedError,
ошибочное решение — ValueError. Пустой результат не считается успешной интеграцией.

Для первого шага достаточно заполнить handlers одного выбранного потока.
Остальные графы можно собрать для просмотра, но их выполнение потребует
соответствующих операций. Например, получить текст схемы без вызова узлов:

```python
from orchestrator.graphs import build_graphs

graphs = build_graphs()
print(graphs['report'].get_graph().draw_mermaid())
```

Счётчики `searches_used` и `revisions_used` обновляет оболочка узлов.
Лимиты `max_searches` и `max_revisions` передаёт вызывающий код; по умолчанию
они равны нулю, поэтому без явной политики поиск и доработка запрещены.
Это ограничение числа операций, не денежного бюджета или общего времени:
таймауты, стоимость и сетевые повторы нужно ограничивать внутри интеграций.

## Обязательства будущих интеграций

- Входные данные проверяются в `validate_event`; пользовательский контекст
  берётся из доверенного backend. `authorize` проверяет компанию, событие,
  отчёт и диалог до загрузки данных. Фоновые графы вызываются только доверенным
  обработчиком заданий с привязкой к компании.
- `deduplicate_event` отличает обработанную версию от незавершённой доставки.
  Сохранённое событие без созданных заданий не должно навсегда стать «дублем».
- Сохранение и создание заданий должны быть идемпотентными. Обновления события
  и контекста компании требуют проверки актуальности отчётов. Ключ задания
  включает событие, компанию, роль, версии входов и версию политики анализа.
- `ensure_report_job` должен атомарно сохранять долговечное задание. Если
  уведомление из `enqueue_report` потеряется, диспетчер обязан подобрать его
  из хранения. Механизм хранения/доставки ещё не реализован.
- `retrieve_evidence` получает профиль и доступную аналитику банка. Парсинг PDF
  остаётся у сокомандника. Внутренние сведения изолируются по компании.
- `search_external` различает `ok`, `no_hits`, `access_error`; `validate_sources`
  проверяет источники и даты. Ошибка доступа не доказывает отсутствия фактов.
  Текст источника используется как данные, не как инструкции инструментам.
- `draft_report` разделяет факт, позицию банка, вывод модели, риски,
  возможности и пробелы. `verify_report` проверяет опору утверждений на источники.
  Выбор LLM, retrieval и критериев качества остаётся открытым.
- State хранит заменяемые снимки: узел возвращает полный новый список evidence
  или messages, если изменяет его. Параллельной записи в State одного задания нет.
- При подключении checkpointer вызывающий код задаёт стабильный `thread_id`
  для задания, а для чата — изолированный ID разговора. Секреты и полный State
  не транслируются фронтенду. Checkpoint не заменяет прикладное хранение отчётов.
- Необработанная техническая ошибка прерывает выполнение. Классификация ошибок,
  политика повторов и запись failed в БД пока не реализованы; ошибка не маскируется
  успешным ответом. Возобновление требует checkpoint и безопасных повторных операций.

## Проверки для запуска пользователем

Из корня репозитория, в отдельном Python-окружении (Python 3.11+):

```bash
python -m pip install -r orchestrator/requirements.txt
python -m unittest discover -s orchestrator/tests -v
```

Тесты проверяют развилки, ограничения циклов, повторное открытие и отсутствие
неявных заглушек. Они не проверяют качество моделей, атомарность хранения,
доставку заданий, реальные права доступа или совместимость Go API.

**Статус:** код и проверки подготовлены, но агентом не запускались.
Следующее наполнение — один выбранный поток после согласования его контрактов.
