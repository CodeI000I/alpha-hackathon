# Контракт frontend и backend

Этот документ описывает объединённый рабочий интерфейс на 24 октября 2026 года. Источник Go-контракта — [`backend/API.md`](../backend/API.md); устройство объединённого runtime и аналитики описано в [`docs/integration-main-2026-10-24.md`](../docs/integration-main-2026-10-24.md). Деморежим является отдельным локальным сценарием и не описывает production API.

## Транспорт и границы доступа

- Все browser API используют относительный префикс `/api/v1`; в development Vite проксирует `/api` на Go, production использует тот же origin.
- `VITE_DATA_MODE=api` — режим по умолчанию. Ошибка сети, HTTP или формы ответа остаётся ошибкой и не заменяется fixtures.
- `VITE_DATA_MODE=demo` использует локальное хранилище и не отправляет запросы.
- В API-режиме Go выдаёт HttpOnly session cookie. Браузер отправляет её same-origin автоматически и восстанавливает пользователя через `/auth/me`.
- Go определяет пользователя, компанию и доступные роли по сессии. Analytics-запросы могут указывать выбранный `role`, но клиент не передаёт analytics proxy `company_id` или `user_id`.
- Доступ к analytics строится через Go proxy; браузер не получает внутренний адрес Python или служебный токен.
- Все ответы проверяются на ожидаемую форму. Например, logout с `204` не требует JSON-тела, а массивы документов, issues, evidence и history должны быть массивами. HTML или неожиданная JSON-обёртка не считается пустым результатом.

## Авторизация и регистрация

Поддержанные методы:

| Метод | Путь | Результат |
| --- | --- | --- |
| `POST` | `/api/v1/auth/login` | Принимает `{email,password}`, устанавливает session cookie и возвращает `User` |
| `GET` | `/api/v1/auth/me` | Возвращает пользователя текущей сессии |
| `POST` | `/api/v1/auth/logout` | Отзывает сессию, ответ `204` |
| `POST` | `/api/v1/onboarding` | Атомарно создаёт компанию и первого пользователя, устанавливает cookie |

Onboarding принимает структуру `{company:{...}, user:{email,fullName,password,roles}}`. Пароль пользователя обязателен и имеет длину не менее 10 символов. Один idempotency key связывает повтор одного и того же запроса с результатом; frontend сохраняет этот ключ, чтобы восстановиться после неизвестного результата сети. В ключе нет пароля или password fingerprint. Пароль не записывается в localStorage/sessionStorage и не восстанавливается из локального состояния.

Черновик регистрации может содержать остальные поля до закрытия вкладки, но не пароль. Входящий пользователь восстанавливается только подтверждённым `/auth/me`; localStorage сам по себе не означает действительную сессию. Выход ждёт ответа API и показывает ошибку, если сервер не подтвердил отзыв cookie.

Публичное создание или подключение к компании только по известному ИНН не поддерживается: уже существующая компания не раскрывается и не присоединяется к регистрации. Сервер возвращает конфликт. В `demo` вход остаётся клиентским и относится только к локальным fixture-аккаунтам.

## Базовые данные Signal

Обычные методы для текущего пользователя включают справочники ролей и элементов профиля, компанию, пользователей, ленту и метаданные загруженных файлов. Маршруты и модели полностью перечислены в [`backend/API.md`](../backend/API.md). Пользовательские и company ID в базовых Go-маршрутах появляются в пути; при этом production handler проверяет авторизацию и владение. Analytics proxy ниже намеренно не принимает эти ID от браузера.

Файл загружается multipart-полем `file`. UI ограничивает документ 12 МиБ, совпадая с ограничением внутренней загрузки/парсера. Успешный upload подтверждает сохранение оригинала, но не завершение анализа. Состояние обработки читается отдельным analytics endpoint.

## Analytics API

Браузер использует `/api/v1/analytics/<suffix>?role=<owned-role>`. Go проверяет роль и добавляет область доступа из сессии. Параметр `role` обязателен: при его отсутствии или выборе неназначенной роли proxy возвращает `403`. Интерфейс отправляет выбранную роль в каждом analytics-запросе.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/analytics/situation` | Бизнес-ситуация / snapshot |
| `GET` | `/analytics/issues` | Список issues с пагинацией `offset`/`limit` |
| `GET` | `/analytics/issues/{id}` | Детали issue |
| `GET` | `/analytics/issues/{id}/evidence` | Основания и исходные материалы |
| `GET` | `/analytics/issues/{id}/history` | История issue |
| `GET`, `PATCH` | `/analytics/issues/{id}/state` | Получение и изменение пользовательского состояния |
| `GET` | `/analytics/documents` | Статус анализа документов компании |
| `GET` | `/analytics/conversations/{id}` | История закреплённого разговора |
| `POST` | `/analytics/issues/{id}/questions` | Вопрос по issue с `conversation_id`, `request_id` и при наличии версией |
| `POST` | `/analytics/refresh` | Запросить обновление; `retry_failed:true` повторяет неудавшийся разбор документов |
| `GET` | `/analytics/jobs/{id}` | Состояние фонового задания |

Контрактные JSON-типы следует брать из Python router/models, а не моделировать по UI. Ответ documents — массив объектов `{file_id,filename,document_id,status,attempts,error,retry_at}`. `status` имеет значения `queued`, `ready`, `failed`; `retry_at` — Unix timestamp или `null`. Если работа ещё идёт, UI показывает её фактический статус. Ошибка/пустой ответ не превращаются в готовую сводку или демоцифры.

Чат закрепляется за версией issue, выбранной при создании разговора. Вопрос ждёт загрузки текущего разговора и отправляется с его pinned version. Если issue обновился после открытия беседы, интерфейс не меняет версию незаметно: пользователь явно начинает новый разговор для актуальной версии.

Кнопка обновления запрашивает refresh и показывает состояние полученного задания. Повтор обработки неудачных документов отправляет `{retry_failed:true}`. Это не означает, что немедленно появится новый issue: состояние job и данные snapshot обновляются отдельно.

## Оценка и тексты

В совместимом Go `/rank` adapter поле `score` отображает ordinal-уровень urgency: `none → 0`, `unknown → 0.25`, `monitor → 0.5`, `soon → 0.8`, `immediate → 1`. Это порядок приоритета/срочности, а не вероятность события или релевантность. В live UI оценка поэтому называется «срочность» или «приоритет». «Релевантность» допустима только для demo-данных, если это их явная семантика.

Текст источника, интерпретация и evidence должны сохранять различие. URL источников/оснований берутся из ответа и допускаются только с `http:` или `https:` схемой. Наличие загруженного документа само по себе не доказывает, что документ использован в issue.

## Локальные и demo-функции

`demo` сохраняет сценарии автономными и не обращается к сети. Отдельные локальные настройки, например ключевые слова и избранное, не изменяют server-side analytics. Они должны оставаться явно локальными; demo fixtures нельзя выдавать за live API вывод.

## Проверка

Unit- и браузерные контрактные тесты проверяют контролируемые ответы и форму запросов. Они не заменяют совместный smoke с Go, Python, PostgreSQL и файловым хранилищем. Результаты актуального объединённого прогона записываются в [заметках интеграции](../docs/integration-main-2026-10-24.md); старые счётчики тестов frontend-ветки — исторические.
