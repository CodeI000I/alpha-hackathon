# Альфа-Будущее — техническая спецификация аналитического пайплайна

**Версия:** 1.0

**Статус:** Proposed / Ready for implementation planning

**Дата:** 22 октября 2026

**Область ответственности:** ML/LLM-оркестратор, обработка документов и новостей, retrieval, граф связей, формирование бизнес-ситуаций и сводок.

**Вне ответственности:** реализация frontend, банковская инфраструктура доставки новостей и пользовательская аутентификация. Для них определяются интеграционные контракты.

---

# 1. Цель системы

Разработать персонализированный сервис анализа внешней бизнес-среды компании на основе проверенных новостей и внутреннего контекста бизнеса.

Сервис должен отвечать не только на вопрос:

> Как отдельная новость может повлиять на компанию?

Но и на более важный:

> Что сейчас происходит вокруг компании, как взаимосвязанные события влияют на её деятельность, какие риски и возможности возникают и что следует предпринять?

## 1.1. Ожидаемая ценность

Пользователь должен получать:

1. Готовую оценку актуального положения компании относительно внешних событий.
2. Несколько наиболее значимых бизнес-ситуаций вместо длинного списка публикаций.
3. Объяснение механизмов влияния с опорой на конкретные факты компании.
4. Обнаружение косвенных зависимостей и совокупного влияния нескольких событий.
5. Конкретные следующие шаги, вопросы для уточнения или обоснование отсутствия необходимости действовать.
6. Историю ранее подготовленных разборов и изменений ситуации.
7. Возможность углубиться в конкретный вопрос без повторного объяснения контекста.

**Ключевой продуктовый принцип: основная польза должна появляться до клика пользователя.**

Открытие карточки не должно запускать обязательную генерацию основного вывода. Разбор заранее подготовлен, сохранён и доступен для просмотра. Новые LLM-вызовы инициируются дополнительными вопросами, сценариями или обновлением данных.

## 1.2. Базовые допущения

- Новости поступают из инфраструктуры Альфа-Банка и считаются прошедшими upstream-валидацию.
- Дополнительный общий фактчекинг исходных новостей не требуется.
- Корпоративный контекст формируется из предоставленных документов, структурированного профиля и подтверждённых пользователем сведений.
- Документы компании могут быть неполными, противоречивыми и устаревшими.
- Новость может описывать состоявшееся событие, объявленный план, прогноз или намерение. Эти модальности нельзя смешивать.
- Несколько публикаций могут описывать одно событие.
- Несколько различных событий могут воздействовать на один бизнес-фактор и образовывать единую бизнес-ситуацию.
- Система не должна выдавать уверенный вывод при отсутствии необходимых оснований.
- Исходные данные компаний изолированы друг от друга.
- Данные для эмпирической проверки качества будут предоставлены позднее. Все начальные пороги и лимиты — конфигурационные параметры, а не измеренные оптимальные значения.

## 1.3. Что система не должна делать

- Превращать модельный confidence в вероятность будущего финансового результата.
- Считать тематическую близость двух новостей доказательством причинно-следственной связи.
- Перемножать или суммировать вероятности разных бизнес-событий без обоснованной модели зависимостей.
- Придумывать численные последствия без достаточных входных данных.
- Считать отсутствие факта в базе доказательством его ложности.
- Перегенерировать всю историю при поступлении каждого нового сообщения.
- Заставлять пользователя вручную изучать множество новостей для выбора того, что заслуживает анализа.
- Превращать непроверенные гипотезы, извлечённые LLM, в подтверждённые корпоративные факты.

# 3. Общая архитектура

Система состоит из четырёх контуров.

## 3.1. Контур A — корпоративные знания

**Вход:** документы и профиль компании.

**Преобразования:**

- извлечение текста;
- разбиение на смысловые фрагменты;
- извлечение сущностей, фактов и отношений;
- сохранение исходных доказательств;
- построение полнотекстового и векторного индексов;
- построение графа корпоративных зависимостей.

**Результат:** доступное для поиска, версионированное представление компании.

## 3.2. Контур B — общий поток новостей

**Вход:** проверенные новости Альфа-Банка.

**Преобразования:**

- идемпотентное сохранение;
- дедупликация публикаций;
- нормализация событий;
- извлечение упомянутых сущностей;
- определение потенциально затронутых бизнес-факторов;
- индексация событий;
- обновление общего графа событий.

**Результат:** единое структурированное представление внешних событий, переиспользуемое для всех компаний.

## 3.3. Контур C — персональный анализ компании

**Вход:** событие и корпоративный контекст.

**Преобразования:**

- отбор компаний-кандидатов;
- retrieval корпоративных фактов;
- обход релевантных графовых связей;
- построение evidence pack;
- типизированная оценка влияния;
- отнесение к существующей бизнес-ситуации либо создание новой;
- пересмотр затронутых бизнес-ситуаций.

**Результат:** актуальные `CompanyImpact` и `BusinessIssue`.

## 3.4. Контур D — общая ситуация компании

**Вход:** активные бизнес-ситуации, корпоративный профиль, предыдущая версия обзора.

**Преобразования:**

- определение существенных изменений;
- выбор наиболее важных текущих вопросов;
- совместный анализ разнонаправленных и взаимосвязанных факторов;
- формирование рекомендаций;
- подготовка общей сводки;
- сохранение версии результата.

**Результат:** `SituationSnapshot` — готовая картина текущего положения компании относительно внешней среды.

# 4. Модель данных

## 4.1. Общие требования

Все долговременные сущности должны иметь:

- устойчивый идентификатор;
- версию схемы;
- время создания и обновления;
- происхождение данных;
- статус актуальности;
- связь с исходными доказательствами там, где она применима.

Необходимо различать:

- время события;
- время публикации;
- время поступления в систему;
- время начала и окончания применимости факта;
- время формирования аналитического вывода.

Не допускается автоматически считать `published_at` равным `event_time`.

## 4.2. Основные сущности

| Сущность | Назначение |
|---|---|
| `NewsArticle` | Оригинальная публикация банка |
| `Event` | Нормализованное событие |
| `Entity` | Организация, проект, регион, товар, маршрут и т. д. |
| `Company` | Профиль анализируемой компании |
| `SourceDocument` | Корпоративный документ и версия |
| `SourceChunk` | Фрагмент документа с точным локатором |
| `CompanyFact` | Утверждение о компании с источником и модальностью |
| `BusinessFactor` | Экономический/операционный фактор компании |
| `KnowledgeEdge` | Типизированная связь узлов |
| `CompanyImpact` | Оценка влияния события на компанию |
| `BusinessIssue` | Развивающаяся бизнес-ситуация |
| `BusinessIssueVersion` | Версия состояния ситуации |
| `SituationSnapshot` | Общая картина положения компании |
| `AnalysisRun` | Запуск аналитической обработки |
| `Conversation` / `Message` | Обсуждение конкретного разбора |

## 4.3. NewsArticle

Пример входного контракта:

```json
{
  "schema_version": "1.0",
  "source": "alfabank",
  "news_id": "news_101",
  "revision": 1,
  "title": "Поставщик объявил изменение цен",
  "content": "Полный текст публикации...",
  "published_at": "2026-10-22T09:00:00Z",
  "received_at": "2026-10-22T09:02:00Z",
  "source_url": null,
  "upstream_validated": true,
  "metadata": {
    "entities": [],
    "topics": []
  }
}
```

`source_url` может отсутствовать, если банк передаёт новость без публичной ссылки. В таком случае хранится внутренний локатор.

Поле `upstream_validated` отражает доверие к входному источнику. Оно не означает, что любые выводы о компании автоматически достоверны.

**Инварианты:**

- один и тот же `news_id + revision` обрабатывается идемпотентно;
- изменение revision не создаёт дубль исходной публикации;
- полный исходный текст сохраняется;
- ошибка извлечения события не удаляет новость.

## 4.4. Event

```json
{
  "event_id": "event_201",
  "event_type": "supplier_price_change",
  "modality": "announcement",
  "summary": "Поставщик X объявил изменение базового прайса",
  "entities": ["supplier_x"],
  "affected_factors": ["procurement_cost"],
  "event_time": "2026-10-22",
  "effective_from": "2026-11-01",
  "source_news_ids": ["news_101"],
  "extraction_version": "event_extractor_v1"
}
```

Допустимые значения `modality` в первой версии:

- `realized`;
- `announcement`;
- `plan`;
- `forecast`;
- `proposal`;
- `unknown`.

Модель может предложить факторы воздействия, но они должны иметь статус **гипотезы**, пока не подтверждена применимость к конкретной компании.

**Разные статьи об одном изменении** привязываются к одному `Event`.

**Разные изменения одной компании** не объединяются автоматически.

## 4.5. CompanyFact

```json
{
  "fact_id": "fact_301",
  "tenant_id": "tenant_1",
  "company_id": "company_1",
  "subject_id": "company_1",
  "predicate": "buys_from",
  "object_id": "supplier_x",
  "modality": "current_fact",
  "qualifiers": {
    "product": "упаковка",
    "price_terms": "current_price_at_shipment"
  },
  "valid_from": null,
  "valid_until": null,
  "source_refs": ["chunk_51"],
  "verification_status": "source_supported",
  "knowledge_revision": 7
}
```

Ключевые требования:

- каждый существенный факт должен иметь источник либо явный статус пользовательского утверждения;
- дата и область действия договора не должны теряться;
- отсутствие известной даты не подменяется текущей датой;
- модельные предположения хранятся отдельно от подтверждённых фактов.

Необходимы статусы знания:

`known`, `unknown`, `not_applicable`, `conflicting`, `outdated`.

## 4.6. BusinessFactor

Это контролируемый справочник механизмов, связывающих компанию с внешними событиями.

Начальный набор:

| Код | Пример |
|---|---|
| `procurement_cost` | Стоимость закупок |
| `supply_availability` | Доступность поставок |
| `logistics` | Маршруты и сроки логистики |
| `demand` | Спрос на продукцию и услуги |
| `financing` | Стоимость и доступность финансирования |
| `market_expansion` | Выход в новые регионы или сегменты |
| `regulation` | Регуляторные условия |
| `competition` | Конкурентная среда |
| `operations` | Операционная деятельность |
| `workforce` | Персонал и рынок труда |

Справочник расширяемый и версионируемый. Не нужно создавать новый тип фактора под каждую новость.

# 5. Граф знаний

## 5.1. Логическая структура

Предусматриваются два графа, связанных через контролируемые отношения.

**Global Event Graph**

Содержит публичные сущности, события и отношения между ними.

**Company Knowledge Graph**

Содержит корпоративные факты, зависимости, ресурсы, планы и ограничения конкретной компании.

Логически они объединяются только в рамках обработки определённой компании.

Примеры разрешённых путей:

```text
Company
  → buys_from
Supplier
  → uses_route
Route
  ← affects
Event
```

```text
Company
  → produces
Equipment
  → used_in
Industry
  ← demands
InvestmentProject
  ← concerns
Event
```

```text
Event A
  → affects
BusinessFactor
  ← affects
Event B
```

Последняя схема означает общий затронутый фактор, но не доказывает, что события причинно связаны.

## 5.2. KnowledgeEdge

```json
{
  "edge_id": "edge_900",
  "scope": "private",
  "tenant_id": "tenant_1",
  "subject_id": "company_1",
  "predicate": "buys_from",
  "object_id": "supplier_x",
  "evidence_refs": ["chunk_51"],
  "derivation": "extracted",
  "verification_status": "source_supported",
  "valid_from": null,
  "valid_until": null,
  "extractor_version": "extractor_v1"
}
```

Для каждой связи необходимо хранить:

- тип и направление;
- происхождение;
- уровень подтверждения;
- период применимости;
- источник;
- версию извлечения.

`extracted` и `inferred` — характеристики способа получения связи, а не абсолютная гарантия её истинности.

## 5.3. Роль Graphify

Graphify рассматривается как **подключаемый extractor корпоративного графа**.

Утверждённый для MVP вариант:

1. Выполнить извлечение исходного текста документов.
2. Запустить разрешённый Graphify adapter для поддерживаемого корпуса.
3. Получить графовый результат.
4. Преобразовать узлы и рёбра в собственную бизнес-онтологию.
5. Проверить структуру, принадлежность компании и доказательства.
6. Загрузить валидные отношения в PostgreSQL.

Graphify **не является**:

- основным source of truth;
- векторной БД;
- обязательным runtime dependency для каждого поиска;
- системой назначения вероятностей бизнес-эффектам;
- заменой хранения оригинальных документов.

Исходный `graph.json` допускается хранить как производный артефакт для аудита и повторного импорта.

**Требование к адаптеру:**

```python
class GraphExtractor(Protocol):
    async def extract(
        self,
        document_id: str,
        company_id: str,
    ) -> GraphExtractionResult:
        ...
```

Выход должен быть независимым от внутреннего формата Graphify:

```python
class GraphExtractionResult(BaseModel):
    entities: list[ExtractedEntity]
    relations: list[ExtractedRelation]
    source_document_id: str
    extractor_name: str
    extractor_version: str
```

Если связь не удаётся привязать к допустимому источнику, она не должна автоматически попадать в граф подтверждённых фактов.

**Особое замечание:** Graphify может использовать LLM при обработке документов. Перед подключением его к приватным файлам нужно проверить фактический backend, маршрут передачи данных и совместимость с разрешённым API. Автоматический выбор внешнего провайдера не допускается без явной настройки.

## 5.4. Вариант без Graphify

Обязателен простой baseline:

- извлечение фактов обычной LLM;
- валидация Pydantic;
- нормализация по словарю отношений;
- сохранение в той же схеме.

Graphify должен оцениваться по тому, улучшает ли он полноту значимых связей, снижает ли ручную работу и оправдывает ли стоимость извлечения.

## 5.5. Векторное представление графа

Не требуется эмбеддить каждое ребро.

В первой версии embeddings строятся для:

- описаний нормализованных событий;
- описаний бизнес-факторов;
- существенных корпоративных фактов или агрегированных текстовых представлений;
- поисковых фрагментов документов.

Каждый embedding имеет:

- `object_type`;
- `object_id`;
- `model_id`;
- `model_version`;
- `dimension`;
- версию соответствующего текста.

Размерность индекса должна соответствовать модели. Для стандартного HNSW-индекса pgvector тип `vector` поддерживает до 2000 измерений; при выборе более крупной модели потребуется подходящее представление или уменьшение размерности, поддерживаемое самой моделью.

# 6. Обработка корпоративных документов

## 6.1. Последовательность

```text
Document
  → Parse / OCR
  → Structural chunks
  → Fact extraction
  → Entity resolution
  → Relation extraction
  → Provenance validation
  → Graph upsert
  → Embedding / FTS indexing
```

## 6.2. Обязательные свойства

**Structural chunking.**

Разбивать документы с учётом разделов, заголовков и таблиц. Число должно сохраняться вместе с единицей измерения, названием показателя и областью применимости.

**Entity resolution.**

Одинаковые названия не всегда обозначают одну организацию. И наоборот, одна компания может встречаться под несколькими алиасами.

**Temporal validity.**

Срок действия факта не равен дате документа. Для договоров и планов должны быть отдельные поля сроков.

**Provenance.**

Каждый факт сохраняет локатор исходного документа: страницу, раздел, фрагмент либо другой доступный идентификатор.

**Incremental update.**

При изменении документа нужно пересчитывать затронутые факты, связи и индексы, а не весь корпус компании.

## 6.3. Изменение знаний компании

Обновление значимого факта должно инициировать:

1. Пересмотр зависимых графовых связей.
2. Выборку затронутых `CompanyImpact`.
3. Повторную оценку только необходимых воздействий.
4. Пересмотр соответствующих `BusinessIssue`.
5. Обновление общего снимка при существенном изменении вывода.

Для MVP допустима более грубая инвалидация по `knowledge_revision`, если точное отслеживание зависимостей ещё не готово.

# 7. Обработка новостного потока

## 7.1. Нормализация и дедупликация

Каждая новость сохраняется независимо от того, насколько она релевантна существующим компаниям.

Три уровня:

1. **Точная дедупликация:** ID, revision, хеш канонизированного содержимого.
2. **Дедупликация публикаций:** почти одинаковый текст или перепечатка.
3. **Нормализация событий:** различные публикации об одном фактическом событии.

Нельзя объединять события только по cosine similarity.

Для объединения должны учитываться:

- действующие лица;
- действие;
- объект;
- время;
- проект;
- существенные условия.

Исправление новости не должно тихо переписать историю без изменения версии.

## 7.2. Извлечение события

Выполняется один раз для уникального события, а не отдельно для каждого клиента.

Классифицируются:

- тип события;
- упомянутые сущности;
- предмет события;
- временные характеристики;
- модальность;
- потенциально затронутые бизнес-факторы;
- связи с существующими событиями.

Прямая причинно-следственная связь между событиями разрешается только при наличии основания. Тематическая связь маркируется отдельно.

## 7.3. Общий архив

Не следует навсегда выбрасывать новости, признанные нерелевантными текущим компаниям.

При появлении нового клиента или обновлении профиля ранее полученное событие может оказаться существенным.

Поэтому:

- оригинальные новости сохраняются;
- лёгкие индексы доступны для backfill;
- дорогой подробный анализ выполняется только там, где он нужен.

# 8. Candidate generation

## 8.1. Цель

Выбрать достаточно широкий набор потенциально релевантных пар:

`(company_id, event_id)`

При этом не запускать дорогое корпоративное reasoning для всех возможных пар, если поток и количество компаний становятся большими.

## 8.2. Каналы кандидатов

Используется объединение результатов:

1. Совпадения идентификаторов компаний, контрагентов и проектов.
2. Точные совпадения названий, алиасов и терминов.
3. Full-text search.
4. Embedding similarity.
5. Совпадение бизнес-факторов.
6. Графовые пути через подтверждённые зависимости.
7. Обязательные темы и пользовательские подписки.

Первоначально результаты объединяются по OR, чтобы один канал не становился единственной причиной пропуска.

При наличии нескольких ранжированных списков допускается Reciprocal Rank Fusion. Его score не интерпретируется как вероятность релевантности.

## 8.3. Два масштаба поиска

Для небольшого MVP возможен режим:

```text
Каждое событие → все тестовые компании
```

Он полезен как baseline для оценки пропусков.

Для увеличенного числа компаний предпочтительнее:

```text
Событие
  → затронутые сущности и факторы
  → индекс компаний
  → компании-кандидаты
```

Это позволяет не выполнять корпоративный retrieval для каждой пары.

## 8.4. Политика порогов

До размеченных данных:

- не задавать произвольный hard reject по cosine similarity;
- сохранять оценки и причины выбора;
- использовать ограничение top-K как операционную меру при необходимости;
- проводить аудит исключённых кандидатов.

После разметки допускается два порога:

- `t_low` — ориентирован на сохранение recall;
- `t_high` — ориентирован на precision принятого набора;
- промежуток — дополнительная обработка.

`unknown` и недостаток контекста не равнозначны нерелевантности.

Численные значения порогов **не входят в эту спецификацию** и должны быть выбраны экспериментально.

# 9. Hybrid Graph Retrieval

## 9.1. Цель

Для выбранной пары компания–событие сформировать компактный и достаточный набор корпоративных оснований, необходимых для оценки влияния.

## 9.2. Алгоритм

**Шаг 1. Формирование поискового запроса**

Использовать:

- сущности события;
- тип изменения;
- бизнес-факторы;
- регион;
- предмет;
- время;
- известные проекты или контрагентов.

**Шаг 2. Получение первичных кандидатов**

Параллельно выполнить:

- exact/entity lookup;
- PostgreSQL FTS;
- vector search;
- выборку известных графовых зависимостей.

**Шаг 3. Объединение**

Дедуплицировать результаты и объединить ранги. При необходимости использовать reranker, если он улучшает выбор исходных фрагментов.

**Шаг 4. Graph expansion**

От начальных релевантных узлов пройти ограниченное число переходов по разрешённым типам отношений.

Начальный ориентир — до двух дополнительных переходов от найденного seed, с отдельными правилами для разрешённых шаблонов пути. Это параметр, а не ограничение самой бизнес-онтологии.

**Шаг 5. Проверка**

Отфильтровать:

- связи другой компании или tenant;
- недействующие отношения;
- неподтверждённые гипотезы, выдаваемые за факты;
- высокостепенные общие узлы, не дающие содержательного механизма;
- доказательства, не относящиеся к конкретной ситуации.

**Шаг 6. Сборка evidence**

Вернуть сами факты, их источники, существенные условия и графовые пути.

## 9.3. Что не должно происходить

- Не передавать LLM весь подграф без ограничения.
- Не считать путь через «экономику», «Россию» или другую общую сущность достаточной связью.
- Не терять направление зависимости.
- Не скрывать отрицательные и смягчающие факторы.
- Не заменять оригинальные источники неконтролируемым пересказом LLM.

## 9.4. Контракт EvidencePack

```json
{
  "schema_version": "1.0",
  "company_id": "company_1",
  "event_id": "event_201",
  "as_of": "2026-10-22T12:00:00Z",
  "company_knowledge_revision": 7,
  "news": {
    "news_id": "news_101",
    "text": "Полный текст новости...",
    "modality": "announcement"
  },
  "company_facts": [
    {
      "fact_id": "fact_301",
      "text": "Компания закупает упаковку у поставщика X",
      "modality": "current_fact",
      "source_refs": ["chunk_51"]
    }
  ],
  "candidate_paths": [
    {
      "path_id": "path_1",

        "company_1",
```

Полная новость передаётся в assessment, когда помещается в согласованный контекстный бюджет. Если слишком длинная, используется отдельное извлечение с сохранением исходника и источников; молчаливое обрезание запрещено.

# 10. Оценка влияния события

## 10.1. Назначение

Преобразовать evidence pack в типизированную оценку возможного воздействия на конкретную компанию.

Для MVP использовать адаптер `DecisionModel`.

Возможные реализации:

- LLM с проверяемым структурированным ответом;
- Jev через отдельный API;
- Clef через отдельный API;
- эвристический baseline для простых случаев.

Организаторский шлюз предоставляет перечисленные чат-модели, но не Jev. Поэтому реализация на доступной LLM должна работать без Jev.

## 10.2. Требуемые поля

| Поле | Значения |
|---|---|
| `relevance` | relevant / irrelevant / unknown |
| `evidence_sufficiency` | sufficient / conditional / insufficient / conflicting |
| `link_type` | direct / indirect / unknown |
| `risk_supported` | yes / no / unknown |
| `opportunity_supported` | yes / no / unknown |
| `impact_magnitude` | low / medium / high / unknown |
| `urgency` | none / monitor / soon / immediate / unknown |
| `impact_horizon` | short / medium / long / unknown |
| `business_factors` | IDs из справочника |
| `supporting_fact_ids` | IDs фактов |
| `supporting_path_ids` | IDs графовых путей |
| `missing_factors` | Коды недостающих сведений |

## 10.3. Контракт ImpactAssessment

```json
{
  "schema_version": "1.0",
  "event_id": "event_201",
  "company_id": "company_1",
  "relevance": "relevant",
  "evidence_sufficiency": "conditional",
  "link_type": "direct",
  "risk_supported": "yes",
  "opportunity_supported": "unknown",
  "impact_magnitude": "unknown",
  "urgency": "soon",
  "impact_horizon": "short",
  "business_factors": ["procurement_cost"],
  "supporting_fact_ids": ["fact_301"],
  "supporting_path_ids": ["path_1"],
  "missing_factors": [
    "next_order_price_fixation"
  ],
  "event_probability": null,
  "assessment_version": "decision_v1"
}
```

Этот пример синтетический.

## 10.4. Правила

- Модель не может возвращать ссылки на неизвестные `fact_id` и `path_id`.
- Недостающие данные не превращаются в отрицательный эффект.
- Риск и возможность могут существовать одновременно.
- Важность и срочность — разные измерения.
- Confidence модели не является вероятностью финансового исхода.
- При противоречиях между полями результат переводится в дополнительную проверку.
- Если контекст недостаточен, допускается условный вывод.
- Если результата получить не удалось, публикация уверенного анализа запрещена.

После LLM обязательны Pydantic validation, проверка допустимых идентификаторов и проверка логических инвариантов.

Структурная валидация не гарантирует семантическую истинность объяснения — для неё нужны тесты на размеченных примерах.

# 11. BusinessIssue — центральная сущность

## 11.1. Назначение

Объединять различные события, затрагивающие **один конкретный бизнес-вопрос компании**.

Пример:

**Бизнес-ситуация:** изменение себестоимости импортных закупок.

Связанные события:

- повышение стоимости морских перевозок;
- изменение курса валюты закупок;
- пересмотр прайса поставщика.

Каждое событие может оказывать отдельное воздействие. Их общий итог требует учёта условий компании.

## 11.2. Что считается одной ситуацией

Объединение допускается, когда совпадают или содержательно связаны:

- company_id;
- предмет решения;
- бизнес-фактор;
- существенная экспозиция;
- временной горизонт;
- конкретный проект, поставщик или направление деятельности.

Совпадение одного широкого бизнес-фактора недостаточно.

Например, две несвязанные закупки оборудования в разных регионах не обязаны становиться одной ситуацией.

## 11.3. Статусы

- `active` — актуальная ситуация;
- `watching` — дальнейшее изменение может иметь значение;
- `resolved` — рассмотрена или решена;
- `superseded` — заменена новой формулировкой;
- `archived` — потеряла применимость.

Пользовательское состояние — открыто, просмотрено, закрыто — хранится отдельно от бизнес-статуса.

## 11.4. Контракт BusinessIssue

```json
{
  "schema_version": "1.0",
  "issue_id": "issue_import_cost_1",
  "company_id": "company_1",
  "title": "Стоимость импортных закупок",
  "business_factors": [
    "procurement_cost",
    "logistics"
  ],
  "event_ids": [
    "event_201",
    "event_202",
    "event_203"
  ],
  "impact_ids": [
    "impact_501",
    "impact_502",
    "impact_503"
  ],
  "status": "active",
  "overall_effect": "mixed",
  "evidence_sufficiency": "conditional",
  "summary": "На стоимость закупок действуют разнонаправленные факторы.",
  "key_unknowns": [
    "Валюта ближайшего заказа",
    "Условия фиксации цены"
  ],
  "suggested_action": "Проверить условия ближайших отгрузок.",
  "version": 3,
  "as_of": "2026-10-22T12:00:00Z"
}
```

## 11.5. Алгоритм обновления

Для нового `CompanyImpact`:

1. Найти существующие ситуации компании, связанные с затронутыми факторами.
2. Отобрать кандидатов по предмету, сущностям, горизонту и графовым зависимостям.
3. Проверить, относится ли новое воздействие к существующему вопросу.
4. Если относится — добавить воздействие и пересчитать вывод.
5. Иначе — создать новую бизнес-ситуацию.
6. Определить, изменились ли значимые поля.
7. Сохранить новую версию только при содержательном изменении.

Для неоднозначных объединений допускается один вызов LLM. Очевидные совпадения обрабатываются кодом.

**Важно:** изменение нескольких релевантностей не даёт численного совокупного эффекта. Для количественного расчёта требуются реальные величины, зависимости и временные условия.

## 11.6. Защита от ошибок накопления

Нельзя формировать новую версию так:

`старое LLM-summary + новая новость → новое summary`

на протяжении неограниченного числа циклов.

При каждом содержательном пересчёте должны использоваться актуальные структурированные воздействия и их источники.

Предыдущая версия применяется для определения изменений, но не заменяет исходные данные.

---

# 12. SituationSnapshot — текущее положение дел компании

## 12.1. Назначение

Формировать общую картину актуальных внешних факторов, влияющих на компанию.

В снимок входят:

- важнейшие активные бизнес-ситуации;
- разнонаправленные и совместные эффекты;
- срочные вопросы;
- возможности;
- существенные неизвестные;
- изменения по сравнению с предыдущим обзором;
- следующие действия и основания для наблюдения.

## 12.2. Контракт

```json
{
  "schema_version": "1.0",
  "snapshot_id": "snapshot_10",
  "company_id": "company_1",
  "as_of": "2026-10-22T12:00:00Z",
  "news_processed_through": "2026-10-22T11:58:00Z",
  "company_knowledge_revision": 7,
  "issue_version_ids": [
    "issue_import_cost_1:v3",
    "issue_market_2:v2"
  ],
  "overall": {
    "summary": "На компанию воздействуют изменения закупочных затрат и новые рыночные возможности.",
    "key_unknowns": [
      "Условия цены ближайших закупок"
    ]
  },
  "priority_issues": [
    {
      "issue_id": "issue_import_cost_1",
      "issue_version": 3,
      "reason": "Предстоящее изменение условий закупки.",
      "action_required": true
    }
  ],
  "changes_since_previous": [
    {
      "issue_id": "issue_import_cost_1",
      "change_type": "new_condition",
      "description": "Появилась информация о пересмотре прайса."
    }
  ],
  "snapshot_version": 4
}
```

`news_processed_through` обозначает watermark обработанных системой данных, а не утверждение о полноте всех мировых новостей.

## 12.3. Правила генерации

Генеративная LLM получает:

1. Краткий структурированный профиль компании.
2. Активные BusinessIssue.
3. Их версии, основания и ключевые условия.
4. Изменения относительно предыдущего снимка.
5. Ограничения по длине и формату результата.

Основной ответ должен быть пригоден для чтения сразу.

Не требуется запускать отдельный LLM-вызов, если:

- существует только одна актуальная ситуация;
- её сохранённый разбор уже полностью подходит;
- ничего содержательно не изменилось.

В таком случае обзор можно собрать детерминированно.

## 12.4. Триггеры пересчёта

| Триггер | Действие |
|---|---|
| Новая новость | Обновить затронутые воздействия |
| Новая значимая BusinessIssue | Обновить общий снимок |
| Изменился вывод или срок существующей ситуации | Обновить общий снимок |
| Неизменное повторное сообщение | Не перегенерировать |
| Изменён корпоративный факт | Пересчитать затронутые ситуации |
| Плановый запуск | Проверить актуальность и подготовить обзор |
| Пользователь запросил обновление | Вернуть готовый актуальный snapshot или инициировать пересчёт |

Начальный вариант планирования:

- периодическая утренняя проверка;
- немедленная обработка потенциально срочных изменений;
- debounce для серии обычных новостей;
- переиспользование сохранённого результата.

Конкретные интервалы определяются конфигурацией и нагрузочным экспериментом.

## 12.5. Существенность изменения

В первой версии определяется прежде всего по структурным признакам:

- новая бизнес-ситуация;
- изменение основного воздействия;
- изменение срочности;
- появление или исчезновение решающего условия;
- изменение рекомендуемого действия;
- изменение существенного срока;
- закрытие или повторное открытие ситуации.

Не нужно вызывать LLM только для сравнения двух одинаковых JSON.

# 13. Подготовка пользовательского результата

## 13.1. До открытия

Для публикуемой значимой ситуации должны быть подготовлены:

- заголовок, объясняющий бизнес-смысл;
- краткий вывод;
- решающий фактор компании;
- важные условия;
- следующий шаг;
- основания;
- полная структурированная версия разбора.

Основная сводка также сохраняется заранее.

## 13.2. При открытии

Должен возвращаться сохранённый результат без обязательного нового LLM-вызова.

Допускается дополнительная генерация только при:

- новом вопросе;
- новом сценарии;
- запросе более глубокого анализа;
- изменившихся данных, делающих сохранённый результат устаревшим.

## 13.3. Обсуждение

Каждое обсуждение привязано к конкретной версии BusinessIssue или SituationSnapshot.

В prompt передаются:

- выбранный сохранённый результат;
- необходимые доказательства;
- пользовательский вопрос;
- ограниченная релевантная история;
- актуальные права доступа.

Гипотетический сценарий не меняет корпоративную базу фактов автоматически.

## 13.4. История

Хранятся:

- опубликованные результаты и их версии;
- пользовательские статусы;
- связанные диалоги;
- значимые изменения;
- ссылки на источники;
- информация об устаревании.

Не следует смешивать сохранение продукта с сохранением execution state LangGraph.

## 14.4. Адаптеры

Минимальные интерфейсы:

```python

    async def assess(self, evidence: EvidencePack) -> ImpactAssessment:
        ...

class SynthesisModel(Protocol):
    async def summarize_issue(self, issue_context: dict) -> dict:
        ...

    async def summarize_company(self, snapshot_context: dict) -> dict:
        ...

class GraphRetriever(Protocol):
    async def retrieve(
        self,
        company_id: str,
        event_id: str,

        ...
```

Реализации должны быть заменяемыми без изменения доменной логики.

# 15. Оркестрация LangGraph

Не требуется единый огромный граф, выполняющий вообще всё.

Предпочтительны небольшие независимые workflow.

## 15.1. News Ingestion Workflow

```text
receive
  → validate envelope
  → deduplicate
  → extract event
  → resolve entities
  → update global index
  → dispatch candidate analysis
```

## 15.2. Company Impact Workflow

```text
event + company
  → hybrid retrieval
  → graph expansion
  → evidence pack
  → decision model
  → validate
  → route
  → save assessment
  → update issue
```

Маршруты:

- `accepted`;
- `irrelevant`;
- `needs_context`;
- `inconsistent`;
- `failed`.

## 15.3. BusinessIssue Workflow

```text
new impact
  → candidate issues
  → match / create
  → collect current impacts
  → synthesize if necessary
  → validate evidence
  → calculate changes
  → persist issue version
```

## 15.4. Company Snapshot Workflow

```text
trigger
  → load active issues
  → detect significant changes
  → decide regeneration
  → synthesize if needed
  → validate
  → persist snapshot
  → publish update
```

## 15.5. Conversation Workflow

```text
question
  → load pinned result
  → retrieve extra evidence if needed
  → generate answer
  → validate references
  → persist message
```

## 15.6. Сохранение состояния

LangGraph checkpointer нужен для:

- возобновления прерванной обработки;
- повторного выполнения после исправимой ошибки;
- отладки;
- обработки уточнений.

Он не должен заменять таблицы `CompanyImpact`, `BusinessIssue` и `SituationSnapshot`.

Побочные эффекты должны выполняться идемпотентно. Повторный запуск workflow не должен создавать дубли публикаций, ситуаций или готовых карточек.

# 16. Хранение, индексы и кэширование

## 16.1. Хранилище

**PostgreSQL:**

- корпоративные сущности;
- нормализованные события;
- типизированные связи;
- assessments;
- issues;
- snapshots;
- пользовательская история;
- метаданные заданий.

**pgvector:**

- embeddings текстовых представлений;
- связь вектора с объектом, версией текста и embedding-моделью.

**Object storage или существующее файловое хранилище:**

- оригинальные документы;
- большие исходные файлы;
- производные extraction-артефакты при необходимости.

## 16.2. Индексы

Минимальные индексы:

- уникальность `(source, news_id, revision)`;
- связи события с публикациями;
- связи событий и сущностей;
- `tenant_id + company_id`;
- активные BusinessIssue компании;
- временные поля для актуальности;
- GIN для нужных полнотекстовых полей;
- vector index для совместимой размерности;
- поиск `KnowledgeEdge` по начальной вершине, типу и времени;
- уникальность ключей идемпотентности.

При небольших объёмах vector search может начинаться с exact search. ANN-индексацию следует выбирать после оценки размера корпуса и задержек.

## 16.3. Кэш-ключи

Для assessment существенны:

- event revision;
- company knowledge revision;
- retrieval version;
- model ID;
- prompt version;
- assessment schema version;
- политика обработки.

Для snapshot:

- company ID;
- роль и права пользователя;
- выбранные issue versions;
- synthesis model и prompt version;
- temporal context.

Если появился новый существенный корпоративный факт, кэшированный вывод не должен считаться актуальным только потому, что ранее использованные fact IDs не изменились.

## 16.4. Ретенция

- Готовые опубликованные разборы и сообщения сохраняются как продуктовая история.
- Устаревшие версии маркируются, а не бесследно переписываются.
- Operational checkpoints и debug payloads имеют ограниченный срок хранения.
- Крупные промежуточные состояния не должны бесконтрольно дублироваться.
- Пользовательские и корпоративные данные удаляются по предусмотренной политике доступа и удаления.

Численные сроки хранения определяются командой с учётом условий хранения данных. В MVP достаточно конфигурируемой политики.

# 17. Планировщик и инкрементальность

## 17.1. Принцип

Не запускать полную генерацию снимка на каждую входящую новость.

Каждое событие сначала обновляет структурированное состояние.

Затем определяется, требуется ли пересчёт готового пользовательского результата.

## 17.2. Обработка обычных событий

- Нормализовать и сохранить.
- Обновить затронутые CompanyImpact.
- Пересчитать необходимые BusinessIssue.
- Сопоставить версии.
- Если ключевые поля не изменились — не вызывать общий генератор.
- Если изменились — назначить обновление snapshot.

## 17.3. Срочные события

Потенциально срочное событие должно проходить без задержки обычного debounce, если при подтверждённом контексте ожидание может лишить пользователя возможности своевременно действовать.

Срочность — отдельный продуктовый критерий; высокая тематическая релевантность сама по себе не означает срочность.

## 17.4. Периодический пересчёт

Плановая задача должна:

- проверять актуальность активных ситуаций;
- обнаруживать пропущенные или ранее не обработанные обновления;
- учитывать истечение известных сроков;
- пересобирать обзор из структурированных данных при необходимости;
- переиспользовать готовый результат, если существенных изменений нет.

Старые события не исчезают только потому, что опубликованы более суток назад.

# 19. Надёжность и безопасность

## 19.1. Неуспешные LLM-ответы

Обрабатывать отдельно:

- невалидный JSON;
- недостающие поля;
- усечённый ответ;
- неизвестный evidence ID;
- несогласованные оценки;
- timeout;
- rate limit;
- временную недоступность модели;
- ошибку авторизации;
- исчерпание бюджета.

Для исправимых ошибок допускается ограниченный retry.

Бесконечные повторные вызовы запрещены.

## 19.2. Бюджет

На ключ организаторов действует общий лимит **500 ₽/сутки**.

Нужно записывать:

- model ID;
- этап;
- количество вызовов;
- input/output tokens при наличии;
- latency;
- ошибки;
- оценочную стоимость, если тарифы известны.

Локальная оценка расходов не является гарантированным остатком общего командного бюджета.

При `Budget has been exceeded`:

1. Прекратить новые платные операции.
2. Сохранить незавершённые задания в допустимом состоянии.
3. Не запускать повторные попытки до восстановления бюджета.
4. Продолжать отдавать сохранённые готовые результаты.

## 19.3. Защита данных

- Приватные факты компании не могут попасть в результаты другой компании.
- Tenant scope применяется на уровне запросов к БД, а не только prompt.
- Глобальный граф содержит только допустимые общие сведения.
- Передача корпоративных документов внешним моделям должна соответствовать согласованным ограничениям.
- Текст новости и документа считается **данными**, а не командами для агента, даже если новость прошла проверку достоверности.
- Инструкции, встроенные в документ, не должны изменять системный prompt, вызвать инструменты или раскрывать секреты.

## 19.4. Отказоустойчивость

Предусмотреть:

- детерминированные idempotency keys;
- уникальность результатов обработки;
- transaction boundaries;
- ограничение параллелизма;
- диагностику зависших задач;
- безопасное восстановление после рестарта;
- отсутствие дубликатов готовых карточек при повторном клике или запросе.

# 20. Метрики качества

Метрики разделяются по этапам.

## 20.1. Event extraction

- качество извлечения сущностей;
- корректность модальности;
- качество дедупликации;
- корректность нормализации одного события из нескольких публикаций.

## 20.2. Retrieval

- Recall@K корпоративных доказательств;
- Recall@K для косвенных зависимостей;
- доля ложных графовых путей;
- полнота временных и ограничивающих условий;
- p50/p95 retrieval latency;
- стоимость индексирования.

## 20.3. Candidate generation

- recall значимых company-event пар;
- доля пропущенных косвенных событий;
- доля кандидатов, требующих дорогой обработки;
- число обработанных пар на одно событие;
- экономия относительно baseline без отбора.

Необходимо размечать часть исключённых кандидатов.

## 20.4. Impact assessment

- precision / recall полезных событий;
- корректность `unknown`;
- качество классификации риска и возможности;
- частота противоречий;
- доля необоснованных утверждений;
- стоимость одного assessment.

## 20.5. Multi-event reasoning

- корректность объединения BusinessIssue;
- сохранение существенных отдельных событий;
- качество анализа разнонаправленных воздействий;
- отсутствие необоснованного сложения оценок;
- качество определения изменений.

## 20.6. Продуктовые метрики

- время до первого полезного результата;
- время до обоснованного решения;
- доля полезных подготовленных разборов;
- пропущенные существенные ситуации;
- ложные срочные сигналы;
- качество рекомендаций;
- доля успешных уточнений;
- возвращение к ранее рассмотренным ситуациям;
- стоимость полезного результата.

Количество кликов не является основной целевой метрикой.

| T11 | LLM придумывает evidence ID | Результат отклоняется |
| T12 | Важная старая ситуация остаётся актуальной | Не исчезает из snapshot из-за даты публикации |
| T13 | У компании нет релевантных новостей | Пустое или спокойное состояние без искусственных карточек |
| T14 | Два параллельных запуска обрабатывают одно событие | Идемпотентный результат |
| T15 | Исчерпан API-бюджет | Сохранённые результаты доступны, платные повторы остановлены |
| T16 | Пользователь задаёт гипотетический вопрос | Профиль компании не изменяется |
| T17 | Одна компания пытается получить evidence другой | Доступ запрещён |
| T18 | Источник содержит prompt injection | Инструкция внутри источника не исполняется |
| T19 | Изменилось только оформление summary | Нет необоснованного изменения бизнес-состояния |
| T20 | Отменено или перенесено запланированное событие | Состояние связанных ситуаций корректно обновляется |

# 22. Сравнение архитектурных вариантов

Экспериментальная часть обязательна: выбранные компоненты считаются начальными инженерными решениями, а не доказанным оптимумом.

## 22.1. Retrieval

Сравнить:

- A: полнотекстовый поиск и структурированный профиль;
- B: A + embeddings;
- C: B + типизированные графовые пути;
- D: C + автоматическое извлечение Graphify.

Условия сравнения:

- одинаковые документы;
- одинаковый входной набор событий;
- одинаковый контекстный бюджет;
- одинаковая модель конечного анализа.

## 22.2. Оценка

Сравнить:

- один генеративный вызов на оценку и текст;
- отдельный типизированный assessment + генерация;
- assessment с дополнительным retrieval для неопределённых случаев.

Сравнивать качество, задержку и стоимость.

## 22.3. Синтез нескольких событий

Baseline:

> Взять top-N релевантных событий и передать их одной LLM для общей сводки.

Основной вариант:

> Нормализовать события, собрать CompanyImpact, сгруппировать BusinessIssue и затем выполнить synthesis.

Измерить, действительно ли сложная архитектура улучшает точность взаимосвязей и сохранение контекста при приемлемой стоимости.

Если baseline не хуже на фактической нагрузке, дальнейшее усложнение не должно быть самоцелью.

## 22.4. Пороговая политика

Подбор значений выполняется на размеченной валидационной выборке.

Определяются:

- цена пропуска значимого события;
- цена ложного сигнала;
- доступный бюджет дополнительной проверки;
- ограничения по latency;
- целевая полнота.

Пороги, калибровка и рабочая политика версионируются.

- не переписывать работающие компоненты без необходимости.

**Результат:** карта текущего состояния и перечень изменений.

## Этап 1. Доменная модель и persistence

Реализовать:

- Pydantic-контракты;
- PostgreSQL migrations;
- сущности Event, CompanyFact, KnowledgeEdge, CompanyImpact, BusinessIssue, SituationSnapshot;
- версионирование;
- уникальность и идемпотентность.

**Готовность:** доменные сущности сохраняются и читаются независимо от LLM.

## Этап 2. Новостной ingestion

Реализовать:

- входной адаптер;
- дедупликацию;
- извлечение событий;
- нормализацию сущностей;
- индексирование;
- тесты с несколькими публикациями одного события.

**Готовность:** повторный ввод не создаёт дубли.

## Этап 3. Контекст компании

Реализовать:

- extraction;
- разбиение документов;
- сохранение фактов с provenance;
- FTS;
- embeddings;
- базовые типизированные связи.

**Готовность:** по событию находятся конкретные корпоративные доказательства.

## Этап 4. Graph retrieval

Реализовать:

- поиск seed nodes;
- ограниченный обход;
- проверку принадлежности и актуальности;
- evidence pack;
- тестирование косвенных путей.

**Готовность:** система находит обоснованные непрямые связи, не пропуская приватные или недействующие отношения.

## Этап 5. Impact assessment

Реализовать:

- DecisionModel adapter;
- вызов организаторского API;
- структурированный output;
- Pydantic validation;
- обработку unknown;
- маршрутизацию результатов;
- budget handling.

**Готовность:** одна новость обоснованно оценивается для разных компаний.

## Этап 6. BusinessIssue

Реализовать:

- сопоставление существующих ситуаций;
- группировку событий;
- версионирование;
- анализ совместного влияния;
- определение существенных изменений.

**Готовность:** несколько событий могут формировать одну обновляемую бизнес-ситуацию.

## Этап 7. SituationSnapshot

Реализовать:

- сбор активных ситуаций;
- общий synthesis;
- периодические и событийные триггеры;
- сохранение готовых разборов;
- отслеживание изменений.

**Готовность:** пользователь получает подготовленную актуальную сводку без обязательного LLM-вызова при открытии.

## Этап 8. Интерфейсы для backend

Реализовать согласованные сервисные операции:

- получение текущего состояния;
- получение готового разбора;
- получение оснований;
- история версий;
- обновление профиля;
- вопросы по конкретной ситуации.

**Готовность:** frontend может показать полный сценарий на реальных данных пайплайна.

## Этап 9. Graphify adapter

Добавить за feature flag:

- запуск extraction;
- маппинг результатов;
- проверку источников;
- загрузку в общий формат графа;
- тестирование качества против baseline.

**Готовность:** Graphify можно включать и выключать без изменения других компонентов.

Не блокировать предыдущие этапы отсутствием интеграции Graphify.

## Этап 10. Качество и оптимизация

Реализовать:

- оценочный датасет;
- recall/precision метрики;
- стоимость и задержки по этапам;
- аудит исключённых кандидатов;
- сравнение архитектур;
- настройку порогов;
- оптимизацию context budget и модельных вызовов.

# 24. Definition of Done для MVP

MVP считается реализованным, когда выполняются все следующие условия.

**Данные:**

- Новости поступают по согласованному контракту.
- Дубликаты корректно обрабатываются.
- Компания имеет версионированный профиль.
- Существенные факты сохраняют источники.
- События и графовые связи доступны для retrieval.

**Анализ:**

- По одной новости можно получить разные обоснованные оценки для разных компаний.
- Находится хотя бы один тестовый косвенный механизм влияния.
- Несколько событий могут объединяться в одну бизнес-ситуацию.
- Разнонаправленные воздействия не объединяются арифметически без оснований.
- Система допускает неизвестность и условные выводы.

**Пользовательский результат:**

- Есть готовый обзор положения компании.
- В нём представлены значимые BusinessIssue.
- Обзор содержит изменения с прошлой версии.
- Открытие готового результата не требует обязательной новой генерации.
- Сохранены источники и история.
- Уточняющий вопрос обрабатывается в контексте конкретной ситуации.

**Надёжность:**

- Все LLM-ответы проходят структурную проверку.
- Ключ API не содержится в репозитории.
- Исчерпание бюджета не приводит к бесконечным повторам.
- Повторный запуск не создаёт дубликатов.
- Изоляция корпоративных данных соблюдается.
- Критические сценарии покрыты автоматическими тестами.

**Оценка качества:**

- Есть baseline без графа.
- Можно измерить время и токены каждого этапа.
- Можно воспроизвести результат по сохранённым версиям исходных данных, схемы и моделей.
- Все незаполненные эмпирические параметры явно помечены как требующие измерения.

# 25. Что откладываем после MVP

Не включать в обязательный объём первой реализации:

- полноценную графовую БД Neo4j;
- замену основного хранилища на Graphiti;
- автоматическое многошаговое agentic browsing по внешнему интернету;
- построение большого причинного графа экономики;
- обучение собственного LLM-классификатора;
- численные прогнозы будущей прибыли без данных и калибровки;
- десятки специализированных LLM-агентов;
- сложное RL-ранжирование;
- отдельный сервис предсказания кликов;
- Kafka/Flink ради небольшого потока;
- полное event sourcing, если достаточно версий и журнала изменений;
- массовые уведомления без продуктовой проверки их полезности.

Эти возможности могут быть добавлены при наличии конкретных требований, измеренных проблем или подтверждённого выигрыша.

# 27. Продуктовый демонстрационный сценарий

Основное демо должно показывать не просто работу модели, а ценность архитектуры.

**Сценарий:** производственная компания зависит от импортных комплектующих.

В корпоративном профиле:

- известен поставщик;
- известно направление поставок;
- указан способ определения закупочной цены;
- есть планируемая поставка.

Поступают три проверенные новости:

1. Повышение стоимости логистики.
2. Изменение курса валюты закупок.
3. Изменение условий прайса поставщика.

Ожидаемый результат:

**Уровень событий:** система корректно нормализует три различных события.

**Уровень графа:** находит их связь с корпоративными поставками и общим фактором стоимости закупок.

**Уровень CompanyImpact:** отдельно определяет возможное воздействие каждого события.

**Уровень BusinessIssue:** объединяет воздействия в вопрос стоимости ближайших закупок, учитывает разнонаправленность и условия.

**Уровень SituationSnapshot:** формирует готовый вывод о положении компании.

**Уровень диалога:** пользователь уточняет условие контракта.

**Уровень обновления:** после нового документа система изменяет только затронутый анализ и показывает, что изменилось.

Результат должен содержать реальные ссылки на переданные доказательства. Все количественные оценки, отсутствующие во входных данных, остаются неизвестными.

**Главный демонстрируемый эффект:** система самостоятельно соединяет разрозненные внешние события с конкретными бизнес-зависимостями и выдаёт готовую картину, на основе которой можно действовать.

# 28. Инструкция для разработки

При реализации необходимо соблюдать следующие правила:

1. Сначала изучить текущее устройство репозитория и уже существующие интерфейсы.
2. Не реализовывать параллельную архитектуру, если нужный компонент уже существует.
3. Строго разделить domain, persistence, retrieval, model adapters и orchestration.
4. Использовать типизированные Python-контракты и валидацию.
5. Детерминированные операции выполнять обычным кодом.
6. Не добавлять новый LLM-вызов без объяснения его роли и проверяемой пользы.
7. Обеспечить возможность работы без Graphify.
8. Не использовать LLM-summary как источник истины вместо фактов и доказательств.
9. Все важные объекты должны быть версионируемыми и воспроизводимыми.
10. По умолчанию использовать модельные заглушки в unit tests.
11. Реальные вызовы API выносить в отдельные integration tests.
12. Не изменять чужие ветки и не выполнять commit/push без явного разрешения команды.
13. Не публиковать API-ключи и чувствительные корпоративные данные.
14. Не считать приведённые здесь гипотезы подтверждёнными метриками.
15. При конфликте между текущей реализацией и спецификацией сначала документировать расхождение, затем согласовывать изменение контракта.

# 30. Краткий итог

**Реализуем не рекомендательную ленту новостей, а систему постоянного мониторинга внешних бизнес-факторов компании.**

Её основная цепочка:

**Проверенные новости → нормализованные события → общий граф событий → поиск корпоративных зависимостей → персональная оценка влияния → накопление BusinessIssue → совместный анализ → SituationSnapshot → готовый обзор и отслеживание изменений.**

Технологическая основа MVP:

- PostgreSQL — source of truth.
- pgvector и FTS — поиск.
- Типизированные связи — граф бизнес-зависимостей.
- Graphify — опциональный extractor с единым контрактом.
- LangGraph — выполнение и восстановление аналитических workflow.
- Организаторский OpenAI-compatible API — структурный и генеративный анализ.
- Версионированные BusinessIssue и SituationSnapshot — долгосрочное представление положения компании.

**Главный критерий правильности архитектуры: пользователь сразу получает полезную, обоснованную и актуальную картину положения своего бизнеса, а не очередную задачу по самостоятельному чтению и анализу новостей.**
