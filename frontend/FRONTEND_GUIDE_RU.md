# «Сигнал»: инструкция по frontend

Этот документ описывает запуск, основные пользовательские пути и границы между рабочим API и локальной демонстрацией. Технические маршруты и payload собраны в [контракте интеграции](./BACKEND_INTEGRATION_RU.md); серверные решения — в [`backend/API.md`](../backend/API.md) и [заметках объединённого runtime](../docs/integration-main-2026-10-24.md).

## 1. Структура и маршруты

`frontend/src/` содержит страницы, API-клиент и компоненты; `frontend/tests/` — unit и Playwright проверки. Go раздаёт production frontend и принимает запросы на том же origin.

| Адрес | Назначение |
| --- | --- |
| `/bank.html` | Изолированная демонстрация банковской главной; не использует банковскую сессию |
| `/landing` | Описание сервиса |
| `/register`, `/login` | Создание аккаунта и вход |
| `/dashboard` | Бизнес-ситуация, сводка и лента |
| `/news/:itemId` | Разбор новости и TXT-экспорт |
| `/issues/:issueId` | Бизнес-ситуация, основания, история и чат |
| `/profile?tab=roles\|company\|keywords\|documents` | Кабинет компании |

Старые адреса `/onboarding`, `/feed`, `/feed/:itemId` и `/company` перенаправляются на актуальные маршруты.

## 2. Режимы запуска

Режим выбирается при запуске или сборке через `VITE_DATA_MODE`. Без явной настройки используется `api`.

```bash
cd frontend
npm ci
VITE_DATA_MODE=demo npm run dev
```

Для Go API: `VITE_DATA_MODE=api npm run dev`. Vite проксирует `/api` на `http://localhost:8080`. Production использует тот же origin для UI и API. Режим уже собранного приложения нельзя поменять переменной окружения без новой сборки.

`api` вызывает сервер и показывает ошибки без автоматической подмены fixtures. `demo` полностью автономен: вход, регистрации и данные остаются локальными, запросы не отправляются. Demo-аккаунты существуют только в demo fixture: `finance@signal.demo` и `operations@signal.demo`, пароль `SignalDemo2026!`.

## 3. Сессия и регистрация

В API-режиме `/login` отправляет email и пароль на `POST /api/v1/auth/login`. Go устанавливает HttpOnly cookie. При запуске приложения frontend обращается к `/api/v1/auth/me`; localStorage не считается подтверждением входа. Выход вызывает серверный logout, и ошибка сервера показывается пользователю.

Регистрация состоит из двух экранов, но серверный вызов один: финальная отправка делает атомарный `POST /api/v1/onboarding` с `company` и `user`, включая пароль. Повтор с тем же idempotency key безопасен при неопределённом результате сети. Черновик может сохранить остальные поля формы, но не пароль и не его hash. Backend не разрешает подключение к существующей компании по одному ИНН.

В demo проверка demo-аккаунта и создание профиля происходят локально. Этот путь не создаёт Go-сессию.

## 4. Обзор, события и оценки

`/dashboard` объединяет серверную бизнес-ситуацию и issue-список с лентой событий. Суточная сводка берёт новости за последние 24 часа по дате публикации из последних 200 записей всех назначенных ролей. Каждая новость учитывается один раз по `news.id`; из нескольких ролевых разборов выбирается запись с наибольшим приоритетом. Это сводка загруженной ленты, а не серверное резюме ИИ и не полный архив компании.

Полоса показывает распределение по типам, а стрелки обозначают риск и возможность — не вероятность и не изменение за день. Кнопки сводки снимают несовместимые поиск и фильтр закладок и при необходимости переключают роль на ту, где есть выбранные события. Пустой результат и ошибка запроса показываются отдельно, без подстановки demo KPI.

Сегменты полосы доступны мышью и клавиатурой: наведение и фокус выделяют соответствующую категорию, активация включает её фильтр и переносит фокус к ленте. Счётчик ленты показывает количество видимых записей из записей активной роли; фильтр «Все» относится к этой роли. Если выбранного типа нет, но он есть у другой назначенной роли, предлагается явная кнопка переключения. После ручного обновления появляется «Лента без изменений» или «Лента обновлена»; при ошибке успешное подтверждение не показывается.

В API-режиме успешная пустая выборка активной роли перепроверяется каждые 15 секунд, пока вкладка видима: не более четырёх автоматических повторов на выборку пользователя и набора ролей. Ошибка останавливает этот опрос. Кнопка «Обновить события» рядом с заголовком ленты и возврат во вкладку позволяют получить более поздний результат. Для аналитических задач экран отдельно использует server job status и статус документа; опрос ленты не подтверждает завершение модели.

Совместимый `/rank` передаёт в live `score` ordinal-уровень срочности/приоритета, не вероятность и не релевантность. Поэтому live подписи используют «срочность» или «приоритет». «Релевантность» может быть подписью только у demo fixture с такой семантикой.

## 5. Issue, основания и чат

Issue можно открыть, чтобы просмотреть детали, evidence (источники и основания), историю и пользовательское состояние. Ссылки источников берутся из ответа сервера и должны вести на HTTP(S). Загруженный документ не считается использованным, пока backend не свяжет его с выводом.

Чат привязан к версии issue, на которой начался разговор. UI ждёт загрузки существующего разговора и отправляет вопросы с его pinned version. Если issue изменился, для актуальной версии нужно явно начать новый разговор; версия не меняется молча.

Обновление запускает analytics refresh и показывает состояние job. При необходимости повторной обработки документов запрашивается retry failed. В кабинете в разделе документов доступны состояния `queued`, `ready` и `failed`, а также повторная обработка неудавшихся файлов. Отображаемый статус описывает результат backend, а не наличие файла в форме загрузки.

## 6. Кабинет и локальные данные

Кабинет содержит роли, сведения компании, ключевые слова и документы. Роли можно переключать для просмотра и изменять через доступный UI. Сложные поля профиля отображаются по согласованным данным, а не интерпретируются по догадке. Загрузка передаёт содержимое файла Go API; ограничение UI — 12 МиБ. Demo сохраняет только метаданные локального файла и ничего не отправляет.

Часть настроек и избранное остаются локальными для браузера и не синхронизируются с сервером. Аналитические данные в API-режиме принадлежат текущей Go-сессии; frontend не отправляет analytics proxy company/user ID. Подробный контракт хранения — в [документе интеграции](./BACKEND_INTEGRATION_RU.md).

Плашки «Демо» и коды элементов профиля в карточках убраны. Числовые графики и виджеты сохраняют видимое пояснение «Источник данных не подключён»; подробности локальных функций доступны в раскрывающихся разделах. TXT продолжает явно указывать синтетическое происхождение demo-данных и коды профиля. В разделе «Аналитика от Альфа-Банка» сохраняется сообщение об отсутствии или непереданных сведениях: название блока не подтверждает участие банка в разборе. «Решения Альфа-Банка» — отдельный справочный каталог без серверной персонализации.

## 7. Проверка

Из `frontend/`:

```bash
npm test
npm run typecheck
npm run build
npm run test:e2e
```

После повторного объединения 24 октября 2026 года прошли 154 unit-теста, TypeScript, production build и все 55 Playwright сценариев: 27 demo и 28 API. Mock API тесты проверяют контракты и интерфейс. Backend-код не менялся; успешный совместный `scripts/test_unified.py` с Go/Python и временной PostgreSQL БД относится к предыдущему раунду интеграции, заново он не запускался. Подробности — в [отчёте интеграции](../docs/integration-main-2026-10-24.md).

## 8. Основные файлы

- `src/App.tsx` — маршрутизация и проверка сессии;
- `src/api/client.ts` — API/demo transport и проверки формы ответа;
- `src/pages/` — страницы Signal, включая бизнес-ситуацию и issue;
- `src/auth/` — onboarding draft и клиентские проверки формы;
- `src/report.ts` — источники, формулировки и TXT-экспорт;
- `src/localState.ts` — локальные настройки;
- `tests/` — unit и браузерные проверки.
