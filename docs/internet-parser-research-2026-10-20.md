# Техническое исследование интернет-парсера для персонализированной новостной аналитики крупного бизнеса

Исследование выполнено по состоянию на **20 октября 2026 года**. Оно ограничено обнаружением интернет-материалов, их загрузкой, нормализацией, извлечением содержания и фактов, отслеживанием версий и адресным поиском источников. Обработка банковских PDF, модель оценки влияния новости на компанию, генерация аналитического отчета, чат и frontend остаются за границей рассматриваемого компонента.

## Рекомендация и границы решения

### Рекомендуемый MVP

**Основной вывод:** для первого работающего варианта разумнее **не строить отдельную универсальную crawling-платформу и не вводить Python-сервис заранее**, а расширить существующий Go-backend четырьмя хорошо отделенными возможностями:

1. **Discovery adapters** для RSS/Atom/API и небольшого числа известных HTML-страниц.
2. **Единый безопасный HTTP fetcher** с дедупликацией запросов, условными GET, ограничениями частоты, версионированием и политикой допустимого использования источника.
3. **Двухуровневое извлечение текста:** правила конкретного источника для приоритетных сайтов плюс универсальный extractor как fallback.
4. **Отдельный adapter поискового API** для адресного поиска, который возвращает кандидаты-URL в тот же общий конвейер, а не создает отдельный «Deep Research».

На текущем наборе библиотек это можно сделать преимущественно в Go: существующий RSS-код оставить там, где он достаточен, либо унифицировать feeds через `gofeed`; серверный HTML разбирать `net/http` + `goquery`; универсальное извлечение экспериментально закрыть `go-trafilatura`. Современный `go-readability` как новую базовую зависимость я бы не выбирал: репозиторий `go-shiori/go-readability` был архивирован владельцем в декабре 2025 года. `goquery`, напротив, продолжает обновляться, как и `chromedp`; для последнего и для свежих версий `goquery` следует сначала проверить версию Go в проекте, поскольку последние релизы подняли требования к toolchain. citeturn7search1turn7search2turn7search3turn8search12

**Python-sidecar имеет смысл не «на всякий случай», а после сравнительного теста.** Сильнейший аргумент за него — не RSS или HTTP crawling, которые уже естественно ложатся в Go, а качество универсального article extraction: Python Trafilatura активно поддерживается, а релиз 2.3.1 вышел 6 октября 2026 года; Scrapy и Playwright также активно развиваются. citeturn8search0turn8search16turn8search1turn8search2 Если тест покажет заметное преимущество Python-extractor на реальном корпусе, лучше передавать ему **уже загруженный HTML**, сохраняя единственную точку сетевой загрузки, rate limiting, права доступа и дедупликацию на стороне общего backend.

**Браузер в MVP не нужен.** Он оправдан только для конкретной разрешенной страницы, где важное содержание действительно отсутствует в исходном HTML/API и появляется после JavaScript. Playwright и chromedp позволяют такой режим реализовать, но браузер увеличивает стоимость, поверхность отказов и требования к изоляции. citeturn8search18turn7search23

**Внешний extraction-as-a-service также не нужен по умолчанию.** Zyte API документирует HTTP/browser fetch и automatic extraction; Diffbot имеет специализированный Article API; Firecrawl совмещает scrape/crawl/search и тарифицирует использование по кредитам. Это реальные способы быстро заменить собственную browser/extraction-инфраструктуру, но их качество на выбранных российских источниках еще не проверено, появляется внешняя зависимость и передача URL/контента третьей стороне, а разрешение правообладателя такой сервис сам по себе не создает. citeturn21search0turn21search4turn21search12turn21search5turn21search2

### Критический продуктовый риск — не парсинг HTML, а права на коммерческие СМИ

Самое существенное наблюдение исследования: **технически доступная страница нельзя автоматически считать допустимым источником полного текста для продуктовой базы**.

Например, РБК прямо запрещает автоматизированное извлечение информации сайта любыми сервисами без официального разрешения и отдельно требует разрешение правообладателя для использования материалов; ссылка на RSS присутствует на том же сайте, но сама по себе она не отменяет эти правила. citeturn25view0 Interfax также предусматривает договорный режим использования и прямо оговаривает ограничения в отношении RSS; на странице указано, что материалы сайта предназначены для персонального использования, а дальнейшее воспроизведение/распространение требует письменного разрешения. citeturn26view0

Поэтому для MVP я предлагаю разделить конфигурацию источника минимум на две независимые оси:

**`technical_access`** — RSS/API/HTML/browser, и **`content_policy`** — разрешено ли автоматически получать и сохранять metadata, teaser, full text, quotations/evidence.

Это решает проблему ошибочного предположения «раз URL открывается, значит можно складывать его полный текст в продукт». Более простая альтернатива — один флаг `enabled`; она достаточна только для полностью собственных или явно открытых источников и быстро становится опасной при появлении коммерческих СМИ.

### Стартовый набор

Для первой версии я бы подключил:

**Банк России → Официальный интернет-портал правовой информации → regulation.gov.ru → Росстат → несколько заранее выбранных пресс-центров компаний/ведомств → один коммерческий или отраслевой источник только после подтверждения условий → Yandex Search API для адресного поиска.**

Банк России официально публикует перечень RSS-каналов, включая новости, нормативные акты и проекты актов. citeturn24search7turn24search0turn24search4 Портал официального опубликования правовых актов предоставляет RSS, открытые данные и документированный API. citeturn24search9turn24search12turn24search2 Федеральный портал проектов НПА прямо предоставляет Open Data и RSS-подписку. citeturn26view1 У Росстата публично доступны новостные/анонсные разделы, RSS и открытые данные. citeturn24search1turn24search20turn24search5

Такой набор намеренно **не обеспечивает полный поток общего бизнес-news**. Он будет хуже ловить аварии, локальные ограничения, логистические сбои, неофициальные сигналы о конкурентах, отраслевые слухи, зарубежные события и многие commodity/supply-chain события до появления официальной публикации. Это приемлемая цена за MVP: сначала доказать устойчивость общего конвейера и адресного поиска, а затем добавлять источники по измеренным пробелам покрытия.

## Состав задач парсера и точки применения моделей

Главное проектное разделение: **«получить и понять, что утверждает материал» — задача этого слоя; «что это значит для конкретной компании» — уже нет.**

| Этап | Вход | Минимальный выход | Предпочтительный способ | Когда можно пропустить | Нужна ли модель |
|---|---|---|---|---|---|
| **Обнаружение ссылок** | конфигурация источника, cursor/time range либо search goal | URL, source ID, external ID если есть, время обнаружения, причина/канал обнаружения | RSS/Atom/API → sitemap/listing → известный HTML → search API | если URL пришел извне уже известным | Нет |
| **Получение метаданных** | feed item/API item/HTML | title, description, source ID, canonical URL, publication/modified dates, author/category, language | feed/API fields, `<link rel=canonical>`, HTML meta/JSON-LD, source-specific rules | практически никогда: metadata нужны до дорогой обработки | Нет |
| **Загрузка полного материала** | normalized URL + policy + fetch request | HTTP metadata, body или формальный статус «не загружен/запрещен/ошибка» | обычный HTTP; conditional request при повторе | teaser достаточен; full text запрещен; downstream не запросил | Нет |
| **Основной текст** | HTML | clean text + extraction method + completeness | source selector → universal extractor fallback | API/feed уже дал полный разрешенный текст | Обычно нет |
| **Факты/признаки события** | clean text + metadata | сущности, величины, event/effective dates, тип утверждения, evidence spans | правила/regex/NER/структурные поля; semantic fallback | downstream работает только с сырым текстом | Иногда |
| **Дубли/версии** | normalized metadata + hashes/text | exact duplicate, reprint/cluster, version relation | external ID, URL normalization, hashes; similarity для перепечаток | нельзя пропускать exact dedupe; semantic clustering можно отложить | Обычно нет |
| **Адресный поиск** | конкретная нехватка сведений | candidate URLs + query provenance | Search API → общий discovery/fetch pipeline | фон уже дал достаточные первичные подтверждения | Для генерации/переформулировки запроса — опционально |

HTML-страницы новостей часто предоставляют `datePublished` и `dateModified` через структурированные данные Schema.org, поэтому эти поля следует извлекать до попыток угадывать даты из текста. citeturn22search3turn22search7

### Обнаружение — это не загрузка

Discovery должен быть дешевым и максимально широким. RSS/API дают лучшую основу, потому что публикация уже приходит как структурированный элемент и обычно содержит URL, заголовок, дату и стабильный идентификатор или guid. Для общих feeds можно использовать `gofeed`: библиотека поддерживает RSS, Atom и JSON Feed и распространяется по MIT. citeturn7search0turn7search4

Sitemap и HTML listing — fallback, а не первая линия. `robots.txt` нужно соблюдать как стандартный механизм управления поведением crawler, но RFC 9309 отдельно указывает, что Robots Exclusion Protocol **не является механизмом авторизации**; соответственно, его нельзя использовать ни как лицензию на контент, ни как замену анализу условий сайта. citeturn22search0

### Метаданные следует получать всегда

До полного download нужны хотя бы:

`source_id`, `external_id`, `original_url`, `canonical_url`, `title`, `description`, `published_at`, `modified_at`, `discovered_at`, `discovery_method`, `discovery_reason`.

Это дает возможность сделать exact dedupe, отсечь уже известный материал и передать компактное представление внешнему relevance-компоненту **до** загрузки тела.

Не стоит заставлять LLM восстанавливать опубликованную дату, если она есть в RSS/API, JSON-LD или явно размечена на странице. Модель полезна только после исчерпания структурированных вариантов и должна в таком случае возвращать не только значение, но и неопределенность.

### Полный материал — отдельное решение

Обычного HTTP достаточно, когда нужный контент содержится в server-rendered HTML. Повторные запросы следует делать условными, если origin предоставляет ETag/Last-Modified: HTTP caching предусматривает `If-None-Match`, `If-Modified-Since` и ответ `304 Not Modified`, что позволяет не передавать повторно неизмененное тело. citeturn22search2turn22search5

Полный текст следует получать, когда одновременно выполнены условия:

- источник разрешает такой вид использования;
- материал еще не был загружен в общую базу или есть признак изменения;
- полный текст нужен либо по source policy, либо из-за неоднозначного teaser, либо по запросу следующего слоя.

Это **не должно выполняться на уровне “company × article”**. Один URL загружается и извлекается один раз; компании затем ссылаются на общий `material_id`/`version_id`.

### Source-specific parser и universal extractor должны сосуществовать

Для важных источников правила конкретного сайта полезны не только для текста: они позволяют надежнее выделять дату изменения, лид, подписи, информационный блок, номер нормативного документа и признаки исправления.

Универсальный extractor нужен как fallback и для long tail сайтов. В Go актуальным кандидатом является `markusmobius/go-trafilatura`, лицензия Apache-2.0. citeturn8search12 В Python — Trafilatura, также Apache-2.0 в актуальной ветке и активно обновляемая. citeturn8search0turn8search16

**Собственный вывод:** universal extractor следует считать инструментом «получить вероятное тело статьи», а не источником истины о структуре события. Он принципиально хуже source adapter знает, является ли блок исправлением, live-update, таблицей статистики, несколькими новостями на одной странице или нормативным приложением. Поэтому контракт должен сохранять `extraction_method` и `text_completeness`, а не выдавать любой извлеченный текст за полный.

### Факты события не равны бизнес-влиянию

Здесь допустимо извлекать:

- кто сделал/объявил действие;
- что произошло или планируется;
- денежные и количественные значения;
- географию;
- `event_at`, `effective_from`, deadline;
- является ли фраза **состоявшимся фактом, заявленным планом, прогнозом или мнением**;
- точный supporting span из документа.

Но компонент **не должен** выводить «это повысит кредитный риск компании», «опасно для клиента банка» или «возможность для CFO». Это следующая стадия.

LLM имеет смысл подключать лишь к трудным семантическим случаям: например, различить «компания рассматривает запуск», «запустила» и «аналитик ожидает запуск», связать несколько временных указаний с нужным действием или нормализовать свободный текст в ограниченную event schema. Извлеченное значение без evidence span желательно считать менее надежным.

### Дубли, перепечатки и обновления — разные сущности

Нужны как минимум четыре отношения:

**exact duplicate** — тот же source/external ID, canonical URL или тот же нормализованный content hash;

**reprint / near duplicate** — существенно тот же материал на другом URL/источнике;

**same topic** — разные публикации об одной теме, которые нельзя удалять как дубли;

**new version / correction** — тот же материал изменился после первой загрузки.

Условный HTTP помогает увидеть отсутствие изменений, но не заменяет content hash и собственное versioning. HTTP validators предназначены для проверки актуальности представления ресурса. citeturn22search5

Для MVP exact duplicates и версии можно делать полностью детерминированно. MinHash/SimHash или embedding-based similarity для перепечаток стоит добавлять после появления реального корпуса; отдельная LLM здесь обычно неоправданна.

### Что добавить раньше очередного СМИ

После обязательных регуляторных источников я бы серьезно рассмотрел **e-disclosure и Федресурс**, если хакатон/банк может получить разрешенный доступ. Причина проста: это не еще одна редакционная интерпретация события, а структурированные корпоративные и юридические сообщения. API Федресурса, например, возвращает содержание сообщений в XML и поддерживает связанные сообщения; это прямо помогает с версионностью/изменениями. citeturn14view0turn15view0

Для конкретного демо-пула компаний также стоит добавить их собственные press centers. Но поскольку реальные названия обезличенных компаний и все их зависимости по условию неизвестны, **не следует проектировать список press-center adapters как статическую глобальную энциклопедию**: новый источник регистрируется при появлении компании или нового monitoring topic.

## Реализация: реалистичные варианты и инструменты

### Сравнение архитектурных вариантов

| Вариант | Что входит | Сильная сторона | Главный недостаток | Рекомендация |
|---|---|---|---|---|
| **Go-first adapters + universal fallback** | существующий worker/PostgreSQL; feeds/API; `net/http`; `goquery`; source-specific rules; Go universal extractor; search API adapter | Минимум новых сервисов, один слой rate-limit/cache/security/dedupe; хорошо соответствует уже существующему backend | Качество universal extraction нужно доказать на реальных источниках; меньше готовой scraping-экосистемы | **MVP — выбрать этот** |
| **Go orchestration + Python extraction/browser sidecar** | Go остается владельцем jobs/source state; HTML отправляется в Python Trafilatura; при необходимости Scrapy/Playwright | Более зрелая Python extraction/crawling ecosystem, проще быстро экспериментировать | Второй runtime, deploy/observability/interface, риск дублирования загрузок | Добавить только при измеренном выигрыше |
| **Внешний extraction/browser API** | Zyte/Diffbot/Firecrawl либо аналогичный provider получает URL и возвращает rendered/extracted content | Быстрый запуск сложного rendering/extraction, меньше собственного browser ops | recurring cost, vendor dependency, security/data review, неизвестная эффективность на целевых RU sources; не решает source rights | Резервный вариант, не основа MVP |

### Go-стек

`mmcdole/gofeed` поддерживает RSS, Atom и JSON Feed и имеет MIT-лицензию; это естественное расширение существующего RSS 2.0 слоя, когда появится потребность в нескольких форматах feed. citeturn7search0turn7search4

`PuerkitoBio/goquery` — активно поддерживаемый jQuery-подобный HTML query layer с BSD-3-Clause; актуальные релизы продолжают выходить в 2026 году. Свежие версии повысили минимальные требования Go, поэтому перед закреплением version pin следует сравнить их с текущим `go.mod` backend. citeturn7search1turn7search5turn7search17

`markusmobius/go-trafilatura` — Apache-2.0 универсальный extractor текста/metadata и более предпочтительный кандидат для нового MVP, чем архивированный `go-shiori/go-readability`. citeturn8search12turn7search2

`chromedp` — активно поддерживаемый MIT Go-клиент Chrome DevTools Protocol; релиз 0.21.0 вышел в октябре 2026 года. Но browser dependency следует заводить только после появления URL, который не удается корректно обработать обычным HTTP. citeturn7search3turn7search23

### Python-стек

Trafilatura 2.3.1 актуальна на октябрь 2026 года; актуальная ветка распространяется под Apache-2.0. citeturn8search0turn8search16

Scrapy 2.19.0 на сентябрь 2026 года — поддерживаемый BSD-3-Clause crawling framework с Python 3.11+; однако для этой задачи он будет дублировать scheduling/retry/source-state, уже существующие в Go, поэтому полный перенос crawling в Scrapy выглядит избыточным. citeturn8search1

Playwright Python поддерживает Chromium, Firefox и WebKit и активно выпускается; Apache-2.0. Это предпочтительный кандидат, если позже будет выделен browser-worker. citeturn8search2turn8search18

**Предложение:** при эксперименте с Python не переносить туда весь pipeline. Интерфейс вида `HTML bytes → extracted article` позволяет сравнить Go и Python extractor на одних и тех же байтах, не вмешивая сеть в эксперимент.

### Когда действительно нужен браузер

Браузер оправдан, если одновременно:

1. URL нужен продукту;
2. доступ и автоматизация разрешены;
3. server HTML/API не содержит важного материала;
4. JS rendering реально восстанавливает его;
5. невозможно заменить источник первичным API/RSS/другой страницей.

Это гораздо более строгий критерий, чем «сайт современный и использует JavaScript».

Та же логика видна у внешних провайдеров: Zyte отдельно различает HTTP и browser requests и документирует получение browser-rendered HTML; следовательно, browser является отдельным, более тяжелым способом получения representation, а не обязательной стадией каждого scrape. citeturn21search12turn21search16

### Поисковый API

Для русскоязычного адресного discovery первым кандидатом выглядит **Yandex Search API**: официальная документация предоставляет REST/gRPC interfaces, текстовый web search, сортировку по relevance/time и временные ограничения; требуется billing account/API key. citeturn10search1turn10search3turn10search5 Yandex публикует отдельные quotas и mode-dependent pricing, поэтому стоимость следует измерять через фактическое число targeted jobs, а не закладывать выдуманный бюджет. citeturn10search8turn10search0

**Brave Search API** — полезный второй кандидат для сравнительного покрытия, особенно международных источников; провайдер заявляет независимый search index и предоставляет web/news APIs, при регистрации для платных сценариев требуется платежная информация. citeturn9search5turn9search29turn9search33

Не стоит проектировать новую интеграцию вокруг старых Bing Search APIs или Site Restricted Google Custom Search: Microsoft прекратила Bing Search APIs 11 августа 2025 года, а соответствующий Google Site Restricted JSON API перестал обслуживать traffic 8 января 2025 года. citeturn9search3turn9search2

Важная граница: search response хранится как **discovery provenance** — запрос, позиция, найденный URL, время. Тело найденной страницы проходит обычные source policy → safe fetch → extraction. Search provider не должен определять факт как достоверный только потому, что поставил ссылку высоко.

### Внешние extraction-сервисы как контрольная альтернатива

Zyte API поддерживает обычные HTTP requests, browser rendering и automatic extraction; цены зависят от режима и extraction type. citeturn21search0turn21search28 Diffbot Article API заявляет извлечение article text, HTML, authors, dates и tags из article pages. citeturn21search5 Firecrawl предоставляет scrape/crawl/search и публикует credit-based pricing, актуализированный в сентябре 2026 года. citeturn21search2

Это **маркетинговые/поставщицкие возможности, а не доказательство качества на Банке России, Коммерсанте или российских отраслевых СМИ**. Поэтому правильный способ оценки — включить одного провайдера как третью колонку одинакового A/B корпуса, а не принимать заявленные возможности за benchmark result.

## Совместная работа фонового сбора и адресного поиска

### Базовый поток обработки

Предлагаемый поток выглядит так:

```text
RSS / API / listing / sitemap / search result
                    │
                    ▼
          normalize discovery item
                    │
                    ▼
     canonicalization + exact dedupe
                    │
          already known unchanged?
             ┌──────┴──────┐
            yes            no
             │              │
        update seen_at      ▼
                     metadata enrichment
                            │
                            ▼
                   source/content policy
                     ┌──────┼─────────┐
                     │      │         │
                forbidden metadata  full fetch
                     │     enough      │
                     │      │          ▼
                     │      │     safe HTTP fetch
                     │      │          │
                     │      │      extraction
                     │      │          │
                     └──────┴──────────┤
                                      ▼
                            version / duplicate check
                                      │
                                      ▼
                            optional event facts
                                      │
                  ┌───────────────────┴──────────────────┐
                  │                                      │
            information enough                  material still ambiguous
                  │                                      │
                  ▼                                      ▼
              ready/shared                    targeted search job
                                                         │
                                                         └──► same pipeline
```

Ключевой эффект такого устройства: **targeted search не создает параллельный интернет-парсер**. Он всего лишь еще один producer для `discovered_url`.

### Что собирать всегда

До любых company-specific операций стоит собирать общую, повторно используемую запись:

- источник и source class;
- source external ID/guid;
- original и canonical URL;
- title + source description/lead;
- publication/modified times, если источник их сообщил;
- `first_seen_at` и `last_seen_at`;
- discovery method: feed/api/html/search/manual;
- конкретную discovery reason: feed ID, query/job, source page;
- язык/category/author, когда доступны;
- policy state: можно ли fetching/full-text persistence;
- HTTP validators после первой загрузки.

Structured article markup предоставляет стандартные свойства `datePublished` и `dateModified`, но источник этих значений все равно следует сохранять, поскольку разные representations могут расходиться. citeturn22search3turn22search7

### По каким основаниям загружать полный текст

Здесь полезно избежать жесткой крайности «fetch everything» / «fetch только после relevance score».

**Предложение — трехрежимная source policy:**

`metadata_only` — коммерческий/ограниченный источник или source discovery без разрешения на тело;

`fetch_on_demand` — тело разрешено, но поток большой; сначала metadata, полный текст запрашивается при потенциальной полезности;

`prefetch_body` — высокоценный официальный или небольшой поток с разрешенным доступом, где full text часто нужен нескольким компаниям.

Сам parser не должен рассчитывать бизнес-релевантность. Он принимает от соседнего компонента сигнал вроде `requested_level=content`, а собственными основаниями загрузки остаются source policy, version check и техническая необходимость.

### Что делать с важным, но неясным анонсом

Правильная последовательность:

**Сначала** попытаться загрузить полный материал с того же разрешенного URL.

**Если тела нет или его использование запрещено** — найти первичный источник, на который ссылается анонс: ведомство, компания, нормативный портал, disclosure.

**Если первичного источника не найдено** — targeted web search с конкретным информационным gap.

**Если остается только teaser** — вернуть материал как `partial` с явно заполненным `incomplete_fields`, а не «достраивать» факты моделью.

### Когда запускать дополнительный поиск

Адресный поиск оправдан не на каждую новость, а при одном из следующих состояний:

- появилась новая компания/отрасль/география, для которой еще нет достаточного source coverage;
- важный feed-item содержит только неясный teaser;
- отсутствует критический event/effective date;
- текст ссылается на решение/приказ/заявление, но первичный документ не найден;
- несколько источников противоречат друг другу;
- background stream дает событие, но не дает достаточных доказательств;
- изменились темы мониторинга компании и нужно найти существующие source endpoints/недавние материалы.

Это не решение модели бизнес-влияния; trigger может прийти от relevance/orchestration layer как формальный «нужны дополнительные источники по таким полям».

### Как формулировать search goal

Вместо широкого:

> «Что нового важного для компании X?»

лучше передавать задачу вида:

> «Найти первичный источник, подтверждающий изменение правила X; определить дату опубликования и дату вступления в силу; приоритет — сайт регулятора/ведомства; вернуть URL документов и supporting snippets».

или:

> «Найти независимое подтверждение сообщения о приостановке производства в регионе Y; нужны субъект события, дата начала, заявленная длительность и первоисточник».

Так поисковый API остается механизмом candidate discovery, а наше приложение контролирует evidence gathering.

### Как ограничивать поиск без выдуманных порогов

У `SearchJob` должны быть configurable budgets:

`max_queries`, `max_results`, `max_fetch_documents`, `max_bytes`, `deadline/wall_time`, `per_domain_limit`.

Конкретные числа сейчас назначать не следует. Их надо получить из pilot distribution: сколько дополнительного качества приносит каждый следующий query/document и сколько он стоит.

Stop conditions:

- требуемые поля подтверждены источником нужного класса;
- новые результаты повторяют уже известные документы;
- разрешенных URL больше нет;
- budget/deadline исчерпан;
- дальнейшие результаты дают только запрещенные/paywalled sources.

В последнем случае результат поиска — не пустая строка, а явное:

```text
status = incomplete
missing = [effective_date, primary_confirmation]
attempted_sources = [...]
stop_reason = search_budget_exhausted | access_restricted | no_more_candidates
```

## Данные, актуальность, версии, надежность и безопасность

### Минимальный входной контракт

Вместо множества несвязанных функций полезен единый job envelope:

| Поле | Назначение |
|---|---|
| `job_id` | идемпотентность и трассировка |
| `mode` | `background_discovery`, `fetch`, `targeted_search`, `refresh` |
| `source_id` | обязательный для известного источника |
| `url` / `discovery_item` | URL или feed/API metadata |
| `requested_level` | `metadata`, `content`, `facts` |
| `trigger` | `scheduled`, `new_company`, `ambiguous_teaser`, `missing_fact`, `manual` и т. п. |
| `search_goal` | только для targeted search; конкретная цель, не общий prompt |
| `monitoring_topics` | допустимые темы: отрасль, рынки, сырье, логистика, география, финансирование, регулирование |
| `budget` | ограничения requests/results/docs/bytes/time |
| `policy_ref` | версия source/security/content policy |

Полное внутреннее описание договоров обезличенной компании parser знать не обязан. Если downstream считает зависимость чувствительной, достаточно передавать нормализованный monitoring topic, а не исходное коммерческое условие.

### Минимальный выходной контракт материала

Существующую запись `{source, external_id, URL, title, description, full_text, publication_date}` я бы **расширял, а не заменял**.

Минимально полезная модель:

```text
Material
  material_id
  source_id
  external_id?

  original_url
  canonical_url

  title?
  description?
  author?
  language?
  categories[]

  published_at?
  modified_at?
  discovered_at
  fetched_at?

  published_at_source
  date_confidence
  date_precision

  content_text?
  content_status       # full | partial | metadata_only | unavailable
  extraction_method
  content_hash?

  http_status?
  content_type?
  etag?
  last_modified?

  discovery_method
  discovery_reason
  discovery_job_id

  version_id?
  supersedes_version_id?
  duplicate_group_id?
  reprint_of?

  parse_status
  error_code?
  incomplete_fields[]
```

Для событий — отдельная дочерняя структура, а не поля статьи:

```text
EventFact
  fact_type
  subject?
  value / object?
  event_at?
  effective_from?
  deadline?
  statement_kind      # fact | announced_plan | forecast | opinion
  evidence_text
  evidence_offsets?
  source_version_id
  extraction_method
  confidence?
```

Так сохраняется важное различие: **`published_at` относится к документу, `event_at` — к событию, `effective_from` — к началу действия решения**.

### Как обращаться с датами

Нужно хранить минимум четыре различных времени:

**`published_at`** — что заявил publisher;

**`modified_at`** — что publisher обозначил как изменение;

**`discovered_at`** — когда наша система впервые увидела материал;

**`event_at/effective_from`** — когда произошло или начнет действовать описываемое событие.

В нормативных источниках это особенно важно: Банк России, например, отдельно отображает номер/дату акта, регистрацию и дату официального опубликования. citeturn24search19turn24search25

Если дата отсутствует, **не заменять ее `discovered_at` без маркировки**. Лучше:

```text
published_at = null
date_confidence = unknown
discovered_at = exact timestamp
```

Если известен только день, не придумывать время суток: сохранять `date_precision=day`.

### URL normalization

Хранить одновременно `original_url` и `canonical_url`.

Нормализация может убирать fragment, стандартный порт, известные tracking parameters и приводить host/scheme к выбранной форме, но нельзя произвольно удалять query parameters: у нормативных/search/download URL они могут идентифицировать документ.

`rel=canonical`, если он есть, — подсказка publisher, а не повод потерять исходный адрес.

### Версии исправленной статьи

При каждой разрешенной повторной проверке:

1. получить HTTP validators/conditional response;
2. при новом body вычислить hash нормализованного содержания;
3. если hash изменился, **создать новую `version_id`**, а не перезаписать доказательство, на котором мог быть построен сохраненный отчет;
4. связать версии `supersedes`;
5. если publisher явно обозначает correction/update — сохранить этот source signal отдельно.

ETag и Last-Modified хорошо уменьшают traffic, но HTTP позволяет publisher менять ETag/representation независимо от вашей семантики; поэтому локальное versioning все равно необходимо. RFC 9111 описывает validation через ETag/Last-Modified и 304. citeturn22search2turn22search5

### Скользящее окно — не retention policy

Следует различать три понятия.

**Окно показа** определяет, какие новости сейчас попадают в общий/отраслевой feed пользователя.

**Рабочее хранение** обеспечивает дедупликацию, повторное обнаружение, catch-up, version comparison и targeted search.

**Хранение использованных оснований** обеспечивает воспроизводимость уже сохраненного пользовательского отчета.

Поэтому удаление публикации из текущего news window **не должно удалять version/evidence, уже использованные сохраненным отчетом**.

Событие с будущей датой вступления в силу также не становится «неактуальным» только потому, что article published давно. Parser должен сохранить `effective_from/deadline`; решение о повторном показе принимает downstream stream/relevance layer.

Конкретные периоды retention без требований банка, объема потока, лицензий и downstream expectations назначать сейчас было бы произвольно.

### Состояния обработки

Практичный минимальный state machine:

```text
discovered
  → metadata_ready
  → fetch_pending | content_skipped
  → fetched
  → extracted | partial
  → facts_ready
  → ready
```

Поперечные terminal/retry states:

```text
retryable_error
permanent_fetch_error
blocked_by_policy
paywalled_or_auth_required
unsupported_content_type
not_found
superseded
```

`403` не следует автоматически превращать в «источник навсегда заблокирован», а timeout — в `permanent_error`; это особенно видно по текущему исследованию: официальные CBR/Rosstat/Pravo страницы индексируются и документируют нужные функции, хотя отдельные запросы из нашей исследовательской среды получили 403/502/timeout. citeturn24search7turn24search1turn26view2turn26view3

### Расписание, восстановление и polite fetching

У источника нужен cursor плюс **перекрывающийся повторный просмотр недавнего диапазона**, потому что publisher может допоздна добавить элемент или исправить существующий. Точная ширина overlap должна быть измерена на источнике, а не задана одинаково глобально.

После простоя worker должен сначала выполнить catch-up через API/archive/list pages за пропущенный interval, а не просто продолжить «сейчас».

Retry должны быть ограниченными и применяться к transient network/5xx/429 cases; серверный `Retry-After`, когда он предоставлен, предназначен для указания клиенту, сколько ждать до повторного запроса. citeturn22search1

На повторных downloads применять conditional requests. citeturn22search5

Rate limit должен существовать **per source/domain**, чтобы 100 company contexts не превратили один и тот же источник в 100 независимых crawlers.

### Контроль поломки парсеров

Для каждого source adapter полезно наблюдать:

- долю successful discovery/fetch/extraction;
- внезапную потерю обязательного selector/field;
- медиану/распределение размера извлеченного текста;
- рост `metadata_only`/`partial`;
- появление одинакового boilerplate на множестве материалов;
- число новых URLs относительно обычного диапазона;
- время последнего успешно увиденного item.

Здесь нужны не заранее выдуманные alarms, а baseline по первым дням/неделям тестового запуска.

Новая верстка коммерческого СМИ — реальный operational risk: например, текущая лента «Коммерсанта» — полноценная HTML-структура с категориями/timestamps, поэтому изменение layout потенциально затронет source-specific selectors. citeturn25view2 Feed/API adapters обычно меньше зависят от визуальной разметки.

### Минимум безопасной загрузки URL

Search API и внешние страницы являются недоверенными источниками URL, поэтому fetcher — SSRF boundary. OWASP прямо описывает SSRF как возможность заставить сервер обращаться к внутренним ресурсам и рекомендует network-level isolation/deny-by-default controls. citeturn21search3turn21search11

Для такого сервиса минимальны:

- разрешать только `http`/`https`;
- запрещать loopback, private, link-local и metadata-address ranges;
- проверять IP после DNS resolution и **заново после redirect**;
- ограничивать redirects;
- задавать connect/read/overall timeout;
- ограничивать response bytes и decompressed size;
- проверять Content-Type;
- не выполнять `file:`, `ftp:`, `gopher:` и другие схемы;
- не передавать cookies/credentials между доменами;
- browser запускать в изолированной среде с ограниченным egress;
- не исполнять JS вообще, кроме отдельного browser path.

`robots.txt` при этом соблюдается как crawler policy, но, согласно RFC 9309, не является механизмом access authorization. citeturn22search0

### Интернет-текст как недоверенные данные

HTML следует очищать от active content до дальнейшей обработки. Текст, найденный в интернете, передаваемый затем LLM, должен быть маркирован как **данные источника, а не инструкции системе**. Это особенно важно для targeted search: злоумышленник способен намеренно разместить текст, рассчитанный на prompt injection.

Parser должен передавать downstream по возможности:

`source + URL + version + evidence span`

вместе с фактом. Он не должен исполнять инструкции из текста, запускать найденные команды или автоматически переходить по произвольным embedded links.

## MVP, проверка вариантов и неизвестные

### Последовательность небольших шагов

| Шаг | Что сделать | Зачем | Более простая альтернатива и критерий достаточности |
|---|---|---|---|
| **Source registry и policy** | описать discovery method, allowed fetch mode, rate policy, rights state | централизует главное различие технического и разрешенного доступа | hardcoded switch достаточен лишь для нескольких полностью собственных sources |
| **Общий safe fetcher** | normalization, redirect/SSRF protection, conditional HTTP, bounded retries, fetch metadata | одна загрузка на публикацию вместо загрузок на компанию | существующий HTTP-client достаточен, если URLs только статически whitelisted; search API это условие отменяет |
| **Дедупликация и версии** | canonical/external IDs, content hash, first/last seen, version records | основа повторного использования и исправлений | URL unique constraint достаточен только пока ни один publisher не редактирует URLs и нет tracking variants |
| **Официальные adapters** | CBR, Pravo, regulation.gov, Rosstat | дают большой набор высокодостоверных regulatory/macro events без необходимости browser | начать даже с CBR + Pravo, если сроки очень жесткие |
| **HTML extraction** | source-specific selectors + Go universal fallback | покрывает body без отдельного runtime | source-specific only достаточен, если MVP имеет считанные известные сайты |
| **Targeted Search adapter** | Yandex Search API → candidate URLs → общий pipeline | закрывает пробелы и новые contexts | ручное добавление URL достаточное только для демонстрации с полностью известным сценарием |
| **Extractor benchmark** | тот же HTML прогнать Go extractor, Python Trafilatura, при желании внешний provider | принять решение о Python на данных | не выделять sidecar, если выигрыш на целевом corpus практически незначим |
| **Один rights-cleared broad/sector source** | подключить после подтверждения условий | добавить неофициальные события, отсутствующие в regulator feeds | оставить search-on-demand, если demo не требует широкого realtime news stream |
| **Browser path** | только по конкретным failed cases | динамический content | никогда не добавлять, если server HTTP/API дает требуемые поля |

### Как сравнивать реализации честно

Нужен **один фиксированный corpus**, а не отдельные «удобные» страницы для каждого инструмента.

Для каждого выбранного источника команда фиксирует интервал теста и reference list публикаций, построенный из официального feed/API/archive. В corpus специально включаются обычные статьи, короткие новости, материал с обновлением, одинаковое событие у нескольких publisher, длинный текст, listing-like page, страницы с attachment и известные JS-heavy pages.

Затем все варианты получают **одинаковый набор URL или одинаковые сохраненные HTML bytes**.

| Измерение | Как проверять | Что логировать |
|---|---|---|
| **Полнота discovery** | сопоставить найденные IDs/URLs с reference publication set данного источника/интервала | missed, duplicate, unexpected items |
| **Задержка** | `first_seen_at - publisher_timestamp`, отдельно учитывать материалы без достоверного publisher time | median/distribution, источник discovery |
| **Извлечение текста** | ручной gold на выборке: потерянные абзацы, попавший boilerplate, перепутанные несколько материалов | completeness grade, extra/missing content |
| **Даты** | сравнение `published`, `modified`, `event/effective` с ручной annotation | тип ошибки и источник даты |
| **Факты** | ручная разметка небольшого набора entity/value/date/statement-kind + supporting span | precision/recall или field-level correctness после определения схемы |
| **Дубли** | заранее размеченные exact duplicate/reprint/same-topic pairs | false merge / missed merge |
| **Updates** | сохранить v1, затем дать системе v2/correction | обнаружила ли новую версию, сохранила ли старую |
| **Нагрузка** | одинаковый corpus | HTTP requests, bytes, CPU, memory, browser seconds |
| **API стоимость** | фактические provider billable units | search requests, extraction requests, retries |
| **Сопровождение** | после контролируемого изменения fixture/selectors | engineer time и число ручных source rules |

Никаких достигнутых значений сейчас нет, поэтому заявлять recall/precision/cost было бы выдумкой.

### Как выбрать пороги после pilot

Порог качества текста стоит определять не абстрактным «95%», а последствиями ошибки:

- насколько отсутствие одного абзаца меняет extracted fact;
- может ли boilerplate создать ложное событие;
- допускает ли downstream report `partial` material;
- сколько важных материалов теряется при metadata-only prefilter.

То же относится к search budget: построить кривую **«дополнительный найденный подтвержденный факт / дополнительный query/document/cost»** и выбрать point of diminishing returns под SLA продукта.

Для Yandex Search API такие измерения особенно важны, потому что provider отдельно тарифицирует режимы и устанавливает quotas; стоимость должна выводиться из реального job distribution. citeturn10search0turn10search8

Для external extraction аналогично: Zyte и Firecrawl публикуют per-use/credit pricing, но из прайса нельзя вывести итоговую стоимость без частоты browser fallback и количества документов. citeturn21search0turn21search2

### Практический A/B, который даст решение о Python

На сохраненном HTML corpus сравнить:

**A — source-specific Go selector**

**B — Go universal extractor**

**C — Python Trafilatura**

и только для страниц, где все три провалились:

**D — browser or external provider**.

Так можно ответить на главный инженерный вопрос без архитектурных предположений: дает ли Python enough incremental quality, чтобы оправдать второй service/runtime.

Scrapy при этом вообще не обязан входить в сравнение: поскольку scheduling и source adapters уже существуют на Go, оценивать его имеет смысл только если проект позже перерастет в большой generic crawler. Scrapy 2.19.0 остается активно поддерживаемым framework, но это не делает его автоматически подходящим для имеющейся архитектуры. citeturn8search1

### Существенные неизвестные, способные изменить рекомендацию

**Права на commercial news — неизвестная №1.** РБК без официального разрешения прямо запрещает automated extraction, Interfax предлагает договорный путь, а для использования полного текста «Коммерсанта» в таком продукте в ходе исследования не удалось найти достаточно однозначные актуальные условия. citeturn25view0turn26view0 Если Альфа-Банк/организаторы уже имеют news licenses, состав MVP может резко измениться: лицензированный feed/API почти всегда предпочтительнее scraping публичного сайта.

**Версия Go backend.** Свежие релизы отдельных библиотек подняли minimum Go version; без `go.mod` нельзя гарантировать, что текущие latest releases встанут без обновления toolchain. citeturn7search17turn7search23 Это не меняет Go-first подход, но может изменить конкретные pins.

**Реальные отрасли demo-компаний.** Без них нельзя обоснованно выбрать отраслевые СМИ и press centers. Нефтехимия, retail, telecom и logistics имеют совершенно разный long tail источников.

**Доступ к e-disclosure/Fedresurs products.** При наличии разрешенного API-доступа они заметно повышают ценность structured corporate/legal layer; спецификация Федресурса предполагает авторизованный production access. citeturn14view0turn15view0

**Доля JS-only страниц.** Если тест покажет, что важные разрешенные sources действительно требуют JS rendering, browser-worker станет оправданным. Пока такого доказательства для стартового official set нет.

**Доля полезного контента в PDF/attachments.** Если большая часть regulatory payload живет только во вложениях, internet parser должен хорошо передавать attachment metadata/URLs дальше, но PDF parser по условию остается у другого участника.

**География.** Российский MVP естественно делает Yandex Search API основным targeted-search кандидатом. При существенной международной supply-chain/geopolitical coverage имеет смысл параллельно измерить Brave Search API или другого direct search provider. citeturn10search3turn9search5

**Data/security rules банка для внешних API.** Они могут исключить отправку URLs или fetched content в external extraction providers независимо от технической привлекательности.

**Retention и licensing conditions.** Они определят, можно ли хранить raw HTML/full text и как долго. До выяснения этого архитектура должна уметь работать в `metadata_only`, `transient_body` и `persistent_body` modes, а не предполагать бессрочную копию всех материалов.

### Итоговый выбор для передачи разработчику

Оптимальная исходная конструкция выглядит как **расширение существующего Go backend, а не новый crawler-service**:

```text
existing scheduler
      │
      ├── Source adapters
      │      ├── RSS / Atom
      │      ├── official APIs
      │      ├── source listing HTML
      │      └── Search API discovery
      │
      ▼
Source policy + URL normalization
      │
      ▼
Shared safe HTTP fetcher
      │
      ├── rate limit / retries
      ├── ETag / Last-Modified
      ├── SSRF controls
      └── global URL/content cache
      │
      ▼
Extraction
      ├── source-specific rules
      └── universal Go fallback
      │
      ▼
Metadata / text / versions / evidence
      │
      ├── relevance & reporting boundary
      └── optional semantic fact extractor
```

**Python добавить только при доказанном выигрыше universal extraction; browser — только для конкретного разрешенного JS-only source; внешний scraping provider — только если после benchmark собственное извлечение/browser обслуживание оказывается экономически или операционно хуже.**

Именно этот вариант минимизирует количество новых moving parts, использует уже существующие worker/adapters/PostgreSQL, сохраняет единую точку безопасного доступа к интернету и не связывает продукт заранее ни с браузерной автоматизацией, ни с Python, ни с внешним scraping vendor. При этом он оставляет ясные upgrade paths для всех трех вариантов.

Самое важное архитектурное решение для MVP — **не выбор extractor library, а разделение discovery, fetching, extraction, semantic facts и business relevance, плюс независимая source-policy для технического доступа и права на использование материала**. Это позволяет постепенно расширять coverage, не скачивая одну и ту же публикацию для каждой компании, и не превращать адресный поиск в отдельный непрозрачный исследовательский сервис.
