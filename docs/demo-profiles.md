# Инструкция по запуску и демонстрации Signal

Этот документ описывает работу со стендом, подготовку пользователей и локальный
запуск. [Обзор проекта, архитектура и таблица аккаунтов](../README.md).

## 1. Как открыть стенд

- Приложение: [https://alpha.devgit.net](https://alpha.devgit.net).
- Вход: [https://alpha.devgit.net/login](https://alpha.devgit.net/login).
- Регистрация: [https://alpha.devgit.net/register](https://alpha.devgit.net/register).
- Сравнение PDF-графиков: [https://alpha.devgit.net/report-charts.html](https://alpha.devgit.net/report-charts.html).

Адрес соответствует ingress в Helm. При подготовке этой редакции, 26 октября
2026, запросы к стенду из среды автора завершились тайм-аутом; доступность извне
и серверные аккаунты требуют проверки перед сдачей. Это не результат проверки
модельного качества или состояния базы.

**Аккаунты из таблицы README ещё не созданы на сервере.** Сначала выполните
[подготовку](#server-accounts); затем передайте проверяющим ссылку на вход и
таблицу. Реквизиты `finance@signal.demo` и `operations@signal.demo` относятся
только к автономному браузерному демо и на сервере не работают автоматически.

## 2. Сценарий для проверяющего

### Шаг 1. Войти и проверить профиль

1. Откройте `/login`, введите email и пароль из [таблицы](../README.md#demo-users).
2. Перейдите в личный кабинет `/profile`.
3. Проверьте название компании и выбранные роли. В документах должны быть четыре
   файла соответствующей компании из `fixtures/miro-personas/<persona>/documents/`.
4. Дождитесь статуса «Анализ завершён». `queued` означает ожидание, `failed` —
   ошибку обработки; факт загрузки оригинала не означает успешное извлечение.

Профили синтетические. Для проверки не требуется загружать реальные коммерческие
или персональные данные. Смена пользователя выполняется через выход и новый вход.

### Шаг 2. Посмотреть события и разбор

1. Откройте `/dashboard` и выберите назначенную роль.
2. Просмотрите ленту, переключите тип «Риск» / «Возможность» / «Событие».
3. Найдите новость через поиск, добавьте её в закладки и откройте подробности.
4. Проверьте исходную ссылку, дату, объяснение влияния и связь с компанией.
5. При необходимости выгрузите карточку в TXT.

«Обновить события» перечитывает готовую ленту, а не запускает скачивание новых RSS.
Общий корпус предзагружен, но персональные результаты появляются после регистрации
и обработки очереди. Отсутствие карточек не заменяется подготовленной демо-лентой.

### Шаг 3. Проверить бизнес-ситуацию и ИИ-компаньона

1. Откройте сформированную бизнес-ситуацию из дашборда.
2. Просмотрите основания и историю её версий.
3. В «Уточнить ситуацию» задайте вопрос:
   - «На какие данные нашей компании ты опираешься?»;
   - «Каких данных не хватает, чтобы принять решение?»;
   - «Какие условия могут изменить этот вывод?».
4. Задайте уточняющий вопрос по ответу и перезагрузите страницу.
5. Проверьте, что история осталась у той же ситуации и версии. После изменения
   ситуации для новой версии предлагается новый диалог; старый сохраняется.

Свободного общего чата без бизнес-ситуации в рабочем API нет. Наличие ответа и
корректного JSON не доказывает смысловую точность: проверяющий должен сопоставить
вывод с приведёнными фактами и источниками.

### Шаг 4. Сравнить роли

Выйдите и войдите вторым пользователем той же компании. Корпоративный контекст
общий, рабочие вопросы различаются:

| Компания | Первый пользователь | Второй пользователь | Что сравнить |
|---|---|---|---|
| Билайн | Дмитрий — стратегия | Ирина — продукт | Экономика пилота и стратегическая применимость / готовность продукта |
| X5 | Анна — финансы | Павел — коммерция | Ликвидность и долговая нагрузка / спрос и коммерческие условия |
| РЖД | Сергей — закупки | Ольга — операции | Цена и поставщики / сроки и непрерывность работ |
| Эталон | Марина — коммерция | Алексей — финансы | Продажи и спрос / финансовая чувствительность |

Это направления проверки, а не обещание заранее рассчитанного ответа на любую
новость. Подробные положительные и отрицательные сценарии:
[fixtures/miro-personas/scenarios.md](../fixtures/miro-personas/scenarios.md).

### Шаг 5. Посмотреть аналитические графики

1. На дашборде выберите «Добавить виджет → График из PDF».
2. Выберите отчёт, диаграмму и один ряд.
3. Откройте исходный фрагмент и сведения об источнике и точности.
4. На `/report-charts.html` сравните исходное изображение с отдельным SVG и
   измеренными опорными точками. JSON/SVG можно скачать.

Набор архивный: девять PDF, 97 диаграмм и 253 ряда. Точные напечатанные значения,
приблизительная оцифровка, прогнозы и недоступные значения обозначены отдельно.
Это не поток актуальных котировок и не подтверждение импорта полных PDF в RAG.

<a id="server-accounts"></a>
## 3. Подготовка серверных тестовых аккаунтов

Выполняется администратором стенда **перед сдачей**, на отдельной демонстрационной
базе. Все действия ниже создают только синтетические компании и пользователей.
Таблица с логинами и паролями находится в [README](../README.md#demo-users),
исходные запросы — в [fixtures](../fixtures/miro-personas/README.md).

Первых пользователей можно создать через `/register`, используя эти данные:

| Persona / папка | Название компании | Искусственный ИНН | Первый пользователь |
|---|---|---|---|
| `beeline` | Билайн | `0000001001` | Дмитрий |
| `x5` | X5 | `0000001002` | Анна |
| `rzd` | РЖД | `0000001003` | Сергей |
| `etalon` | Группа «Эталон» | `0000001004` | Марина |

После регистрации заполните профиль данными `profile.json` и загрузите четыре
файла `documents/*.txt`. Для воспроизводимой подготовки через HTTPS API ниже
приведён вариант с `curl` и Python 3; его запускают из корня репозитория.
Публичные API не требуют LLM-ключа клиента: он настроен на сервере.

### 3.1. Подготовить запросы для одной компании

```bash
export DEMO_URL=https://alpha.devgit.net
export DEMO_PERSONA=x5
signal_demo_dir=$(mktemp -d)

python3 - "$DEMO_PERSONA" "$signal_demo_dir" <<'PY'
import json, sys
from pathlib import Path
persona, target = sys.argv[1], Path(sys.argv[2])
items = json.loads(Path('fixtures/miro-personas/registration-requests.json').read_text())
account = next(item for item in items if item['persona'] == persona)
(target / 'onboarding.json').write_text(json.dumps({
    'company': account['company'], 'user': account['user']}, ensure_ascii=False))
(target / 'login.json').write_text(json.dumps({
    'email': account['user']['email'], 'password': account['user']['password']}))
PY
```

### 3.2. Создать компанию и первого пользователя

```bash
curl --fail-with-body --silent --show-error \
  --cookie-jar "$signal_demo_dir/cookies.txt" \
  -H "Origin: $DEMO_URL" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: demo-persona-$DEMO_PERSONA-v1" \
  --data-binary @"$signal_demo_dir/onboarding.json" \
  "$DEMO_URL/api/v1/onboarding"
```

Если аккаунт уже существует, вместо повторного создания войдите с его паролем:

```bash
curl --fail-with-body --silent --show-error \
  --cookie-jar "$signal_demo_dir/cookies.txt" \
  -H "Origin: $DEMO_URL" -H 'Content-Type: application/json' \
  --data-binary @"$signal_demo_dir/login.json" \
  "$DEMO_URL/api/v1/auth/login"
```

Сервер не присоединяет нового пользователя к существующей компании только по ИНН.
При конфликте данных проверьте исходную учётку; не меняйте ИНН случайным образом,
если нужно сохранить именно этот демо-набор.

### 3.3. Записать профиль и загрузить документы

```bash
curl --fail-with-body --silent --show-error \
  --cookie "$signal_demo_dir/cookies.txt" \
  "$DEMO_URL/api/v1/auth/me" --output "$signal_demo_dir/me.json"

signal_company_id=$(python3 -c \
  'import json,sys; print(json.load(open(sys.argv[1]))["companyId"])' \
  "$signal_demo_dir/me.json")

curl --fail-with-body --silent --show-error -X PATCH \
  --cookie "$signal_demo_dir/cookies.txt" \
  -H "Origin: $DEMO_URL" -H 'Content-Type: application/json' \
  --data-binary @"fixtures/miro-personas/$DEMO_PERSONA/profile.json" \
  "$DEMO_URL/api/v1/companies/$signal_company_id/profile"

for signal_document in fixtures/miro-personas/"$DEMO_PERSONA"/documents/*.txt; do
  curl --fail-with-body --silent --show-error \
    --cookie "$signal_demo_dir/cookies.txt" -H "Origin: $DEMO_URL" \
    --form "file=@$signal_document;type=text/plain" \
    "$DEMO_URL/api/v1/companies/$signal_company_id/files"
done
```

Цикл загрузки документов предназначен для первой подготовки. Перед повторной
загрузкой проверьте список файлов в кабинете: серверный upload не является
идемпотентным импортом. Убедитесь, что компания и `companyId` соответствуют persona.

### 3.4. Создать второго пользователя той же компании

```bash
python3 - "$DEMO_PERSONA" "$signal_company_id" "$signal_demo_dir" <<'PY'
import json, sys
from pathlib import Path
persona, company_id, target = sys.argv[1], int(sys.argv[2]), Path(sys.argv[3])
items = json.loads(Path('fixtures/miro-personas/colleague-requests.json').read_text())
colleague = next(item for item in items if item['persona'] == persona)
payload = {key: value for key, value in colleague.items() if key != 'persona'}
payload['companyId'] = company_id
(target / 'colleague.json').write_text(json.dumps(payload, ensure_ascii=False))
PY

curl --fail-with-body --silent --show-error \
  --cookie "$signal_demo_dir/cookies.txt" \
  -H "Origin: $DEMO_URL" -H 'Content-Type: application/json' \
  --data-binary @"$signal_demo_dir/colleague.json" \
  "$DEMO_URL/api/v1/users"
```

Повторите 3.1–3.4 для `beeline`, `rzd`, `etalon`, меняя `DEMO_PERSONA`. После
проверки удалите временные папки с cookie-файлами. Если второй пользователь уже
создан, `409` не требует повторного создания компании — проверьте его вход.

Используйте публичный HTTPS-адрес, чтобы Secure cookie серверной сессии работала
штатно. Локальный `seed_demo_profiles.py` намеренно не принимает произвольный
серверный домен; обходить это ограничение для подготовки стенда не требуется.

### 3.5. Проверка готовности к сдаче

- По каждому из восьми логинов удаётся войти на публичном HTTPS-адресе.
- У двух пользователей одной компании одинаковый `companyId` и нужные роли.
- У каждой компании есть профиль и четыре обработанных документа.
- В Go worker настроен analytics API; аналитика имеет действующий `AI_API_KEY`.
- В ленте и бизнес-ситуациях есть результаты, проверены ссылки на основания.
- Проверены один диалог, история после перезагрузки и второй пользователь.
- Архивные PDF-графики открываются и показывают ограничения точности.
- После фактической подготовки пометка «аккаунты ещё не созданы» в README обновлена.

<a id="local-start"></a>
## 4. Полный локальный стек

Основная инструкция: [README → запуск](../README.md#launch).

```bash
cp .env.example .env
# Заполните AI_API_KEY, замените AI_SERVICE_TOKEN и INTERNAL_API_TOKEN.
make up
```

Создайте Python venv для загрузчика:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r orchestrator/analytics/requirements.txt
.venv/bin/python scripts/seed_demo_profiles.py \
  --base-url http://127.0.0.1:8080 --personas beeline x5 rzd etalon
```

Без `--personas` загружаются только X5 и РЖД, по одному пользователю и четыре
документа на компанию. При активированном venv этот вариант доступен как
`make demo-seed`. Загрузчик проверяет точное совпадение личности и компании,
входит в существующий аккаунт, обновляет изменившийся профиль и пропускает
совпадающие по имени/размеру/MIME файлы. Контрольной суммы в списке файлов пока
нет: изменение текста без изменения размера загрузчик может не заметить.

Коллеги автоматически не создаются. Для них выполните 3.4 через локальный адрес,
сохранив сессию первого пользователя и получив его `companyId` по шагам 3.1–3.3
без повторной загрузки документов. В локальном Compose Secure cookie отключена;
HTTP разрешён на loopback. Публичная серверная конфигурация использует HTTPS.

Обычные источники опрашиваются при старте, далее каждые 15 минут. Cold start
сохраняет 352 архивных материала ЦБ и Frank Media; снимок не содержит персональных
LLM-ответов. Оценка охватывает последние 21 день на момент обработки и зависит от
профиля, очереди и лимитов модели. Прошедшие проверки описаны отдельно:
[cold start](news-coldstart.md).

## 5. Разработка отдельными процессами

Нужны Go версии из `backend/go.mod`, Node 22+, Python 3.12 и зависимости проекта.
Не запускайте контейнер `server` одновременно с локальным Go на том же порту.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install \
  -r orchestrator/analytics/requirements.txt -r parser_service/requirements-test.txt
source .venv/bin/activate
(cd frontend && npm ci)
docker compose up -d postgres rustfs
make analytics-migrate
```

После настройки `.env` запустите в разных терминалах из корня; для Python
активируйте тот же venv. Makefile экспортирует значения из `.env`:

```bash
make server
make analytics-server
make analytics-worker
make worker
make web
```

Go работает на `:8080`, Python API — на `127.0.0.1:8090`, Vite — на `:5173` и
проксирует `/api` в Go. Откройте [http://localhost:5173](http://localhost:5173).
Для live-обработки должны совпадать внутренние токены и быть настроен LLM-ключ.

## 6. Автономное демо интерфейса

```bash
(cd frontend && npm ci)
make demo-web
```

Откройте [http://127.0.0.1:5173/login](http://127.0.0.1:5173/login), раскройте
«Тестовые аккаунты». `finance@signal.demo` и `operations@signal.demo` используют
пароль `SignalDemo2026!`. Они относятся только к frontend demo.

Лента и ответы подготовлены заранее, модель не вызывается. Виджеты, порядок,
закладки и демонстрационный чат сохраняются в браузере. Серверные бизнес-ситуации
в этом режиме недоступны. Для остановки Vite — Ctrl+C в его терминале.

## 7. Если что-то не работает

| Симптом | Проверка / действие |
|---|---|
| Сайт не открывается | Проверьте DNS/HTTPS, ingress и здоровье приложения в Argo CD; для локального стека — `docker compose ps` |
| Логин из таблицы не подходит | Убедитесь, что аккаунт создан именно на этом стенде; браузерное demo и сервер имеют разные аккаунты |
| Вход в старую учётку невозможен | У старого пользователя может не быть password hash; оператор использует `backend/cmd/set-password`, см. Backend API |
| `401` от Python | Сверьте `AI_SERVICE_TOKEN` и `ORCHESTRATOR_TOKEN`; служебный токен не вводят в браузере |
| Пустая лента | Проверьте роли, профиль, очередь `news_deliveries`, окно 21 день и доступность модели; «Обновить события» перечитывает результат |
| Файл загружен, но анализа нет | Проверьте analytics worker, статусы `queued/failed`, `AI_API_KEY`; для failed доступен повтор |
| Модель вернула ошибку или пустой ответ | Посмотрите код отказа и настройки выбранной модели, токены/таймауты; результат не подменяется успешным ответом |
| Нет чата | Сначала должна сформироваться бизнес-ситуация; общего свободного чата API не предоставляет |
| Jev доступен локально, но не используется на сервере | Триаж по умолчанию выключен, в Helm пока нет передачи ключа Jev |
| Документы создаются повторно | У upload нет общей идемпотентности; локальный загрузчик пропускает совпадающие файлы, ручной curl-цикл — нет |
| После изменения `.env` ничего не меняется | Пересоздайте нужные контейнеры; `VITE_DATA_MODE` требует пересборки frontend |

Логи локального стека:

```bash
docker compose logs --tail=100 server worker analytics analytics-worker
```
