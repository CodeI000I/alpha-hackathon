# API backend «Сигнала»

Контракт, который сейчас реализует Go backend (`internal/httpapi`). Его использует frontend
(`frontend/src/api/client.ts`, описание со стороны frontend — `frontend/BACKEND_INTEGRATION_RU.md`
в ветке `frontend`). Новые маршруты появляются только после согласования с frontend.

## Общие правила

- Базовый путь `/api/v1`, JSON в camelCase, модели — `internal/domain/models.go`.
- Даты — RFC 3339. Пустые списки — `[]`, пустой профиль компании — `{}`.
- Ошибка — неуспешный HTTP-статус и тело `{"error": "текст"}`. Текст на русском:
  frontend показывает его пользователю как есть.
- Неизвестный путь под `/api/` — `404 {"error": "Метод API не найден"}`, а не `index.html`.
- При запуске `cmd/server` API требует сессию в cookie `alpha_session`. Роль, пользователь и компания
  берутся из сессии, а не из присланных клиентом заголовков или ID. Локальные старые API-тесты могут
  создавать `Server` без `RequireAuth`, но production entrypoint включает его.
- Для браузерных мутаций сервер проверяет same-origin `Origin`/`Sec-Fetch-Site`. Cookie HttpOnly,
  SameSite=Strict; Secure включён по умолчанию (`SESSION_COOKIE_SECURE=false` только для локального HTTP).

| Статус | Когда |
| --- | --- |
| `400` | Некорректный ID в пути, битый JSON, не прошла проверка полей |
| `401` | Нет действующей сессии или служебного токена |
| `403` | Пользователь пытается обратиться к другой компании/пользователю, не назначенной роли или не с того origin |
| `404` | Нет пользователя или компании |
| `409` | Email уже зарегистрирован |
| `413` | Загружаемый файл больше 12 МиБ |
| `503` | Не настроено файловое хранилище (`S3_ENDPOINT` пуст) |
| `500` | Непредвиденная ошибка (подробности только в логе сервера) |

## Маршруты

| Метод | Путь | Ответ | Ошибки |
| --- | --- | --- | --- |
| `POST` | `/auth/login` | `200 User`, устанавливает сессию | `400`, `401`, `429` |
| `GET` | `/auth/me` | `200 User` | `401` |
| `POST` | `/auth/logout` | `204`, отзывает текущую сессию | `401` |
| `POST` | `/onboarding` | `201 {company,user}`, устанавливает сессию | `400`, `409` |
| `GET` | `/roles` | `200 Role[]` | |
| `GET` | `/profile-elements` | `200 ProfileElement[]` | |
| `POST` | `/companies` | `201 Company` (legacy/test only; production registration uses `/onboarding`) | `400`, `403` |
| `GET` | `/companies/{id}` | `200 Company` | `400`, `404` |
| `PATCH` | `/companies/{id}/profile` | `200 Company` | `400`, `404` |
| `GET` | `/companies/{id}/files` | `200 CompanyFile[]`, новые первыми | `400`, `404` |
| `POST` | `/companies/{id}/files` | `201 CompanyFile` | `400`, `404`, `413`, `503` |
| `POST` | `/users` | `201 User`; authenticated user may add a colleague to their own company | `400`, `403`, `404`, `409` |
| `GET` | `/users/{id}` | `200 User` | `400`, `404` |
| `PUT` | `/users/{id}/roles` | legacy/test only; production role changes are denied | `400`, `403`, `404` |
| `GET` | `/users/{id}/feed` | `200 FeedItem[]` | `400`, `404` |

`/analytics/{path}` GET/POST/PATCH — ограниченный прокси к Python `/v1/analytics/*`; принимает только
ситуации, документы, issues, evidence/history/state, conversations, jobs, questions и refresh.
Все запросы требуют `?role=...`, причём роль должна быть назначена текущему пользователю. Глобальная
загрузка новостей, профиля компании и документов недоступна через browser proxy.

Служебные: `GET /healthz` (процесс жив), `GET /readyz` (`503`, если нет связи с БД).

## Авторизация и bootstrap

`POST /auth/login` принимает `{"email":"...","password":"..."}`. `GET /auth/me` возвращает
пользователя текущей сессии. `/onboarding` создаёт новую компанию и первого пользователя атомарно;
`user.password` обязателен (10–72 байта). Повтор с тем же `Idempotency-Key` возвращает те же записи
и выдаёт новую сессию. Повторное присоединение к компании только по ИНН/ID запрещено. После входа
пользователь может зарегистрировать коллегу через `POST /users`, передав `companyId` своей компании,
почту, имя, пароль и роли. Отозванные и истёкшие сессии не работают.

Пароль хранится только как bcrypt-хеш, cookie содержит случайный bearer-токен, а PostgreSQL хранит
его SHA-256-хеш. Существующие до этой миграции пользователи получают пустой `password_hash` и не могут
войти, пока оператор не назначит им пароль. Для существующей учётной записи используйте CLI из
каталога `backend` (пароль читается из stdin, а не из аргументов команды):

```bash
DATABASE_URL='postgres://…' go run ./cmd/set-password existing-user@example.org
```

Команда обновляет только найденную учётную запись и отзывает её активные сессии; она не создаёт
пользователя и не меняет компанию или роли. В production CLI должен быть собран/доступен оператору
в backend-образе.

Миграция `0006_case_insensitive_email.sql` добавляет уникальность email без учёта регистра. Перед
первым запуском на существующей базе проверьте возможные неоднозначности:

```sql
SELECT lower(email), array_agg(id ORDER BY id), array_agg(email ORDER BY id)
FROM users GROUP BY lower(email) HAVING count(*) > 1;
```

Миграция намеренно завершится ошибкой при таких дублях и никого автоматически не объединяет. Сначала
оператор должен определить правильные учётные записи и вручную разрешить конфликт, сохранив нужные
роли и связи; после этого миграцию можно повторить.

## Регистрация

Production frontend регистрирует компанию и первого пользователя одним атомарным запросом
`POST /onboarding`, описанным выше. При конфликте ИНН регистрация останавливается: публичного
присоединения к существующей компании только по ИНН нет. `POST /companies` и passwordless `POST /users`
сохранены для изолированных legacy-тестов, но `cmd/server` не разрешает использовать их так.

### `POST /companies`

```json
{ "inn": "7707083893", "name": "ООО Север" }
```

- `name` обязателен, после обрезки пробелов от 1 до 160 символов.
- `inn` — 10 или 12 цифр. Контрольная сумма не проверяется.
- `ogrn` необязателен, если передан — 13 или 15 цифр. `profile` необязателен.
- Legacy endpoint в режиме теста возвращает существующую компанию при совпавшем ИНН. В production
  этот путь закрыт; добавление коллег выполняет только уже аутентифицированный пользователь той же компании.

### `POST /users`

```json
{ "fullName": "Анна Петрова", "email": "anna@example.ru", "companyId": 17, "roles": ["ceo", "cfo"] }
```

- `fullName` обязателен, до 120 символов; `email` — вида `x@y.z`, до 320 символов.
  Пробелы по краям обрезаются (как во frontend).
- `companyId` может быть `null`; несуществующая компания → `404 {"error": "Компания не найдена"}`.
- `roles` — коды из `/roles`, неизвестные коды пропускаются. В ответе фактический набор ролей.
- Повторный email → `409 {"error": "Пользователь с такой электронной почтой уже зарегистрирован"}`.
- Пользователь и его роли создаются одной транзакцией: неудачная попытка email не занимает.

Если `POST /users` вернул ошибку, компания уже создана. Frontend хранит её `id` и при повторе
отправляет только `POST /users`, поэтому после `409` по email достаточно исправить почту.

## Роли

`PUT /users/{id}/roles` с телом `{"roles": ["strategy", "cfo"]}` заменяет набор ролей целиком
в legacy/test режиме. В production самостоятельная смена ролей запрещена; её должен выполнять
администраторский путь после появления соответствующей политики доступа.

## Лента

`GET /users/{id}/feed?role=cfo&limit=200`

- `role` необязателен: без него лента по всем ролям пользователя.
- `limit` от 1 до 200, по умолчанию 50; больше 200 обрезается до 200.
- Порядок: сначала свежие новости (`news.publishedAt`), при равенстве — выше `score`.
- `kind` — `event`, `risk` или `opportunity`; `score` — релевантность `0…1`; `elements` — всегда массив.
- Несуществующий пользователь → `404`; у существующего без записей — `[]`.

Ленту строит воркер (`cmd/worker`). Каждые `INGEST_PERIOD` он собирает RSS-ленты включённых
источников, ставит новости за последние `RANK_LOOKBACK` в очередь и отдаёт на оценку AI-оркестратору
не больше `RANK_MAX_PER_RUN` штук за проход, начиная с последних. Оценка одна на пару (новость, компания)
по всем ролям её директоров. Оценка сохраняется для пары (новость, компания, роль), а выдача ограничена ролями конкретного
пользователя. Добавленные позже роли оцениваются отдельно; новые коллеги получают карточки по своим
ролям. Очередь использует revision-fenced leases, а проходы чередуют новые и старые доставки, чтобы
постоянный поток свежих новостей не вытеснял backlog. Один вызов оркестратора получает union ролей
директоров компании. Пока `ORCHESTRATOR_URL` пуст, вместо оркестратора работает заглушка: новость
попадает в ленту, если в ней есть название или ИНН компании.

## Файлы компании

`POST /companies/{id}/files` — `multipart/form-data`, поле строго `file`, до 12 МиБ.
Компания проверяется до записи в хранилище, поэтому `404` не оставляет файлов-сирот. Статус
обработки документов доступен через `GET /analytics/documents?role=...`; загрузка в аналитику
идёт через backend worker и служебный маршрут `GET /api/v1/internal/files/{id}/content`,
доступный только с `INTERNAL_API_TOKEN`. Worker скачивает только файл, принадлежащий известной
компании в Go PostgreSQL; произвольный URL передать нельзя. Размер ограничен 12 МиБ.

## Служебный импорт новостей

Не для frontend: загрузка демо-новостей и новостей из источников без RSS. Маршрут работает,
только если задан `INTERNAL_API_TOKEN`; иначе `404`.

```bash
curl -X POST https://alpha.devgit.net/api/v1/internal/news \
  -H "Authorization: Bearer $INTERNAL_API_TOKEN" -H 'Content-Type: application/json' \
  -d '[{"title": "РЖД повышает тарифы на перевозку металла", "summary": "…", "body": "Полный текст…",
        "url": "https://…", "sourceId": "S139", "publishedAt": "2026-10-22T10:30:00Z"}]'
```

- Тело — массив из 1–100 новостей. `title` обязателен, до 1000 символов; `summary` до 30 000,
  `body` до 100 000 (лимиты оркестратора). `body` во frontend не отдаётся, его читает только оркестратор.
- `sourceId` — ID из листа «3. Источники» (`S001`…); по умолчанию `manual`. Неизвестный → `404 {"error": "Источник не найден"}`.
- `externalId` — ID новости в источнике, по умолчанию `url`, а без него — хеш текста. Повторный
  импорт той же новости ничего не меняет.
- `publishedAt` по умолчанию — время импорта. Новость старше `RANK_LOOKBACK` (неделя) не оценивается.
- Ответ `200`: `[{"id": 1001, "created": true}]`, `created: false` — такая новость уже была.
- Без токена или с неверным токеном — `401 {"error": "Нужен служебный токен"}`.

Сервер сразу будит воркер, и через несколько секунд (время ответа оркестратора) новость
появляется в лентах директоров, для ролей которых она важна.

## Проверка

Тесты контракта (`internal/httpapi/api_test.go`) идут против настоящего PostgreSQL и без
`TEST_DATABASE_URL` пропускаются, в том числе в CI:

```bash
docker run -d --rm --name alpha-test-pg -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app \
  -e POSTGRES_DB=alpha -p 127.0.0.1:55432:5432 postgres:16-alpine
TEST_DATABASE_URL='postgres://app:app@localhost:55432/alpha?sslmode=disable' go test ./...
docker stop alpha-test-pg
```
