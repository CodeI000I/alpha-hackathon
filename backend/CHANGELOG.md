# Изменения backend

Версии выпускает CI при слиянии в `main` (см. «Как выпускается версия» ниже).
Первой будет 1.0.0: она соберёт согласованные `frontend`, `backend` и `ai-orchestrator`.

## 1.0.0 — готовится

### Сверка с новым frontend (коммиты ttrn2nd в ветке `frontend`, 21–22 октября 2026)

Дизайнер полностью обновил интерфейс и описал интеграцию в `frontend/BACKEND_INTEGRATION_RU.md`.
Клиент `frontend/src/api/client.ts` вызывает те же 11 маршрутов, что уже были в backend,
с теми же JSON-моделями, поэтому новых маршрутов нет. Возможности из раздела 14 его документа
(вход, чат, закладки, карточка новости по ID и т.д.) там же помечены как ещё не согласованные
и не реализованы. Исправлено то, в чём ответы backend расходились с его контрактом:

- **Повторный ИНН при регистрации давал `500`.** В одной компании несколько директоров
  с разными ролями, поэтому второй директор с тем же ИНН присоединяется к уже созданной
  компании: `POST /companies` отвечает `200` и существующей компанией, данные компании
  не меняются. Новая компания по-прежнему `201`. Свою роль директор выбирает сам.
- **Повторный email давал `500`.** Теперь `409` «Пользователь с такой электронной почтой
  уже зарегистрирован», frontend показывает текст в форме. Проверено в браузере: после `409`
  достаточно вернуться на первый шаг и сменить почту, компания второй раз не создаётся.
- **Пользователь создавался без транзакции**: при сбое на ролях оставался пользователь, и повтор
  получал «email занят». Теперь пользователь и роли создаются вместе.
- **Ошибки БД вместо `400`.** ИНН длиннее 12 символов падал на `VARCHAR(12)` с `500`. Поля
  проверяются по тем же правилам, что в форме: ИНН из 10 или 12 цифр, email вида `x@y.z`,
  имя до 120 символов, название компании до 160, ОГРН (если передан) из 13 или 15 цифр.
  Пробелы по краям обрезаются.
- **`500` вместо `404`:** `POST /users` с несуществующей компанией и `PUT /users/{id}/roles`
  для несуществующего пользователя. `GET /users/{id}/feed` и `GET /companies/{id}/files`
  для несуществующих ID отдавали `[]`, теперь `404`, как в demo-режиме frontend.
- **Загрузка файлов:** больше 50 МБ — `413` вместо `400` с неверным текстом. Компания
  проверяется до записи в хранилище: раньше файл для несуществующей компании оставался
  в S3, а запрос заканчивался `500`.
- **`null` вместо `[]`:** `/roles` и `/profile-elements` на пустом справочнике.
- **Неизвестный путь `/api/...` отдавал `index.html` со статусом `200`**, и frontend принял бы его
  за успешный ответ. Теперь `404 {"error": "Метод API не найден"}`.
- **Тексты ошибок на русском**, раньше были `not found`, `bad id`, `internal error`.
- **`limit` больше 200** в ленте сбрасывался на 50, теперь обрезается до 200.
- **Воркер:** если оркестратор вернёт `elements: null`, запись в ленту падала на `NOT NULL`.
  Теперь сохраняется пустой массив.
- **Параллельные `PUT /roles`** одного пользователя могли столкнуться на первичном ключе
  `user_roles`, теперь выполняются по очереди (`SELECT … FOR UPDATE`).

Схема БД и JSON-модели не менялись, миграций нет. Полный контракт — [API.md](API.md).

### Код

- `internal/storage/postgres`: `CreateCompany` возвращает существующую компанию по ИНН
  (`INSERT … ON CONFLICT (inn) DO NOTHING`) и признак `created`; ошибка `ErrEmailTaken`; `CompanyExists`;
  `ErrNotFound` из `Feed`, `ListCompanyFiles`, `SetUserRoles`, `CreateUser`, `CreateCompanyFile`.
- `internal/httpapi`: проверка полей, `fail(w, err, notFound)` переводит ошибки хранилища
  в `404`/`409`/`500`; `Server.Files` стал интерфейсом `FileStore`, чтобы тестировать загрузку
  без S3.
- `internal/httpapi/api_test.go`: тесты контракта против PostgreSQL (как запускать — в API.md).

## Как выпускается версия

После успешной сборки образа и обновления тега в `values.yaml` job `release` создаёт тег `vX.Y.Z`
на слитом коммите и GitHub Release с автоматическими заметками (`gh release create --generate-notes`).

- Нет ни одного тега `v*` — выходит `v1.0.0`.
- Дальше версия считается по сообщениям коммитов с прошлого тега
  ([Conventional Commits](https://www.conventionalcommits.org/ru/)):
  `feat!:`/`fix!:` или `BREAKING CHANGE` → major, `feat:` → minor, остальное → patch.
  Коммиты бота `deploy: … [skip ci]` не учитываются.
- Повторный запуск на уже выпущенном коммите ничего не создаёт.
- Слияние, в котором поменялись только `*.md`, `docs/**` или `deploy/**`, CI не запускает,
  поэтому и релиза нет.

Чтобы версии росли осмысленно, коммиты в `main` стоит называть по Conventional Commits,
как это уже делает frontend (`feat(frontend): …`, `fix(frontend): …`).
