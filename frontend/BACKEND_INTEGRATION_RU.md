# Интеграция backend с фронтендом «Альфа Инсайты»

Документ описывает фактический контракт, который использует frontend в ветке `frontend`. Он предназначен для backend-разработчика и не предлагает менять существующие Go-модели без отдельного согласования.

## 1. Общая схема

- Базовый путь API: `/api/v1`.
- В development Vite проксирует `/api` на `http://localhost:8080`.
- В production Go-сервер раздаёт собранный frontend и API с одного origin.
- Формат обмена: JSON, кроме загрузки файлов.
- Названия полей: camelCase в соответствии с `backend/internal/domain/models.go`.
- Frontend по умолчанию работает в `VITE_DATA_MODE=api`.
- При ошибке API frontend показывает ошибку пользователю и не подменяет ответ моками.
- `VITE_DATA_MODE=demo` полностью отключает сетевые вызовы и использует локальный детерминированный store.

## 2. Используемые маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/v1/roles` | Справочник ролей |
| `GET` | `/api/v1/profile-elements` | Справочник элементов профиля |
| `POST` | `/api/v1/companies` | Создание компании |
| `GET` | `/api/v1/companies/{id}` | Получение компании |
| `PATCH` | `/api/v1/companies/{id}/profile` | Есть в клиенте, но UI сейчас не вызывает |
| `GET` | `/api/v1/companies/{id}/files` | Список документов |
| `POST` | `/api/v1/companies/{id}/files` | Загрузка документа |
| `POST` | `/api/v1/users` | Создание пользователя |
| `GET` | `/api/v1/users/{id}` | Восстановление локальной сессии |
| `PUT` | `/api/v1/users/{id}/roles` | Обновление ролей |
| `GET` | `/api/v1/users/{id}/feed` | Лента пользователя |

## 3. Онбординг

Frontend выполняет два последовательных запроса.

### Шаг 1. Создание компании

```http
POST /api/v1/companies
Content-Type: application/json
```

```json
{
  "inn": "7707083893",
  "name": "ООО Север"
}
```

Ожидаемый ответ:

```json
{
  "id": 17,
  "inn": "7707083893",
  "ogrn": "",
  "name": "ООО Север",
  "profile": {},
  "createdAt": "2026-10-21T09:00:00Z",
  "updatedAt": "2026-10-21T09:00:00Z"
}
```

После успешного ответа frontend сохраняет `company.id` как промежуточный идентификатор в `localStorage`.

### Шаг 2. Создание пользователя

```http
POST /api/v1/users
Content-Type: application/json
```

```json
{
  "fullName": "Анна Петрова",
  "email": "anna@example.ru",
  "companyId": 17,
  "roles": ["ceo", "cfo"]
}
```

Если второй запрос упал, повторная отправка формы использует сохранённый `companyId` и не повторяет `POST /companies`. После успешного создания пользователя промежуточный ID удаляется, а `user.id` сохраняется как текущая локальная сессия.

На стороне backend желательно контролировать уникальность компании и пользователя отдельно: сохранение промежуточного ID защищает только от обычного повтора в том же браузере.

## 4. Роли

Frontend не содержит фиксированного списка ролей для API-режима. Названия, коды, вопросы, фокус и связанные элементы всегда берутся из:

```http
GET /api/v1/roles
```

Ответ:

```json
[
  {
    "id": 1,
    "code": "strategy",
    "name": "Директор по стратегии и развитию",
    "question": "Куда расти и за счёт чего?",
    "focus": "Конкуренты, сделки и новые рынки",
    "elements": ["И2", "Б1", "С1"]
  }
]
```

Изменение ролей:

```http
PUT /api/v1/users/23/roles
Content-Type: application/json
```

```json
{
  "roles": ["ceo", "cfo", "marketing"]
}
```

Ожидается полный объект обновлённого пользователя. После ответа frontend инвалидирует кеш пользователя и ленты.

## 5. Лента

```http
GET /api/v1/users/{userId}/feed?limit=200
GET /api/v1/users/{userId}/feed?role=cfo&limit=200
```

- `role` необязателен;
- `limit` нормализуется frontend в диапазон `1…200`;
- основной экран и прямой URL события запрашивают до 200 записей;
- детальная страница находит элемент по `FeedItem.id` внутри полученной ленты.

Пример элемента:

```json
{
  "id": 101,
  "role": "cfo",
  "kind": "risk",
  "score": 0.96,
  "insight": "Рост ставки может увеличить процентные расходы компании.",
  "elements": ["Б3", "С4"],
  "news": {
    "id": 1001,
    "sourceId": "S015",
    "url": "https://example.org/news/1001",
    "title": "Банк России опубликовал решение по ставке",
    "summary": "Краткое содержание события.",
    "publishedAt": "2026-10-20T10:30:00Z"
  },
  "createdAt": "2026-10-20T10:35:00Z",
  "readAt": null
}
```

Требования к данным:

- `kind`: только `event`, `risk` или `opportunity`;
- `score`: число от `0` до `1`; UI подписывает его как «Релевантность»;
- `role`: код из `/roles`;
- `elements`: коды из `/profile-elements`;
- `publishedAt`, `createdAt`, `readAt`: RFC 3339 / ISO 8601;
- `readAt` может быть `null`;
- `sourceId` и `url` могут быть пустыми, но frontend не выдумывает источник;
- для пустой ленты желательно возвращать `[]`, а не `null`.

Поиск, фильтр по `kind` и локальные закладки выполняются на frontend после получения ленты.

## 6. Компания и элементы профиля

Компания загружается по `companyId` пользователя:

```http
GET /api/v1/users/{id}
GET /api/v1/companies/{companyId}
GET /api/v1/profile-elements
```

`company.profile` отображается только для чтения. Frontend-клиент содержит метод `PATCH /companies/{id}/profile`, однако текущий UI его намеренно не вызывает до согласования JSON-формата каждого элемента.

Желательно всегда возвращать `profile` как объект `{}`, даже если данных ещё нет.

Формат элемента справочника:

```json
{
  "code": "Б2",
  "block": "Бизнес",
  "name": "Финансовые результаты",
  "description": "Выручка, прибыль и денежный поток",
  "purpose": "Помогает оценить масштаб влияния события"
}
```

## 7. Документы

Получение списка:

```http
GET /api/v1/companies/{companyId}/files
```

Загрузка:

```http
POST /api/v1/companies/{companyId}/files
Content-Type: multipart/form-data
```

Имя multipart-поля обязательно: `file`.

Frontend ограничивает файл размером 50 МБ. Backend должен повторно проверять размер независимо от frontend.

Ожидаемый объект файла:

```json
{
  "id": 7,
  "companyId": 17,
  "filename": "бюджет-2027.pdf",
  "contentType": "application/pdf",
  "sizeBytes": 1842903,
  "createdAt": "2026-10-21T11:00:00Z"
}
```

Удаление и скачивание файлов в текущем UI не реализованы, потому что соответствующих API-методов нет.

## 8. Ошибки

Для ошибки желательно возвращать HTTP-статус `4xx` или `5xx` и JSON:

```json
{
  "error": "понятное описание ошибки"
}
```

Клиент также понимает строковое поле `message`. Он сохраняет HTTP-статус и тело ответа в типизированной ошибке `ApiError`.

Важные случаи:

- `400` — некорректные поля или формат запроса;
- `404` — пользователь, компания или лента не найдены;
- `409` — конфликт уникальности, если backend его добавит;
- `413` — слишком большой файл;
- `503` — временно недоступный сервис или хранилище.

Не следует возвращать `200` с описанием ошибки внутри успешного JSON: frontend воспримет такой ответ как данные.

## 9. Авторизация и сессия

Настоящей авторизации сейчас нет. Frontend сохраняет `userId` в `localStorage`, затем вызывает `GET /users/{id}` при открытии защищённых страниц.

Это подходит только для прототипа. После добавления авторизации потребуется согласовать:

- способ входа;
- cookie или токен;
- срок жизни сессии;
- `401` и `403`;
- получение текущего пользователя без передачи произвольного ID;
- миграцию существующей локальной сессии.

Не нужно добавлять на backend обработку пароля, пока не согласован полный механизм авторизации.

## 10. Функции без серверного API

Следующие возможности не отправляют данные в backend и помечены в UI как «Демо»:

- закладки;
- ключевые слова;
- чат;
- аналитические графики и показатели;
- прогноз влияния и рекомендуемые следующие шаги.

Если эти возможности должны стать настоящими, сначала требуется согласовать новые endpoint'ы и модели данных. Frontend не следует молча подключать к произвольным полям `company.profile`.

## 11. Чек-лист backend перед совместной проверкой

- Go API доступен на `:8080` для локальной разработки.
- Все маршруты используют префикс `/api/v1`.
- JSON-поля совпадают с camelCase-контрактом.
- `/roles` и `/profile-elements` возвращают массивы.
- Компания после создания возвращает числовой `id` и объект `profile`.
- Пользователь после создания возвращает числовой `id`, `companyId` и массив `roles`.
- Лента принимает `role` и `limit`, возвращает `[]` при отсутствии событий.
- `kind` ограничен тремя поддержанными значениями.
- `score` передаётся как релевантность в диапазоне `0…1`.
- Загрузка файла принимает multipart-поле `file` и проверяет лимит 50 МБ.
- Ошибки возвращаются с корректным HTTP-статусом и полем `error`.
- Production-сервер раздаёт содержимое `frontend/dist` и поддерживает SPA fallback на `index.html`.

## 12. Где смотреть актуальный контракт во frontend

- `src/api/types.ts` — TypeScript-модели;
- `src/api/client.ts` — URL, методы, payload и обработка ошибок;
- `src/pages/OnboardingPage.tsx` — последовательность создания компании и пользователя;
- `src/pages/FeedPage.tsx` — загрузка и фильтрация ленты;
- `src/pages/CompanyPage.tsx` — роли, компания и документы;
- `vite.config.ts` — локальный proxy.

При изменении Go-модели или маршрута необходимо одновременно обновить `types.ts`, `client.ts`, тесты и этот документ.
