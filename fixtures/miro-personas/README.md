# Тестовые профили по портретам Miro

Источник четырёх исходных ролей и мотивов: фрейм «Портрет пользователей» на [доске команды](https://miro.com/app/board/uXjVEcKS518=/). Сводка исходных описаний — в [portraits.md](portraits.md). Ещё четыре [тестовых коллеги](colleagues.md) добавлены для сравнения ролей внутри компаний; их нет на доске. Дата подготовки: 24 октября 2026 года.

**Это полностью синтетический набор.** Названия «Билайн», X5, РЖД и «Эталон» служат только привязкой к портретам Miro. Имена сотрудников, адреса, ИНН, пароли, показатели, контрагенты, проекты и содержание документов вымышлены. Сведения не описывают реальные компании или их банковское обслуживание. Указанное на доске публичное сотрудничество с Альфа-Банком не раскрывает состав услуг; в наборе он не предполагается.

Значения в `profile.json` записаны строками: это позволяет текущему API-интерфейсу показывать их в кабинете. Все элементы, связанные с обеими выбранными ролями в каталоге `backend/migrations/0002_seed.sql`, заполнены; общие сведения `И1` и `Б1` добавлены там, где их нет в ролевом наборе. Остальные необязательные элементы каталога не выдаются за известные факты. Документы каждой компании общие для двух её пользователей.

Оба файла запросов с паролями хранятся в Git. Пароли **вымышленные и общедоступные**; прежние пути в `data/miro-personas/` сохранены как локальные ссылки на эти файлы. Для каждой учётки пароль можно выбрать самостоятельно. Создавать учётки с опубликованными паролями следует только в изолированной тестовой базе; для доступной извне среды задайте новые пароли.

## Как заполнить

1. В режиме API откройте регистрацию первого пользователя. Внесите `fullName` и `email` из `registration.json`, затем `company.name`, `company.inn`, пароль из `registration-requests.json` и роль. Все четыре ИНН уникальны и состоят из 10 цифр; это искусственные идентификаторы, а не ИНН названных компаний.
2. Сохраните ID созданной компании. Пока вы вошли как первый пользователь, добавьте коллегу авторизованным `POST /api/v1/users`: возьмите поля из `colleague.json`, подставьте `companyId` из ответа регистрации и пароль из `colleague-requests.json`. В нём `companyId: null` — место для ID, отправлять `null` нельзя. Форма добавления коллеги во frontend пока не предусмотрена; простая повторная регистрация создала бы конфликт по ИНН.
3. Профиль компании пока доступен в интерфейсе только для чтения. Заполните его авторизованным `PATCH /api/v1/companies/{id}/profile` с содержимым `profile.json` и сессионной cookie пользователя этой компании. Выполняйте запросы с того же origin, что и приложение.
4. В кабинете откройте «Документы» и загрузите четыре `.txt` из папки компании один раз. Они общие для обоих пользователей. Каждый файл меньше лимита 12 МиБ. Убедитесь, что статус анализа стал «Анализ завершён»: успешная загрузка сама по себе анализа не подтверждает.
5. Войдите по очереди под каждым из двух пользователей и проверьте ленту и ответы на **одно и то же событие** по [сценариям](scenarios.md). Ключевые слова во вкладке «Ключевые слова» сохраняются только в браузере и пока не меняют серверный подбор.

Если в тестовой базе уже есть компания с указанным ИНН или пользователь с указанной почтой, регистрация вернёт конфликт. Используйте чистую базу либо замените оба искусственных идентификатора последовательно в своём тестовом экземпляре. Регистрация не присоединяет нового пользователя к существующей компании по ИНН.

Набор проверяет различие по роли при одинаковом контексте компании. Индивидуальные предпочтения не сохраняются в отдельном профиле пользователя: личные заметки в загруженных документах не являются надёжным источником пользовательской настройки. Аккаунты не создавались, файлы не загружались, качество ответов и сквозная работа сервиса этим набором ещё не подтверждены.
