# Интеграция в main — 24 октября 2026

## Результат

Сведены `origin/main` (`51c5108`, Signal/Go/deploy) и `ai-orchestrator`
(`23b60a1`, analytics/parser/System One и исправления аудита). История веток
сохраняется merge-коммитом. Старые backend/frontend ветки уже входят в main,
адаптер System One — в ai-orchestrator. Исходные миграции не переписывались.

Аналитика подключена к приложению: регистрация и сессия → профиль/документы →
новости → Go delivery → Python `/rank` → лента и бизнес-ситуации → evidence,
история, пользовательское состояние и чат. Архитектура и причины решений:
[схема](architecture.md), [ADR](decisions/0001-unified-runtime.md).

Работа разделялась между агентами backend, frontend и runtime. Каждый применял
Ponytail и Agent Skills; интеграционные адаптеры, сквозные контракты и итоговый
review проверялись также основным агентом.

## Что изменилось

- **Доступ:** bcrypt-пароли, случайные PostgreSQL-сессии в HttpOnly cookie,
  восстановление `/auth/me`, logout, проверки Origin и владения company/user/role.
  Публичного присоединения к компании по одному ИНН больше нет. Права proxy
  задаёт Go; служебные токены не передаются браузеру.
  Fingerprint регистрации исключает пароль. Повтор с ключом проверяет текущий
  bcrypt-хеш под блокировкой пользователя и не восстанавливает доступ старым
  паролем после reset. Login и onboarding имеют общий лимит попыток.
- **Go → Python:** закрытый analytics host, совместимый `/rank`, ревизии новостей,
  общий company context и сохранённые результаты. Кеш LLM остаётся в Python;
  дополнительный Go-кеш с независимыми правилами актуальности не создаётся.
- **Очередь:** сохранены claim/lease/fencing/backoff из аудита, объединены роли
  директоров, backfill и исправления main. Claims чередуют новые и старые новости,
  чтобы поток новых не вытеснял ожидающие задачи. Lease учитывает HTTP timeout.
- **Документы:** существующий S3-клиент Go, закрытый маршрут чтения оригинала,
  лимит 12 МиБ и проверка точного размера. Python сохраняет состояние обработки,
  не скачивает готовый файл повторно, допускает явный retry failed.
- **Парсер:** переиспользованы очередь, worker, SourcePolicy и JobResult.
  Результаты с неполным текстом или датой только до дня удерживаются с причиной;
  дата и текст не достраиваются. Запоздалый старый результат не откатывает ревизию.
- **Signal:** сохранён дизайн main, добавлены реальные snapshot/issues/evidence,
  версии, state/chat и фоновые статусы. Рабочий режим не подставляет демо-KPI.
  Диалог сохраняет закреплённую версию, новый разбор начинается явно. Ошибка logout
  показывается пользователю; интерфейс не объявляет действующую сессию закрытой.
- **Запуск:** полный Compose, Python image, приватные Helm API/worker, persistent
  documents volume, явные миграции и readiness. Совместный advisory lock охватывает
  также checkpoint setup. Сервис может запуститься без model key; аналитические
  jobs ждут настройки, а чтение и вход остаются доступны.
- **CI:** тесты Go/Python/PostgreSQL/pgvector и frontend/browser, сквозной HTTP
  smoke; сборка обоих образов до публикации и обновление обоих тегов для Argo CD.

## Запуск локально

```bash
cp .env.example .env
# Заполнить AI_API_KEY и заменить два служебных токена.
make up
docker compose ps
docker compose logs --tail=100 analytics analytics-worker worker
```

UI: `http://localhost:8080`. Все опубликованные порты Compose привязаны к loopback.
`make down` сохраняет данные. Не используйте `down -v`, если данные нужны.

Создайте компанию с паролем, заполните профиль и загрузите документ. Go-источники
из seed выключены: для данных включите подходящие `sources` или используйте
`POST /api/v1/internal/news` с `INTERNAL_API_TOKEN` согласно [API](../backend/API.md).
Наличие ключа модели само по себе не создаёт новости.

Parser ЦБ необязателен. Для него задайте `COMPOSE_PARSER_DATABASE_URL` с адресом,
доступным из контейнера (можно ту же БД, отдельная схема `parser`), явно включите
`PARSER_CBR_ALLOW_FETCH` и `PARSER_CBR_ALLOW_PERSIST`, выполните миграции и
перезапустите analytics worker. В Helm используйте `analytics.parser.enabled=true`
и `PARSER_DATABASE_URL` в Secret. Разрешение в конфигурации не отменяет проверку
политики источника/robots. При отказе источника worker фиксирует ошибку и продолжает
обработку компаний; неполный результат не выдаётся за полноценную новость.

## Обновление существующей установки

1. Сохранить backup PostgreSQL, S3 и documents volume. PostgreSQL major остаётся 16;
   не подставлять PG17 поверх старого PG16 тома. Для новой базы образ должен иметь pgvector.
2. Проверить case-insensitive дубли email запросом из [backend/API.md](../backend/API.md).
   Миграция `0006` не выбирает аккаунт автоматически и останавливается на конфликте.
3. В существующий `alpha-secrets` добавить `ORCHESTRATOR_TOKEN`,
   `INTERNAL_API_TOKEN`, `AI_API_KEY`. Пароль уже созданной PostgreSQL сохраняется.
   Go использует ORCHESTRATOR_TOKEN; Helm передаёт то же значение Python как
   AI_SERVICE_TOKEN. В Compose значение берётся из AI_SERVICE_TOKEN в `.env`.
4. Дождаться CI и двух согласованных тегов, затем проверить Argo CD, pods и readiness.
   Python API/worker разделяют RWO PVC на одном узле; API имеет одну реплику и
   обновляется через Recreate. Это может дать короткую паузу аналитики при rollout.
5. Старым пользователям назначить пароль через `/app/set-password` либо
   `go run ./cmd/set-password`; пароль передаётся через stdin, не аргументом.
   Команда отзывает прежние сессии. Подробный безопасный пример — в API.md.

Новые пользователи получают пароль при регистрации. Уведомления по email,
самостоятельное восстановление пароля и интерфейс приглашений не добавлялись.
Члена своей компании можно создать через авторизованный `POST /api/v1/users`.

## Проверки

Все проверки разработки используют временные компоненты и тестовые данные.
Рабочая БД, модельные ключи и боевой кластер не использовались.

| Проверка | Результат |
|---|---|
| Python orchestrator, реальная PostgreSQL | 112 тестов, без skips |
| Analytics, PostgreSQL/pgvector/checkpoints | 135 тестов, без skips |
| Parser, PostgreSQL | 125 тестов, без skips |
| Python зависимости | `pip check` — нет конфликтов |
| Go | Полный `go test -race ./... -count=1`, без skips; `go vet ./...` |
| Frontend | 121 unit, TypeScript, production build; 16 API + 22 demo Playwright |
| Frontend зависимости | `npm audit` — 0 уязвимостей на момент проверки |
| Инфраструктура | Helm lint/render, actionlint, YAML/syntax и whitespace проверки |
| Сквозной runtime | `scripts/test_unified.py`: passed, две компании, обработка двух файлов, новости и изоляция |

Сквозной smoke поднимает настоящие Go server/worker и Python HTTP, создаёт
уникальную PostgreSQL БД и использует настоящий LLMClient с MockTransport плюс
локальный S3-совместимый стенд. Аналитический worker выполняет production `run_once`;
его долгоживущий цикл и контейнерная оркестрация этой проверкой не имитируются.
Проверены auth, internal file token, оригиналы, две независимые компании, snapshot,
evidence, state, чат, повтор обработки и перезапуск сервисов. Чужой issue возвращает
404; чтение после restart делает **0 новых модельных вызовов**. Дочерняя БД и
временные сервисы удаляются.

Новые регрессии проверяют несовпадение ревизий, сохранение document facts при
обновлении формы, отсутствие повторного скачивания, неготовую модель, явный
retry, ограничение body, контролируемый busy, сериализацию миграций и запоздалый
parser result. Тесты сначала воспроизвели соответствующие сбои.

## Границы результата

Локальные Docker build и rollout в k3s не выполнялись: в рабочей среде нет Docker
daemon и подтверждённого доступа к кластеру. Проверка сборки обоих образов добавлена
в CI. Зелёные локальные тесты не подменяют статус удалённого CI/deploy.

Реальный модельный шлюз и источники не вызывались. Для рабочей эксплуатации нужны
действующие ключи, разрешённые источники и проверка доступности именно в целевом
окружении. Качество выводов на реальных данных, нагрузка, backup/restore и рост
архива требуют дальнейших измерений; абсолютная безошибочность не заявляется.
