# Проект контракта: ИИ-парсер → БД → оценка Jev

22 октября 2026. Статус: **предложение для согласования**, не реализованный API.
LangChain выбран пользователем. Формат хранения, расширение HTTP и правила оценки
ниже предлагаются; они не изменяют существующий контракт автоматически.

## Основания и граница

Кейс требует персонализации по компании/роли, трассируемости, разделения фактов,
позиции банка и выводов ИИ, корректной работы с неизвестным. Основание:
`docs/Контекст_для_ИИ_кейс_Новостная_аналитика.md`, раздел требований;
`docs/Критерии_успеха_—_новостная_аналитика.md`.
Graphify нашёл исторический context bundle в
`docs/alfa_hackathon_full_context.md:330` (раздел 7); это обсуждение, не утверждённый
внешний API Jev. Индекс структурный от 21 октября и не включает последние изменения.

Поток: ИИ-парсер отдаёт проверенные кандидаты → Go импортирует их в БД → формирует
пакет новости и контекста компании → адаптер Jev возвращает отдельную оценку.
Текущие API/очередь парсера остаются отдельно от продуктовых таблиц.
Предложение владельца записи продуктовых новостей: Go, с одним путём импорта.
Python не получает широкие права на продуктовую БД. LangChain не определяет схему БД.

## Общие правила

- Внутренний JSON: snake_case, явный `schema_version`. Текущий frontend camelCase
  остаётся отдельным DTO; не менять его транзитивно.
- news_id/company_id используют существующие BIGINT, revision — положительное целое.
  У поступившего кандидата ещё нет news_id: его назначает БД, не LLM.
- Timestamp — RFC3339 с timezone; календарный день — YYYY-MM-DD. Неизвестное — null.
  Обязательные ключи не заменять пустыми строками. Неизвестное не равно false/no_hits.
- Внешние данные/ответы LLM валидируются; URL, ID, scope и права контролируются кодом.
  Значения источника и выводы модели хранятся отдельно.
- Служебный trace_id связывает job, импорт, извлечение и оценку, не содержит секретов.

## 1. Кандидат новости: результат ИИ-парсера

| Поле | Тип и смысл |
|---|---|
| schema_version | `news_candidate.v1` |
| candidate_id | ID внутри job, назначенный обработчиком; ключ повторной доставки `(job_id,candidate_id)` |
| source_id | FK существующего реестра sources; явная mapping `cbr_press` → ID реестра, не угадывать |
| external_id | string/null; реальный ID/guid источника |
| url, canonical_url | Полученный URL; canonical_url string/null после разрешённой нормализации кодом |
| title | string/null; подтверждённый заголовок |
| source_description | string/null; анонс источника, не автоматически полный текст |
| content_text | string/null; извлечённый исходный текст, не пересказ LLM |
| content_status | `full/partial/metadata_only/unavailable` |
| publication | `{at: timestamp|null, date: day|null, precision: second/day/unknown, evidence_ids: []}` |
| fetched_at | timestamp фактического получения/null при отказе |
| language | код языка/null |
| ai_summary | string/null; явно сгенерированное резюме, только при успешной валидации |
| claims | Список извлечённых утверждений; допустим пустой список |
| evidence | Подтверждения полей и claims в полученном документе |
| attachments | Проверенные `{url, media_type|null}`; без обещания скачивания PDF |
| extraction | Версия загрузчика/очистки/схемы/промпта, model_id/null, хеш входа LLM, признак усечения |
| provenance | job_id, discovery_method, discovery_url/null, policy_version |
| incomplete_fields | Пути недостающих/усечённых полей |
| error | null или `{code,message,retryable}` с безопасным сообщением |

Publication: second требует at и date=null; day требует date и at=null; unknown
требует оба null. Дата публикации не подменяет дату события/вступления в силу.
`full` требует непустого тела и прохождения проверки целостности; LLM не может одна
назначить full. Пустое тело не становится полным после генерации summary.

Claim: `{claim_id, text, modality, event_date, effective_date, evidence_ids}`.
modality: `reported_fact/announcement/forecast/opinion/unknown`. Обе даты nullable,
с той же precision-семантикой, только при явном подтверждении источником.
Claim — утверждение источника, а не доказательство объективной истинности события.

Evidence: `{evidence_id, document_revision, text_hash, locator, quote}`.
До импорта document_revision — ссылка на снимок/хеш входного документа; при импорте
привязывается к сохранённой версии. Locator задаёт блок/абзац и при наличии offsets.
Quote проверяется кодом как точное вхождение в соответствующее сохранённое
представление текста. Такое совпадение доказывает происхождение, не смысловой вывод.
URL источника наследуется от документа, модель не придумывает его.

## 2. Продуктовая новость и версии

Предлагаем логическое разделение (имена таблиц пока не миграция):

| Сущность | Назначение |
|---|---|
| news_items | Стабильная идентичность публикации: id, source_id, identity_key, current_revision |
| news_versions | Неизменяемые версии title/body/publication/description и их происхождения |
| news_extractions | Производные summary/claims/evidence, версии модели/промпта, ссылка на news_revision |
| news_imports | Уникальная доставка `(job_id,candidate_id)` → news_id/revision/extraction_id |
| news_assessments | Оценки новости для компании и роли, с точными входными версиями |

Сначала `(source_id, external_id)`, если ID есть; иначе `(source_id, normalized_url)`.
Нормализация не удаляет значимые query (например file ЦБ). Без идентичности кандидата
не импортировать как полноценную новость, сохранить диагностируемый отказ задания.
При изменении значимого исходного текста/метаданных — новая news_revision, старую
не перезаписывать. Обновление модели/промпта при прежнем входе — новая extraction,
не новая публикация. Ошибка повторного fetch не стирает прежний пригодный текст.

Повтор точного импорта не создаёт версии или повторной оценки. Импорт новости,
запись доставки и постановка обязательства оценить фиксируются транзакционно;
при отдельной очереди нужен transactional outbox. Повторная доставка допустима,
идемпотентный потребитель обязателен. Семантическое объединение разных публикаций
об одном событии не решать уникальностью URL/хеша; event_id — отдельное будущее расширение.

## 3. Вход оценки Jev: наш внутренний контракт

Это DTO адаптера; внешний endpoint/формат Jev перепроверяется перед интеграцией.

| Поле | Содержимое |
|---|---|
| schema_version, request_id, as_of | `news_assessment.v1`, идемпотентный ID, время среза |
| scope | company_id, role_code, версия роли и доступа; scope задаёт доверенный backend |
| news | news_id, news_revision, extraction_id, title, content_text, source_description, ai_summary, publication, claims/evidence, качество/усечение |
| company_context | snapshot_revision, разрешённые факты компании, связи, coverage и подтверждения |
| bank_context | `available/not_found/not_requested/error`, релевантные выдержки аналитики банка с document_id/revision/evidence |
| retrieval | policy_version, статус, covered_dimensions, gaps, conflicts, truncated |
| evaluator | версия набора вопросов/политики оценки |

Один пакет = одна новость × компания × роль. Повторяемую новость можно передавать
по ссылке внутри сервиса, но перед вызовом внешнего оценщика адаптер разрешает её
в фактический текст и доказательства. Summary не заменяет тело незаметно.

Company fact: `{fact_id, element_code|null, predicate, value, modality,
valid_from|null, valid_until|null, evidence_ids}`. Evidence ссылается на разрешённый
документ/версию и локатор; для структурированной БД допустим row/field locator.
Coverage по измерению: `known/unknown/conflicting/not_applicable`; unknown нельзя
преобразовать в отсутствие поставщиков, валютного риска или бизнес-последствий.
Обезличенный company_id не сопоставляется с реальной компанией по догадке.
Передаваемый контекст минимален, ограничен правами и согласованной политикой
передачи корпоративных данных внешнему API.

## 4. Выход оценки

| Поле | Смысл |
|---|---|
| assessment_id, request_id | ID результата и исходного запроса |
| input_refs | news_id/revision, extraction_id, company snapshot, role/access revision, evidence bundle hash |
| status | `assessed/insufficient_data/failed` |
| relevance_score | number|null; предлагаемая шкала [0,1], не вероятность бизнес-эффекта |
| relevance | `relevant/not_relevant/unknown`; семантика вопросов/порогов отдельно утверждается |
| risk, opportunity | Независимые `indicated/not_indicated/unknown`; могут одновременно быть indicated |
| reasons | Механизм связи, news evidence_ids, company fact_ids, bank evidence_ids отдельно |
| missing_data, conflicts | Недостаток и противоречия оснований |
| evaluator | provider/model/null, questions_version, policy_version, evaluated_at |
| error | Безопасная ошибка/null |

Факт, банковское мнение и model inference имеют явную метку происхождения в reason.
Отсутствие аналитики банка не превращается в мнение банка. Пустой массив оценок
не означает технический успех и «новость неважна»: ошибки/unknown явные.
Confidence не добавляем до определения и проверки его семантики.

Обновление любой входной версии помечает прежнюю оценку устаревшей и даёт новое
намерение оценки; предыдущий результат остаётся воспроизводимым. Решение о публикации
в ленту и приоритете фонового отчёта — отдельная policy, не relevance_score.
Статус отчёта хранится отдельно; будущий отчёт ссылается на assessment_id и входные
версии. Топ-отчёты готовятся в фоне, остальные при первом открытии — прежнее решение
пользователя сохраняется. Длинный отчёт/действия не требуются от ИИ-парсера.

## Совместимость и реальные пробелы

- `backend/internal/domain/models.go:52`: Body имеет json:"-". Нельзя использовать
  frontend DTO для Jev; нужен отдельный внутренний DTO с текстом.
- `backend/internal/storage/postgres/news.go:43`: upsert меняет только title.
  Для версий, повторного извлечения и повторной оценки этого недостаточно.
- `backend/migrations/0001_init.sql`: published_at NOT NULL, summary/body NOT NULL,
  feed kind взаимоисключающий. Требуется согласованная миграция и DTO nullable dates,
  версия новости, отдельные оценки с одновременными риском/возможностью.
- `backend/internal/feed/ranker.go`: /rank — внутренний предлагаемый адаптер,
  KeywordRanker — текущая заглушка; реальный Jev не подтверждён.
- parser.jobs хранит снимки исполнения, а не продуктовые версии. Нынешняя schema
  source_id=cbr_press/discovery=rss не становится универсальной автоматически.
