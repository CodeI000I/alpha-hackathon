# «Сигнал»: интеграция frontend с Go backend

Документ фиксирует фактический контракт, найденный в `backend/internal/httpapi` и используемый `frontend/src/api/client.ts`. Будущие продуктовые потребности вынесены отдельно и не выдаются за уже существующие методы.

## 1. Транспорт и режимы

- Базовый путь: `/api/v1`.
- JSON использует camelCase, соответствующий `backend/internal/domain/models.go`.
- Исключение — загрузка файла через `multipart/form-data`.
- В development Vite проксирует `/api` на `http://localhost:8080`.
- Production-схема предполагает API и статику на одном origin.
- `VITE_DATA_MODE=api` — значение по умолчанию; каждый поддержанный сценарий вызывает Go, без fallback на fixtures.
- `VITE_DATA_MODE=demo` — запросов в сеть нет; транспорт полностью заменён детерминированным локальным store.
- API-клиент принимает `AbortSignal`. Отменённый запрос не должен продолжать обновлять экран.
- Ошибка с неуспешным HTTP-статусом становится `ApiError` с полями `status` и `body`.

Значение `VITE_DATA_MODE` выбирается на этапе запуска/сборки. Оно не должно переключаться внутри одной работающей вкладки.

Общий верхний индикатор деморежима удалён по продуктовому решению. Это не меняет режим данных: демонстрационные функции и данные сохраняют локальные пометки «Демо», а технические объяснения вынесены в документацию и раскрывающиеся разделы о данных. Банковская точка входа `/bank.html` остаётся отдельной; логотип внутри приложения ведёт на `/dashboard`, на экранах авторизации — на `/landing`.

## 2. Фактические endpoints

| Метод | Путь | Использование во frontend |
| --- | --- | --- |
| `GET` | `/api/v1/roles` | Справочник всех ролей |
| `GET` | `/api/v1/profile-elements` | Справочник элементов профиля |
| `POST` | `/api/v1/companies` | Первый сетевой вызов после финальной отправки UI-шага 2 |
| `GET` | `/api/v1/companies/{id}` | Компания текущего пользователя |
| `PATCH` | `/api/v1/companies/{id}/profile` | Метод есть в клиенте, но UI намеренно его не вызывает |
| `GET` | `/api/v1/companies/{id}/files` | Список документов |
| `POST` | `/api/v1/companies/{id}/files` | Загрузка документа |
| `POST` | `/api/v1/users` | Второй сетевой вызов после создания компании |
| `GET` | `/api/v1/users/{id}` | Восстановление локальной прототипной сессии |
| `PUT` | `/api/v1/users/{id}/roles` | Сохранение нескольких ролей |
| `GET` | `/api/v1/users/{id}/feed` | Лента; query `role` опционален, `limit` — `1…200` |

В исследованном Go-коде нет `POST /api/v1/analyze`, endpoint для входа, endpoint одной карточки ленты, чата, закладок или ключевых слов. Frontend не должен вызывать их до появления согласованного контракта.

## 3. Модели на проводе

TypeScript-модели в `src/api/types.ts` повторяют текущие Go-модели и не добавляют полей в ответы.

### Роль

```json
{
  "id": 5,
  "code": "cfo",
  "name": "Финансовый директор",
  "question": "Хватит ли денег и сколько стоит капитал?",
  "focus": "Ключевая ставка, облигации, рейтинги, валютные курсы, налоги и отчётность",
  "elements": ["Б2", "Б3", "С4"]
}
```

Frontend не содержит отдельного сокращённого каталога ролей в API-режиме. Название, вопрос, фокус и `elements` берутся из `GET /roles`. Demo fixture содержит все девять ролей текущего каталога.

### Пользователь

```json
{
  "id": 23,
  "companyId": 17,
  "email": "anna@example.ru",
  "fullName": "Анна Петрова",
  "roles": ["ceo", "cfo"],
  "createdAt": "2026-10-22T09:00:00Z"
}
```

`companyId` по Go-модели может быть `null`. Защищённый кабинет без компании показывает отдельное состояние и не должен отправлять запрос с выдуманным ID.

### Компания

```json
{
  "id": 17,
  "inn": "7707083893",
  "ogrn": "1027700067328",
  "name": "ООО Север",
  "profile": {},
  "createdAt": "2026-10-22T08:55:00Z",
  "updatedAt": "2026-10-22T08:55:00Z"
}
```

### Элемент профиля

```json
{
  "code": "Б2",
  "block": "Бизнес",
  "name": "Финансовые результаты",
  "description": "Выручка, прибыль и денежный поток",
  "purpose": "Помогает оценить масштаб влияния события"
}
```

### Элемент ленты

```json
{
  "id": 101,
  "role": "cfo",
  "kind": "risk",
  "score": 0.96,
  "insight": "Рост стоимости капитала может увеличить процентные расходы компании.",
  "elements": ["Б3", "С4"],
  "news": {
    "id": 1001,
    "sourceId": "S015",
    "url": "https://www.cbr.ru/press/keypr/",
    "title": "Банк России опубликовал решение по ставке",
    "summary": "Краткое сообщение источника.",
    "publishedAt": "2026-10-22T10:30:00Z"
  },
  "createdAt": "2026-10-22T10:35:00Z",
  "readAt": null
}
```

Ожидания UI:

- `kind` — `event`, `risk` или `opportunity`;
- `role` — код из `/roles`;
- `score` — релевантность от `0` до `1`, не вероятность события;
- `elements` — коды из `/profile-elements`;
- даты — RFC 3339 / ISO 8601, `readAt` может быть `null`;
- `sourceId` и `url` могут быть пустыми; frontend не выдумывает источник;
- безопасная кликабельная ссылка допускает только `http:` или `https:`.

### Файл компании

```json
{
  "id": 7,
  "companyId": 17,
  "filename": "бюджет-2027.pdf",
  "contentType": "application/pdf",
  "sizeBytes": 1842903,
  "createdAt": "2026-10-22T11:00:00Z"
}
```

## 4. Регистрация

Интерфейс регистрации имеет два UI-шага, которые не следует путать с двумя последовательными сетевыми вызовами:

1. На UI-шаге 1 вводятся и локально проверяются имя и email. Переход по кнопке «Продолжить» не вызывает `POST /companies` или `POST /users` и не создаёт аккаунт.
2. На UI-шаге 2 обязательны название компании, ИНН и хотя бы одна роль. Справочник ролей загружается через `GET /roles`. Только финальная отправка полностью заполненного второго шага запускает два запроса ниже.

Поля и текущий UI-шаг временно сохраняются в режиме-специфичном `sessionStorage`-черновике `signal.registration-draft.v1.{api|demo}`. Закрытие вкладки удаляет этот черновик; он не является серверной записью или сессией.

### 4.1. Создание компании

```http
POST /api/v1/companies
Content-Type: application/json
```

```json
{
  "inn": "7707083893",
  "name": "ООО Север"
}
```

Успешный Go handler отвечает `201 Created` объектом `Company`. Frontend сохраняет положительный `company.id` как промежуточный ID.

### 4.2. Создание пользователя

```http
POST /api/v1/users
Content-Type: application/json
```

```json
{
  "fullName": "Анна Петрова",
  "email": "anna@example.ru",
  "companyId": 17,
  "roles": ["ceo", "cfo"]
}
```

Успешный handler отвечает `201 Created` объектом `User`. Если этот запрос упал после успешного создания компании, повторная отправка использует сохранённый `companyId` и не повторяет `POST /companies`. После успеха промежуточный ID удаляется, а `user.id` становится локальной прототипной сессией.

Эта защита предотвращает обычный дубль в том же браузере, но не заменяет серверную идемпотентность или ограничения уникальности.

## 5. Роли

Изменение ролей:

```http
PUT /api/v1/users/23/roles
Content-Type: application/json
```

```json
{
  "roles": ["strategy", "cfo"]
}
```

Текущий handler возвращает обновлённый объект пользователя с `200 OK`. После успеха frontend обновляет пользователя и инвалидирует ленту.

В кабинете роли сначала показаны как сохранённая настройка, а не постоянно открытая форма. Кнопка «Изменить роли» открывает нативный диалог с полным каталогом. PUT выполняется только по кнопке «Сохранить роли». Отмена и Escape не отправляют запрос; повторное открытие начинает редактирование с сохранённых ролей. Во время уже отправленного PUT закрытие диалога заблокировано до получения ответа. Ошибка остаётся в диалоге с возможностью повтора. UI учитывает список ролей из ответа сервера, а не считает отправленный набор окончательным. После закрытия диалога фокус возвращается к его кнопке открытия.

## 6. Лента и прямой URL

Примеры:

```http
GET /api/v1/users/23/feed?limit=200
GET /api/v1/users/23/feed?role=cfo&limit=200
```

Клиент ограничивает `limit` диапазоном `1…200`; значение по умолчанию — `50`. Обзор получает все назначенные роли одной выборкой до 200 записей, а активный ракурс фильтруется локально: суточная сводка должна оставаться общей. Параметр `role` поддержан клиентом, но для этой общей выборки не передаётся. `/news/:itemId` использует ту же ленту и ищет объект по `id`, потому что endpoint одной карточки отсутствует. При прямой загрузке запрос выполняется заново, при переходе из обзора возможен общий свежий кеш.

Поиск, фильтр по `kind` и локальные закладки работают после получения ответа. Серверный `role` используется только для фильтра роли.

## 7. Компания и `profile`

Для кабинета используются:

```http
GET /api/v1/users/{id}
GET /api/v1/companies/{companyId}
GET /api/v1/profile-elements
```

`company.profile` отображается только для чтения. Клиент технически содержит `PATCH /companies/{id}/profile`, однако UI его не вызывает: команда backend сначала должна определить форму значения для каждого кода элемента. Нельзя записывать туда ключевые слова, настройки графиков, чат или другую произвольную структуру.

Пользовательский заголовок — «О компании». Для известных `block` используется только отображаемое переименование, без изменения wire-значений:

| `block` в каталоге | Название в кабинете |
| --- | --- |
| `Идентификация` | Сведения о компании |
| `Бизнес` | Деятельность и финансы |
| `География` | Регионы работы и поставок |
| `Среда` | Рынок и регулирование |

Названия полей берутся из каталога, технические `code` не показываются в обычном представлении. Примитивные значения отображаются напрямую. Объекты API не интерпретируются по догадке: вместо сырого JSON поле предлагает открыть «О данных и сохранении» → «Полученные данные компании», где сохранён полный `company.profile`. Человекочитаемое представление объектов подготовленных fixtures относится только к `demo` и не задаёт контракт для API.

## 8. Документы

Список:

```http
GET /api/v1/companies/{companyId}/files
```

Загрузка:

```http
POST /api/v1/companies/{companyId}/files
Content-Type: multipart/form-data
```

Имя multipart-поля — строго `file`. UI допускает до 10 МиБ на файл, а Go handler имеет верхний предел 50 МиБ (`50 << 20`) и остаётся окончательной точкой проверки. Если объектное хранилище не настроено, текущий Go handler отвечает `503`.

Успешная загрузка подтверждает только сохранение файла и появление его метаданных в списке. Текущий контракт не сообщает:

- обработан ли файл;
- какие фрагменты извлечены;
- использован ли файл в конкретном выводе;
- можно ли скачать или удалить файл.

Frontend поэтому не утверждает, что загруженный документ повлиял на анализ.

## 9. Нормализация `null`

Backend желательно возвращать пустые коллекции как `[]` и пустой профиль как `{}`. Для устойчивости клиент нормализует:

- ответ `/roles`: `null` → `[]`;
- `role.elements`: `null` → `[]`;
- ответ `/profile-elements`: `null` → `[]`;
- `user.roles`: `null` → `[]`;
- ответ `/feed`: `null` → `[]`;
- `feedItem.elements`: `null` → `[]`;
- `company.profile`: `null` → `{}`;
- ответ `/files`: `null` → `[]`.

Это защитная совместимость frontend, а не предложение изменить wire-модели.

## 10. Ошибки

Текущий Go API обычно отвечает JSON:

```json
{
  "error": "понятное описание"
}
```

Frontend также распознаёт строковое поле `message` и обычный текстовый ответ. Неуспешный статус сохраняется в `ApiError.status`, распарсенное тело — в `ApiError.body`.

Нужно возвращать корректный HTTP-статус, например:

- `400` — плохой ID, обязательное поле или payload;
- `404` — пользователь или компания не найдены;
- `413` — превышение допустимого размера, если handler различает этот случай;
- `503` — временно недоступное хранилище или сервис;
- `500` — непредвиденная серверная ошибка.

Ответ `200` с полем ошибки будет воспринят как успешные данные и использоваться не должен.

## 11. Авторизация и локальная изоляция

### API-режим

Go не имеет входа по email/паролю и не выдаёт серверную сессию. Первый UI-шаг `/register` не создаёт серверных записей; финальная отправка второго шага создаёт компанию и пользователя без пароля. Защищённые страницы восстанавливают сохранённый `userId` через `GET /users/{id}`. Это механизм прототипа, не авторизация.

### Demo-режим

`/login` принимает только два публичных fixture-аккаунта:

| Email | Пароль | Контекст |
| --- | --- | --- |
| `finance@signal.demo` | `SignalDemo2026!` | Технологическая компания, финансы/стратегия |
| `operations@signal.demo` | `SignalDemo2026!` | Промышленная компания, закупки/операции |

Проверка выполняется локально без `fetch`. Пароли не находятся в сохранённом demo store. Новая деморегистрация беспарольная и не создаёт дополнительную пару для входа.

Реквизиты на `/login` находятся в закрытом по умолчанию разделе «Тестовые аккаунты». Длинные пояснения под формами и заметка о черновике убраны с экрана, но правила сохранения и проверки не изменены. В API-режиме экран входа по-прежнему объясняет недоступность серверной авторизации и не имитирует проверку пароля.

### Ключи браузера

- сессия: `signal.session.v2.{api|demo}.userId`;
- незавершённая регистрация: `signal.session.v2.{api|demo}.pendingCompanyId`;
- черновик UI регистрации до закрытия вкладки: `signal.registration-draft.v1.{api|demo}` в `sessionStorage`;
- demo store: `signal.demo-api.v2`;
- пользовательские локальные функции: `alpha.insights.v2.{api|demo}.company.{companyId|none}.user.{userId}.{name}`.

Таким образом, API/demo, пользователи и компании не смешивают сессии и настройки. Старые `alpha.userId` и `alpha.pendingCompanyId` намеренно не читаются и автоматически не мигрируются.

## 12. Происхождение данных и экспорт

Текущий wire-контракт позволяет честно отобразить только часть требуемого разделения:

| Раздел интерфейса и TXT | Текущее поле/правило |
| --- | --- |
| «Что произошло» | `news.summary`, подпись «Сообщение источника» |
| «Значение для бизнеса» | `insight`, подпись «Интерпретация» |
| «Что может измениться» | Отдельных серверных гипотез нет; это явно написано |
| «Документы компании» | API не сообщает использованные документы; наличие файла не считается основанием |
| «Материалы банка» в demo | «Аналитика Альфа-Банка не использована в этом разборе» |
| «Материалы банка» в API | «Сведения об использовании аналитики Альфа-Банка не переданы сервером.» |
| Источник | Только `news.sourceId` и безопасный `news.url` |
| Релевантность | `score` в `0…1`; вне диапазона — «не передана» |

Локальные чат, закладки, графики, виджеты и предложения банка не включаются в аналитический вывод. Экспорт demo помечает данные синтетическими. Каждый TXT заканчивается текстом:

> Материал носит информационно-аналитический характер и не является инвестиционной рекомендацией

## 13. Решения созвона и интеграционный статус

| Договорённость | Frontend сейчас | Статус данных |
| --- | --- | --- |
| Точка входа внутри «Альфа-Бизнеса» | Есть отдельный безопасный `/bank.html`, открывающий «Сигнал» в новой вкладке | Банковский экран — demo; реальное SSO требует backend/платформу |
| Два пользователя разных компаний/ролей | Есть два детерминированных demo fixture | Реальные доступы к нескольким компаниям требуют модели прав |
| Двухшаговая регистрация | Шаг 1 сохраняет локальный черновик; шаг 2 после обязательных компании, ИНН и ролей вызывает `createCompany → createUser` | Новая demo-регистрация локальна и беспарольна; уникальность, идемпотентность и настоящая учётная запись требуют backend |
| Общая сводка и персональная лента | UI использует настоящую ленту и роли | Сложная сводка/виджеты частично demo |
| Развести факт, вывод, гипотезу, документы и позицию банка | Правила и TXT реализуют безопасные подписи | Полная трассировка требует новых серверных полей |
| Не обещать числа из PDF без данных | Графики явно иллюстративные | Структурированные ряды нужны от backend/источника |
| Банковские продукты — редкая контекстная помощь | Блоки отдельно маркированы и ведут на официальный сайт | Контекст и доступность продукта сейчас demo |
| Кабинет без отдельного экрана группы | Четыре вкладки, одна компания в активном контексте | Группа компаний отложена |
| Изменение роли по запросу пользователя | Сохранённые роли видны сразу; редактирование открывается отдельным диалогом. Меню аватарки содержит прямые ссылки на вкладки кабинета | Текущий PUT ролей сохранён; новые маршруты backend не нужны |
| Админ-панель не входит в критический путь | Не реализуется frontend | Будущий отдельный объём |

## 14. Будущие потребности API — не текущие endpoints

Ниже перечислены возможности для отдельного проектирования. Это не обещанные маршруты и не причина добавлять произвольные поля в существующие модели.

1. Авторизация: SSO или логин, безопасная сессия, текущий пользователь, срок жизни, выход, восстановление доступа, `401/403`.
2. Доступ к компаниям: список доступных юрлиц, активная компания, права ролей и, при возвращении задачи, связи группы компаний.
3. Трассировка разбора: отдельные факт, интерпретация, гипотеза, расчёт, степень уверенности/методика, дата актуальности и ссылки на конкретные основания.
4. Банковская аналитика: идентификатор материала, фрагмент/таблица, дата и явный признак участия в каждом выводе; отсутствие материала должно быть представимо отдельно.
5. Документы компании: статус загрузки и обработки, ошибки, извлечённые фрагменты, связь с конкретным выводом, скачивание и удаление.
6. Новости: свежесть сбора, статус источника, дедупликация, полный набор записей и серверная карточка по ID, если лимит ленты станет недостаточен.
7. Сводка: серверные 24-часовые агрегаты и управленческие выводы с теми же правилами происхождения.
8. Чат: поток ответа, статус, ошибка, использованные источники и документальные цитаты.
9. Пользовательские функции: серверные закладки, ключевые слова и настройки виджетов с версионированием.
10. Аналитические показатели: структурированные ряды и единицы измерения вместо извлечения неподтверждённых чисел из дизайнерских PDF.
11. Предложения банка: доступность продукта для клиента, причина показа и актуальные условия — отдельно от аналитического вывода.

## 15. Чек-лист совместной проверки

- Go доступен на `:8080`, база и нужное файловое хранилище готовы.
- Все текущие маршруты имеют префикс `/api/v1` и возвращают camelCase.
- Каталоги и списки возвращают `[]`, профиль — `{}`; клиент также переносит `null`.
- Создание компании и пользователя возвращает числовые ID.
- Пользователь содержит `companyId` и массив кодов `roles`.
- Лента принимает `role` и `limit≤200`; `kind` ограничен тремя значениями.
- `score` передаётся как релевантность `0…1`.
- UI принимает файл до 10 МиБ; загрузка использует multipart-поле `file`, а backend отдельно проверяет свой предел 50 МиБ и готовность хранилища.
- Ошибки имеют неуспешный HTTP-статус и понятное тело.
- Production-раздача включает `index.html`, `bank.html`, ассеты и SPA fallback для маршрутов «Сигнала».
- В DevTools нет неожиданных сетевых запросов в `demo` и автоматического fallback в `api`.

Результаты frontend-проверки 22 октября 2026:

- TypeScript и production-сборка проходят; `dist/index.html` и `dist/bank.html` созданы.
- 106/106 unit-тестов и 33/33 браузерных сценария (20 demo, 13 API-контрактных).
- В API-сценариях проверены реальные JSON-поля POST компании/пользователя, PUT ролей, multipart `file`, `limit=200`, `null`, HTTP-ошибки, повтор после частичного сбоя, источник и TXT. Все API-запросы перехвачены тестами; живой Go не использовался.
- В demo-сценариях проверено отсутствие запросов к API. Неожиданных ошибок консоли и runtime нет; специально возвращаемые 404/503 проверяются отдельно.
- Проверены 1440/768/390 px, низкие окна, клавиатура, диалоги, Escape, возврат фокуса. Дополнительно проверены отмена изменения ролей без PUT, повтор после ошибки и отображение фактического ответа сервера.

Ограничение среды: Docker и Go не установлены. Сборка общего образа и end-to-end с живыми Go/Postgres/файловым хранилищем **не выполнялись**. Совместимость структуры dist сверена с текущим Dockerfile и SPA-handler, но это не замена Docker build или реальной интеграции. Локальный Node.js — 24.21.0; версия Node.js 22 в Dockerfile сохранена.

## 16. Источники истины в коде

- `backend/internal/httpapi/server.go` — зарегистрированные Go routes;
- `backend/internal/httpapi/handlers.go` — payload, статусы и лимиты;
- `backend/internal/domain/models.go` — wire-модели;
- `src/api/types.ts` — их TypeScript-представление;
- `src/api/client.ts` — transport, query, normalization и `ApiError`;
- `src/api/mocks.ts`, `src/api/demoStore.ts` — автономные сценарии;
- `src/pages/OnboardingPage.tsx` — последовательность регистрации;
- `src/auth/onboardingDraft.ts` — режим-специфичный черновик двух UI-шагов;
- `src/report.ts` — точные формулировки provenance и экспорта;
- `src/session.ts`, `src/localState.ts` — локальная изоляция;
- `vite.config.ts` — development proxy и входы сборки.

При изменении контракта нужно одновременно обновить Go-модель/handler, TypeScript-типы, клиент, тесты и этот документ.
