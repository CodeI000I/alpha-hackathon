# Python-компонента интернет-парсера

HTTP-приём заданий, PostgreSQL-хранение и механизм одного прохода исполнения.
Состояния: `queued → running → succeeded/failed`; результат сохраняется атомарно
с конечным состоянием. `202` подтверждает фиксацию задания, а не получение новости.
Добавлены ограниченный RSS/HTML-обработчик Банка России и отдельный CLI `--once`.
Интеграции Go/LangGraph ещё нет. Без запуска worker задания остаются `queued`.

## Внутренний контракт ИИ-извлечения

Первый небольшой шаг расположен отдельно от действующего CBR/RSS API:
`extraction_models.py` описывает сохранённый текст, блоки, извлечённые поля,
утверждения и цитаты; `evidence.validate_evidence(result, document)` проверяет
происхождение цитат. Это внутренние примитивы для будущего LangChain-обработчика,
не новый HTTP endpoint и не полный `NewsCandidate`.

Блок задаётся ID и диапазоном `[start, end)` в Python Unicode-строке документа.
Координаты цитаты, если заданы, абсолютные и должны лежать внутри этого блока.
Проверяются версия документа, SHA-256 его UTF-8 текста и буквальное совпадение
цитаты. Перекрывающиеся блоки допустимы; идентификаторы и ссылки проверяются.
Даты различают точное время с часовым поясом, календарный день и неизвестность.
Неизвестные данные не заменяются текущей датой или выдуманным значением.

Успешная проверка доказывает наличие цитаты в сохранённом тексте, а не истинность
утверждения или правильность смысловой связи. `incomplete_fields` сохраняет
диагностику извлечения; пустой список не доказывает полноту загрузки. Тело новости,
URL, сведения об источнике и статус полноты назначает будущая сборка результата,
а не этот ответ модели. Загрузка URL и запись нового результата в очередь
пока не подключены.

`ai_extract.extract_document(document, model, *, max_input_chars,
max_output_chars, timeout_seconds)` — асинхронная граница LangChain. Она принимает
уже настроенный доверенной серверной сборкой `BaseChatModel`, делает независимый
снимок документа, формирует системную инструкцию и отдельное сообщение с данными,
затем проверяет JSON и цитаты. Провайдер, endpoint, ключ и модель здесь не выбираются.
Тесты используют только подставную модель без сетевых запросов.

Сообщение с данными содержит исходный текст и точный текст каждого блока вместе
с его идентификатором и координатами. Инструкция требует дословные цитаты и
`null` вместо вычисления координат моделью; даты без подтверждённого часового
пояса передаются с точностью до дня. Схема и проверка принадлежности цитат остаются
строгими: невалидный ответ не исправляется автоматически.

Все три лимита обязательны. Лимит входа учитывает весь JSON-массив сообщений,
включая инструкцию и схему; это число символов, не токенов. Длинные документы
не обрезаются: адаптер возвращает `INPUT_LIMIT`. Ответ сверх лимита даёт
`OUTPUT_LIMIT`; ошибки схемы, цитат, tool calls и незавершённый ответ —
`EXTRACTION_INVALID`. Ошибки модели и ожидания дают `MODEL_UNAVAILABLE` и
`MODEL_TIMEOUT`, без исходного текста ошибки. Отмена вызывающей задачи сохраняется.

Адаптер вызывает модель один раз, без собственных retries/repair/fallback.
Ограничение токенов и повторы внутри SDK позже должна настроить серверная сборка.
Таймаут ограничивает ожидание, но не гарантирует отмены уже отправленного запроса
или его оплаты. Для вызова отключена контекстная LangSmith-трассировка;
произвольные callbacks и внутренняя телеметрия переданной модели остаются
ответственностью её доверенной конфигурации. Сервис парсера пока этот адаптер
автоматически не вызывает.

Проверки на синтетическом тексте без сети, БД и API-ключа:

```sh
parser_service/.venv/bin/python -m unittest parser_service.tests.test_extraction -v
parser_service/.venv/bin/python -m unittest parser_service.tests.test_ai_extract -v
```

Интерфейсы сверены с официальными источниками:
[LangChain models](https://docs.langchain.com/oss/python/langchain/models),
[BaseChatModel](https://reference.langchain.com/python/langchain-core/language_models/chat_models/BaseChatModel),
[tracing_context](https://reference.langchain.com/python/langsmith/run_helpers/tracing_context).

Для парсера пользователь выбрал `z-ai/glm-5.3-flash`.
`llm_client.open_extraction_model(...)` подготавливает эту модель для командного
шлюза через `ChatOpenAI`. Ключ передаётся явно как `SecretStr`; модуль не читает
локальный секрет или `.env`. Контекст требует явные `max_output_tokens` и
`timeout_seconds`, отключает SDK retries, Responses API, прокси окружения и
редиректы, а при выходе закрывает оба HTTP-клиента. Запасной адрес из инструкции
можно выбрать явно; автоматического переключения нет.

Клиент явно задаёт `reasoning_effort="high"`: у GLM-5.3-Flash пропущенный параметр
означает `max`, что в первом live-тесте исчерпало весь лимит без итогового JSON.
Это поведение описано в [официальной документации Z.ai](https://github.com/zai-org/GLM-5#note).
Повторный эксперимент использует общий предел 16 384 выходных токена (включая
рассуждения) и таймаут 180 секунд. Эти значения задаются явно в эксперименте;
фабрика клиента не подставляет их автоматически. Вариант `low` проверен отдельно:
он выдавал JSON, но нестабильно соблюдал формат дат; результаты сохранены в ноутбуке.

Перед отправкой оба HTTP-клиента пересобирают заголовки из явной конфигурации,
URL и тела запроса. Настройки `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID` и
`OPENAI_CUSTOM_HEADERS` из окружения не могут добавить заголовки или подменить
переданный ключ. Это проверяется настоящим HTTPX pipeline с `MockTransport`.

Создание клиента не вызывает модель. Проверки перехватывают HTTP-вызовы и проверяют
Chat Completions payload: выбранная GLM и `max_completion_tokens` (так библиотека
сериализует `max_tokens`). Live-запросы к выбранной модели подтверждены HTTP 200;
результаты настройки и строгой проверки сохранены в
[ноутбуке эксперимента](../experiments/parser_glm_limits_2026-10-22.ipynb).
Этот небольшой опыт не подтверждает надёжность на произвольных новостях.
Общий расход команды этот контекст не считает. Документация клиента:
[ChatOpenAI](https://docs.langchain.com/oss/python/integrations/chat/openai).

## Загрузка статического HTML в документ

`document_loader.load_document(url, policy, *, document_revision, max_output_chars)`
использует действующие CBR `SourcePolicy` и `SafeFetcher`: проверяет разрешения,
robots.txt, интервалы, MIME, суммарные байты и время. Ошибка robots, включая 403/404,
останавливает загрузку страницы. Допускается только UTF-8; объявленный иной charset
отклоняется транспортом до возврата тела. Редиректы и подзапросы не добавлены.
Вызов синхронный; его будущий исполнитель должен сериализовать обращения к источнику,
как существующий worker с source lock. Интервалы здесь учитываются внутри вызова.

`html_document.clean_html(...)` очищает полученную HTML-строку без CSS-селекторов
конкретного сайта. Выбирается одна область `article` или `main`; fallback и
повреждённая структура отмечаются в `incomplete_fields`. Сохраняются текст абзацев,
таблиц, дат, сносок и видимый текст ссылок, затем создаются стабильные блоки с
точными координатами. URL ссылок/вложения пока не извлекаются. Это консервативное
текстовое представление, без браузера и гарантии полноты либо распознавания любой
страницы ошибки. Превышение лимита завершает обработку отказом, без усечения.

Загрузчик возвращает документ, URL, время получения, версию политики и признаки
неполноты. При будущей сборке общего результата эти признаки нужно объединить
с диагностикой извлечения; `extract_document` не переносит их автоматически.
Проверки выполняются на искусственном HTML, fake fetcher/clock и подставной LLM:

```sh
parser_service/.venv/bin/python -m unittest parser_service.tests.test_html_document parser_service.tests.test_document_loader -v
```

Разбор опирается на стандартные
[HTMLParser](https://docs.python.org/3.13/library/html.parser.html) и
[RobotFileParser](https://docs.python.org/3.13/library/urllib.robotparser.html).

Обязательные переменные окружения:

## Миграция и запуск

Администратор подготавливает отдельные учётные записи для миграций и runtime.
В существующей БД схема `parser` принадлежит учётной записи миграций.
HTTP API достаточно `CONNECT` к БД, `USAGE` на схему `parser` и `SELECT, INSERT`
на `parser.jobs`. Отдельному исполнителю нужны `SELECT, UPDATE` на эту таблицу.
Не выдавайте runtime-учётным записям права на таблицы backend, DDL или DELETE.
Секреты и роли в этом изменении не создаются автоматически.

Явно выберите DSN миграций через `PARSER_DATABASE_URL` и выполните:

```sh
parser_service/.venv/bin/python -m parser_service.migrate
```

Первая миграция сохранена без изменений и используется как повторяемый bootstrap.
Следующие миграции учитываются в `parser.schema_migrations`: каждый файл и запись
о нём фиксируются одной транзакцией, повторно он не применяется. Одновременные
миграторы сериализуются session advisory lock, который освобождается при закрытии
соединения. Проверка произвольной заранее созданной несовместимой схемы не реализована.
После миграции переключите `PARSER_DATABASE_URL` на runtime-учётную запись:

```sh
parser_service/.venv/bin/python -m uvicorn parser_service.api:create_app --factory --host 127.0.0.1 --port 8091 --no-access-log
```

Создание API не запускает миграции и не соединяется с БД. Доступность БД проверяется
при операции. Для размещения за пределами loopback нужны отдельные настройки
TLS/сети и входных таймаутов; способ развёртывания ещё не согласован.

## HTTP-контракт

Все операции требуют `Authorization: Bearer <PARSER_API_TOKEN>`.
На вход `POST /v1/jobs` передайте JSON с пятью обязательными полями:

```json
{"job_id":"example-1","mode":"discover","source_id":"cbr_press","requested_level":"content","policy_version":"cbr-v1"}
```

Это пример формы, а не утверждённая политика доступа к ЦБ. `job_id` и
`policy_version` — 1–128 ASCII-символов: первая буква/цифра, далее также `_.-`.
Дополнительные поля запрещены; `fetch`, `refresh`, `search` пока не принимаются.

| Операция | Ответ |
| --- | --- |
| `POST /v1/jobs` | `202`: ID, актуальное состояние, время создания/обновления, ссылки на состояние и результат |
| `GET /v1/jobs/{job_id}` | `200`: та же публичная форма; для `failed` также безопасная `error`; неизвестное — `404` |
| `GET /v1/jobs/{job_id}/result` | `200` и сохранённый снимок при `succeeded`; `409 RESULT_NOT_READY` при `queued/running`; `409 JOB_FAILED` при `failed`; неизвестное — `404` |

Одинаковый `job_id` с тем же JSON, включая иной порядок ключей, возвращает
существующее задание без изменения времени. С другим запросом — `409 JOB_CONFLICT`.
Новый ID означает новое намерение; при сетевом сбое клиент повторяет прежний ID.
Повторный POST завершённого задания возвращает его текущее состояние и не запускает
обработку повторно. Lease-токены, исходный запрос и внутренние поля БД API не выдаёт.

Ошибки: `{"error":{"code":"...","message":"...","retryable":false}}`.
`401 UNAUTHORIZED`, `413 REQUEST_TOO_LARGE`, `422 INVALID_REQUEST`,
`404 JOB_NOT_FOUND`, `409 JOB_CONFLICT`, `409 RESULT_NOT_READY`,
`409 JOB_FAILED`, `503 STORAGE_UNAVAILABLE`. NOT_READY и STORAGE_UNAVAILABLE имеют
`retryable=true`; сообщение не является машинным контрактом. Некорректные маршруты
и методы получают тот же формат с `HTTP_ERROR`.
Доступ и размер потока проверяются до JSON-декодирования и обращения к БД.

## Один проход исполнения

`executor.execute_once(repository, handler, *, lease_seconds, max_attempts, max_items)`
обрабатывает максимум одно задание; если подходящих нет — возвращает `None`.
Все три ограничения обязательны и принимают только положительные целые числа.
Числа в тестах не являются рабочими лимитами. Функция не запускается автоматически
внутри API и не добавляет расписание: оно остаётся ответственностью Go worker.

Обработчик получает копию сохранённого запроса и возвращает JSON-совместимый объект
`{job_id, result_status: complete|partial, items: [...], incomplete_fields?: [...]}`.
Схемы item, даты, происхождения и вложений определены в `result_models.py`.
Материалы результата — снимок конкретного задания; `material_id/version_id`,
глобальная дедупликация и история изменений ещё не реализованы.

Захват использует `FOR UPDATE SKIP LOCKED`, новый UUID lease и время PostgreSQL.
Действующий lease не перехватывается; просроченный допускает новую попытку.
`finish` сначала блокирует строку, затем проверяет состояние, токен и срок lease.
Устаревший обработчик получает `LeaseLost` и не меняет результат. Исчерпание попыток
сохраняет `ATTEMPTS_EXHAUSTED` без нового вызова обработчика. Exactly-once не обещается.

`KeyboardInterrupt` и другие `BaseException` оставляют работу восстанавливаемой
после lease; неизвестное обычное исключение сохраняется как безопасный
`PROCESSING_FAILED`. `ProcessingError` различает `FEED_UNAVAILABLE` и `FEED_INVALID`.
Обработанные ошибки терминальны; `retryable` описывает характер ошибки и не запускает
автоматически новое задание. Ошибки БД и потеря lease не маскируются вторым `finish`.

Lease защищает сохранение и не продлевается heartbeat. Сетевой клиент ЦБ
выполняет каждый GET в отдельном процессе с deadline, включая DNS. Вход разбора
ограничен байтами; budget проверяется между стадиями, жёсткой отмены CPU-разбора нет.

Ограничение `max_items` усекает список результата и помечает его `partial` с
`incomplete_fields=["items"]`; оно не ограничивает память/сеть внутри обработчика.
Сетевой адаптер ЦБ отдельно ограничивает HTTP до разбора и получения HTML. Неполные item не теряются и делают
проход `partial`; `succeeded` означает завершение прохода, а не полноту всех данных.
Нет времени получения — остаётся `fetched_at=null` с признаком неполноты.
Известен только день публикации — используется `published_date` без выдуманного
времени; неизвестны обе даты — они остаются `null`. `published_at_source` может
указывать проверенное поле источника даже при нераспознанной дате. PDF-вложения
передаются как ссылки; функция их не скачивает и не открывает.

## Проверки

Для интеграционных тестов нужен отдельный PostgreSQL с БД `kib_parser_test`.
Задайте `PARSER_TEST_DATABASE_URL` с явным loopback host. Тесты не используют
`PARSER_DATABASE_URL`/`DATABASE_URL`, применяют миграцию только к тестовой БД
и удаляют только собственные записи и созданные ими тестовые триггеры/функции.
Нужна тестовая учётная запись с DDL-правами; runtime-приложению они не нужны.

```sh
parser_service/.venv/bin/python -m unittest discover -s parser_service/tests -v
```

Без `PARSER_TEST_DATABASE_URL` DB-тесты явно пропускаются; такой прогон
не подтверждает PostgreSQL, конкурентные повторы или сохранность после перезапуска.
Рабочую БД для проверок не используйте.

Проверено 21 октября 2026: 19 тестов без пропусков на PostgreSQL 16.15 и Python
3.13.15, включая искусственный сбой COMMIT, отсутствие строки и закрытие соединения.
Отдельно выполнена HTTP-проверка настоящего Uvicorn с остановкой/запуском процесса:
задание сохранилось; runtime с SELECT/INSERT работал, UPDATE/DELETE были запрещены.
Мигратор, `compileall`, установка с constraints в чистое окружение и `pip check`
прошли. Это результаты первого шага.

После добавления исполнения: **39 тестов без пропусков**, включая захват двумя
исполнителями, crash/reclaim, исчерпание попыток, отказ устаревшему владельцу,
истечение lease во время ожидания row lock, ошибку COMMIT при finish и закрытие
соединения. В отдельной проверке настоящий Uvicorn принял задание, отдельный процесс
с тестовым callback сохранил снимок, API выдал его и сохранил тот же результат после
перезапуска. Раздельные тестовые роли проверены: API не может UPDATE, worker —
INSERT/DELETE. Повторный вызов мигратора сообщил `already current`.

## Ограниченный worker ЦБ

`python -m parser_service.worker --once` исполняет максимум одно задание; встроенного
расписания нет. CLI требует DB-настройки, `PARSER_LEASE_SECONDS`,
`PARSER_MAX_ATTEMPTS` и все `PARSER_CBR_*` из `.env.example`. `PARSER_API_TOKEN`
и размер входящего API-запроса нужны API, но не worker. CLI не запускает миграции.
Версия policy обязана совпасть с запросом. `ALLOW_FETCH` и `ALLOW_PERSIST`
задаются явно `true`/`false`; отказ или несовпадение не разрешают сеть.

Согласованный профиль для ограниченного некоммерческого прототипа хакатона:

| Переменная с префиксом `PARSER_CBR_` | Значение |
| --- | --- |
| `POLICY_VERSION` | `cbr-prototype-v1` |
| `ALLOW_FETCH`, `ALLOW_PERSIST` | `true` |
| `MAX_ITEMS` | `3` |
| `MAX_RESPONSE_BYTES` | `1048576` |
| `MAX_TOTAL_BYTES` | `4194304` |
| `REQUEST_TIMEOUT_SECONDS` | `10` |
| `JOB_TIMEOUT_SECONDS` | `45` |
| `MIN_INTERVAL_SECONDS` | `1` |
| `USER_AGENT` | `KIBNewsPrototype/0.1` |

Отдельно `PARSER_LEASE_SECONDS=90`, `PARSER_MAX_ATTEMPTS=2`. Это явно включаемый
проверочный профиль, не defaults или производственные SLA. Lease должен превышать
budget задания. Разрешения относятся к выбранному прототипу, не к коммерческому запуску.

Перед захватом worker удерживает session advisory lock источника на autocommit
соединении. Занятый источник даёт `no_job_or_source_busy`, без claim задания.
Каждый GET предваряется паузой, включая первый. Учитываются crawl-delay/request-rate
из robots. Сбой robots закрывает доступ; RSS-ошибка завершает задание, ошибка
отдельной статьи сохраняется в item. CLI выводит только job_id/status либо безопасный
класс ошибки; код выхода 0 — исполнено/нет задания, 1 — задание failed, 2 — config/БД/lease.

Сеть: только HTTPS www.cbr.ru:443, фиксированные robots/RSS и `/press/` страницы;
query статьи сохраняется. IP/DNS проверяются до соединения, IP закреплён, TLS
проверяет исходный hostname. Нет redirect, proxy, автоматических повторов,
распаковки Content-Encoding или скачивания PDF. Все DNS-адреса должны быть публичными.
Байтовые лимиты относятся к телам HTTP, не к TLS/заголовкам. При неизвестной длине
тело ровно на границе cap принимается только после проверки EOF чтением одного
дополнительного байта; cap+1 отклоняется. Дочерний процесс ограничивает время этой проверки.
Таймаут дочернего процесса консервативно расходует весь cap запроса.

RSS/HTML ожидаются UTF-8; DTD/entities отвергаются. `.landing-text` — единственная
граница полного тела; описание RSS им не подменяется. Повреждённая/неизвестная
структура даёт partial/unavailable. `full` означает прохождение узкой структурной
проверки, не гарантию смысловой полноты. Дата RSS с timezone приоритетна, иначе
календарный день HTML, иначе unknown. PDF — только разрешённые ссылки из статьи;
nofollow исключает их. Raw RSS/HTML не сохраняются. В БД сохраняется снимок результата
задания; retention, канонические версии материалов и дополнительные источники ещё
не реализованы. Текущий код ЦБ не является универсальным браузерным исследователем.

Проверка сетевого шага 22 октября: 64 теста без пропусков на временной PostgreSQL,
включая source lock, искусственные RSS/HTML, HTTP-ошибки и timeout дочернего процесса.
Live POST → отдельный worker → GET выполнен с раздельными ограниченными ролями:
`failed/FEED_UNAVAILABLE`, result HTTP 409. Диагностический GET robots тем же клиентом
вернул HTTP 403/ACCESS_DENIED. Запрет не обходился. Успешное получение реальных
новостей этим шагом **не подтверждено**; ни raw HTML, ни реальные fixtures в Git
не добавлены. Старое утверждение выше об отсутствии сетевого покрытия относится
только к результатам первых двух шагов.

Финальный повторный прогон: **68 тестов без пропусков**, включая настоящий stdlib
HTTPResponse на искусственных HTTP-байтах (Connection: close/chunked), безопасное
отображение ошибки сертификата, timeout чтения/закрытие сокета и завершение зависшего
дочернего процесса. `compileall` и `pip check` прошли. Созданный для проверки
PostgreSQL-контейнер с tmpfs остановлен и удалён; рабочая БД не использовалась.
Блок остаётся открытым до явного решения пользователя.
