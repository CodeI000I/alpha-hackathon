# Качество ответов аналитического агента

25 октября 2026. Изменения относятся к действующему `AnalyticsService`.
Работа выполнена с Ponytail и Agent Skills, с отдельными агентами для проверки
графа и общего LLM-клиента. Производственная система и реальные LLM не вызывались.

## Что уже было

Рабочий граф: `retrieve → triage → assess → save`; triage опционален и служит
подсказкой. PostgreSQL хранит бизнес-данные и checkpoint состояния графа.
Диалог закреплён за версией ситуации, в запрос передаются последние шесть ответов.
Схемы Pydantic, таймауты, ограниченные повторы транспорта, кеш и учёт бюджета уже
реализованы. Отдельный JSON parser или вторая система памяти здесь не нужны.

В проверенной локальной конфигурации все роли используют
`deepseek/deepseek-v4.1-flash`. Есть overrides `AI_DECISION_MODEL`,
`AI_ANALYSIS_MODEL`, `AI_SYNTHESIS_MODEL`, `AI_CHAT_MODEL`; настройки работающего
кластера не проверялись. Модель и зависимости в этой задаче не менялись.

## Исправления

| Пробел | Новое поведение |
|---|---|
| Чат принимал ответ без ссылок и без признания пробела | Новый ответ требует допустимые `evidence_ids` либо непустое описание `missing_facts`; нарушение не сохраняется |
| Влияние публиковалось без объяснения связи | `causal_chain` должен ссылаться на новость и выбранное основание компании; иначе `needs_context` |
| Ссылка на путь позволяла обойти статус исходного факта | Проверяется также факт, связанный с chunk выбранного пути: конфликт, неподтверждённость и срок применимости |
| Обрезанный поиск позволял уверенное «не влияет» | Отрицательные и нейтральные оценки при `context_truncated` требуют дополнительного контекста |
| Уже включённые через факт/путь чанки считались потерянными | Флаг неполноты сравнивает кандидатов со всеми включёнными чанками |
| Полученный JSON считался успешным до проверки схемы/оснований | `calls.status=ok` записывается после валидации; ошибка и использованные токены сохраняются |
| Прерывание валидатора теряло полученный usage | `cancelled` сохраняет usage; исходное прерывание распространяется дальше |

Изменены prompts и версия grounding/retrieval в policy digest, поэтому прежние
impacts не считаются свежими по новой политике. История и закреплённые диалоги
сохраняются. Новых платных повторов при ошибке валидации нет.

## Диагностика

В runtime включён отдельный JSON logger `orchestrator.quality`. Он пишет:

- `graph_node`: `run_id`, policy, node, span IDs, длительность, исход и код ошибки;
- `llm_structured`: stage, model, schema, cache hit, validation outcome, код ошибки
  и длительность; внутри графа добавляются те же `run_id`, policy и node.

В сохранённой записи `run` есть маршрут, количество evidence и causal claims,
признак обрезанного контекста; при ошибке — узел либо фаза checkpoint/synthesis.
Логи не содержат prompts, документов, ответов, исключений целиком или ключей API.
Cache hits отражаются в логах, но не увеличивают счётчик платных запросов.

Langfuse/LangSmith не подключались к внешнему хранилищу. Сначала достаточно этих
диагностических событий; включать автоматический экспорт корпоративных текстов
ради отладки не требуется. Использованы штатные callbacks LangGraph и стандартный
Python logging, новых зависимостей нет. Документация:
[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence),
[LangSmith observability](https://docs.langchain.com/langsmith/observability),
[Langfuse integration](https://langfuse.com/integrations/frameworks/langchain).

## Повторяемая проверка

```bash
.venv/bin/python -m orchestrator.analytics.quality_eval
```

Корпус: `orchestrator/analytics/evals/answer-quality.json`. Используются настоящие
retriever, StateGraph, LLMClient и валидаторы. HTTP-ответы подставляет существующий
`SyntheticGateway` через `httpx.MockTransport`; файлы и память временные, `.env`
не читается. Ненулевой exit code означает нарушение ожидаемого маршрута, лимита
вызовов либо правил публикации. Тест корпуса входит в обычный analytics suite/CI.

16 сценариев включают плавающую/фиксированную цену, нехватку сведений, отмену и
истечение события, конфликт фактов, пустое обоснование, чужую ссылку, неправильную
схему, неполный поиск, mixed impact и четыре варианта ответа чата.

При подстановке прежних правил публикации из `6cd0ca6` тот же корпус нарушал
ожидания в **5 из 16** сценариев. Текущие правила проходят **16 из 16**. В обоих
прогонах — 48 синтетических HTTP-вызовов, дополнительных вызовов не добавлено.
Это сравнение правил публикации, а не измерение точности или стоимости LLM;
ответы и token usage в этом корпусе синтетические.

Полная проверка: **404 Python-теста прошли без пропусков** — 128 core, 151 analytics,
125 parser. Использовалась отдельная PostgreSQL 17.11 + pgvector 0.8.7 на loopback,
включая настоящее восстановление LangGraph после сбоя. `pip check`, компиляция
Python и `git diff --check` проходят. Frontend/Go, Docker и кластер не изменялись
и в этой проверке не запускались.

## Ограничение и следующий критерий

Допустимый ID источника не доказывает, что текст вывода действительно им
подтверждается. Эти проверки закрывают конкретные обходы, но не исключают все
галлюцинации. Для оценки смысловой точности нужен размеченный набор реальных
вопросов/ответов и отдельный прогон выбранных моделей с явным бюджетом.

Поэтому универсальный planner, LLM-критик и автоматический self-repair пока не
добавлены. Их стоит вводить после измерения исправляемых ошибок на одном корпусе
с пределом повторов и сравнением качества/стоимости. HITL потребуется при появлении
инструментов, отправляющих сообщения или изменяющих внешние данные; текущий
аналитический ответ таких действий не выполняет.
