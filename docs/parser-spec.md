# Интернет-парсер: проект спецификации

Дата исходной спецификации: 21 октября 2026 года. Статус на 23 октября: приём/чтение заданий, устойчивое исполнение и ограниченный RSS/HTML-обработчик ЦБ реализованы. Есть отдельные примитивы загрузки документа и ИИ-извлечения с проверкой цитат; они тестируются на временных компонентах. Глобальные версии материалов и интеграции с Go/аналитическим router ещё не подключены. Успешная загрузка живого ЦБ не подтверждена: последний описанный live-прогон получил отказ доступа. Подробности: [parser_service/README.md](../parser_service/README.md). Блок пользователем не закрыт.

Основания: предоставленное пользователем «Техническое исследование интернет-парсера…» от 20 октября; текущий код `backend/internal/ingest/`, worker и PostgreSQL storage, прочитанные без выполнения. Ссылки вида `turn…` в исследовании не являются доступными библиографическими ссылками; актуальные endpoints, условия источников и совместимость библиотек перед интеграцией требуют отдельной проверки. План работ находится только в `harness/plan.md`.

## Актуальное решение пользователя

Парсер реализуется отдельной компонентой с подключением к LangGraph и Go-бэкенду. Прежнее предложение встроить парсер в Go-backend отклонено. Пользователь поручил реализацию с субагентами `gpt-5.6-sol`, reasoning `low`. Фактический запуск помощника с этими параметрами принят инструментом в текущем чате; помощник прочитал контекст и код, передал разбор контракта, файлов не менял и код не запускал. Прежнее заключение о недоступности модели по перечню инструмента не подтверждается этим запуском. Каждый пишущий код помощник использует Agent Skills и Ponytail. Главная модель проверяет правки и результаты; агентам разрешены самостоятельные запуски кода и тестов для этой работы.

В текущем чате пользователь последовательно согласовал:

- Python для отдельного парсера.
- Внутренний HTTP API с JSON: отправка задания и отдельное получение его состояния/результата.
- Парсер владеет заданиями, результатами извлечения, материалами и их версиями. Go-бэкенд владеет пользовательскими данными и ссылками на версии; LangGraph запрашивает обработку и использует результаты.
- Go worker управляет расписанием фонового сбора. LangGraph инициирует адресные запросы. Интервалы отдельно не выбраны.
- Первый источник — RSS пресс-релизов Банка России и HTML публикаций; PDF-вложения передаются ссылками. Актуальный доступ и условия использования нужно проверить перед сетевой интеграцией.
- Хранение парсера — отдельная схема `parser` в существующем PostgreSQL, собственные миграции и учётная запись. Backend и LangGraph получают данные парсера через HTTP.

Предоставленное исследование сохранено в `docs/internet-parser-research-2026-10-20.md`. Остальные положения ниже — требования и предложения для уточнения контракта, не полное согласование спецификации. Верхние разделы `harness/plan.md`, `harness/state.md` и AGENTS.md пока содержат прежние открытые решения и прежнюю оценку доступности помощников; эти файлы в данной работе не обновляются без процедуры harness. Решения текущего чата имеют приоритет.

- Затем подключаем Pravo, regulation.gov.ru и Росстат по одному после проверки доступа и нужности для демо. Это кандидаты, не утверждённый список.

## Цель и границы

Доставлять общий повторно используемый материал с текстом, метаданными, происхождением, версией и явными ограничениями полноты. Один материал используется для нескольких компаний без повторной сетевой загрузки на каждую компанию.

Включено: фоновое обнаружение, получение текста по запросу, безопасный HTTP, нормализация, точные дубли, версии, ограниченный адресный поиск, диагностируемые ошибки.

Исключено: персонализация, оценка бизнес-влияния, отчёты, чат, frontend, PDF parsing, универсальный crawler, браузер и новый брокер. Вложения представлены ссылками и типом; подключение обработчика сокомандника обсуждается отдельно. Python-компонента утверждена; способ развёртывания ещё не выбран.

## Границы возможностей и зависимости

Это логические части отдельной Python-компоненты. Владение материалами и заданиями согласовано выше; детали таблиц и развёртывания ещё обсуждаются.

| ID | Ответственность | Зависимость |
| --- | --- | --- |
| source-policy | Источники, разрешённые действия и лимиты | — |
| safe-fetch | Проверка URL, HTTP и ограничения | source-policy |
| material-store | Идентичность материала, версии и состояние работы | source-policy |
| source-ingest | RSS/API и извлечение текста, сквозной проход | safe-fetch, material-store |
| targeted-search | Получение URL по конкретному пробелу | source-ingest |

Порядок: один сквозной поток ЦБ через минимальные policy/fetch/storage → корректные повторы и версии → дополнительные источники → поиск. Общие абстракции появляются только при втором реальном потребителе.

## Предлагаемые входы

Внутренний запрос: `job_id`, `mode` (`discover`, `fetch`, `refresh`, `search`), `source_id` либо URL, `requested_level` (`metadata`, `content`), причина, ссылка на версию policy. Для search — конкретный `search_goal`, допустимые темы и бюджет запросов/результатов/документов/байтов/времени.

`job_id` стабилен при повторе; тот же ID с другим запросом — ошибка. Конкурирующий повтор получает состояние выполняющейся работы. После сбоя разрешён безопасный повтор; получение материала и доставка результата потребителю учитываются раздельно.

Парсер не получает полный профиль компании. В поисковый API уходят только явно допустимые темы/формулировки. Для неизвестного домена требуется разрешающая политика: поисковая выдача сама по себе ничего не разрешает.

## Предлагаемый результат

| Группа | Поля и смысл |
| --- | --- |
| Идентичность | `material_id`, `version_id`, `source_id`, `external_id?`, исходный и нормализованный URL |
| Метаданные | Заголовок, описание, язык/категории при наличии |
| Даты | `published_at?`, `modified_at?`, `first_seen_at`, `last_seen_at`, `fetched_at?`; источник и точность даты |
| Содержание | `content_text?`, `content_status`, `extraction_method`, `content_hash?`, ссылки на вложения |
| Происхождение | Способ обнаружения, feed либо search query/job, policy version |
| HTTP | Статус, MIME, ETag, Last-Modified при наличии |
| Версии | Предыдущая версия, причина изменения; старое основание не перезаписывается |
| Ограничения | `error_code?`, `incomplete_fields`, возможность повтора и причина остановки |

`content_status`: `full`, `partial`, `metadata_only`, `unavailable`. `full` означает выполненные проверки конкретного адаптера, а не доказанную универсальным extractor полноту любой страницы.

Отдельный результат search: ссылки на полученные материалы, `ok` / `no_hits` / `incomplete` / `access_error`, недостающие сведения, потраченный бюджет и `stop_reason`. Поисковый snippet не считается загруженным телом или подтверждённым фактом.

Даты события и вступления в силу не выводятся из даты публикации. В первом шаге они не извлекаются семантически. Неизвестная дата остаётся неизвестной; текущее время не заменяет её. Совместимость с текущим обязательным `NewsItem.PublishedAt` — отдельная часть миграции.

## Логика обработки

1. Проверить источник, права на действие, URL и конфигурацию лимитов.
2. Обнаружить RSS/API items; сохранить метаданные и происхождение. Не удалять значимые query-параметры. Canonical из HTML — подсказка, не доверенная переадресация.
3. Найти существующий материал по source/external ID и нормализованному URL. Сохранить повторное обнаружение; оно не доказывает неизменность содержания.
4. По policy `metadata_only`, `fetch_on_demand` или `prefetch_body` решить, нужен ли разрешённый fetch. Разрешение на получение и на постоянное хранение тела учитываются раздельно.
5. Получить ресурс через общий HTTP-слой, включая RSS и redirects. При refresh использовать validators; 304 без ранее сохранённого представления не считается готовым результатом.
6. Извлечь текст правилами источника; универсальный extractor добавить только после выявления необходимости. Пустой текст, страница ошибки, teaser и неподдерживаемый attachment не превращаются в полный материал.
7. При изменении нормализованного текста или существенных метаданных сохранить новую версию. Сетевые изменения ETag сами по себе не создают смысловую версию. Правило хеширования и его версия фиксируются в реализации.
8. Надёжно зафиксировать доступность новой версии для потребителя. Повтор обработки не создаёт дубликат, а сбой после сохранения не теряет доставку навсегда. Механизм на PostgreSQL уточнить перед интеграцией; брокер не предполагается.

Одинаковое содержание разных издателей не удаляет происхождение. Семантические перепечатки и одинаковая тема не схлопываются автоматически.

## Безопасность и восстановление

- Только HTTP(S), проверка resolved IP при фактическом соединении и на каждом redirect; запрет локальных, private, link-local и служебных диапазонов IPv4/IPv6. Не допускать обхода повторным DNS-разрешением или неконтролируемым proxy.
- TLS с проверкой сертификатов; ограничения времени, redirect, тела и распакованных байтов. MIME проверяется до передачи extractor.
- Политика частоты на домен/источник, ограниченные retries для временных ошибок с учётом Retry-After. 403 — отдельная диагностика доступа, без бесконечных повторов и обхода ограничений.
- Отмена контекста останавливает HTTP, ожидание и повтор. robots и условия использования учитываются раздельно; robots не является лицензией.
- Никакого исполнения JS/команд/инструкций из материалов. Секреты и чувствительные темы не пишутся в логи.
- Курсор и повторный просмотр с overlap применяются по возможностям источника. Отсутствие архива фиксируется как пробел покрытия: RSS не гарантирует восстановление всей истории.
- Сроки хранения тела/версий согласуются отдельно. Пока не согласованы — нет автоматического удаления оснований отчёта и нет предположения о бессрочном хранении полного текста.

Существующие точки: `backend/internal/ingest/`, `backend/internal/storage/postgres/`, `backend/internal/domain/`, `backend/cmd/worker/`, `backend/migrations/`. Новые тесты — рядом с кодом; fixtures — в `testdata/`.

Существующий worker — согласованный владелец расписания фонового сбора и будущий клиент парсера. Протокол HTTP/JSON выбран; endpoints первого шага приведены ниже. Компонента и её проверки размещены в `parser_service/`, отдельно от `orchestrator/`.

Статическое чтение кода в текущем чате подтвердило препятствия интеграции: `Fetcher` синхронно возвращает `[]NewsItem`; worker сам загружает RSS; `news_items` хранит тело и требует дату публикации; RSSFetcher заменяет ошибочную дату текущим временем; UpsertNews обновляет только заголовок, а повторный материал не передаётся дальше. Это не результаты выполнения. Миграция backend и подключение LangGraph остаются отдельными шагами действующего плана.

## Первый небольшой шаг — согласован, реализован, ожидает подтверждения пользователя

Пользователь согласовал описанный шаг и стек после чтения предложения. Реализованы приём и чтение заданий через HTTP с хранением в `parser.jobs`. Задания сохраняются в состоянии `queued`; загрузка ЦБ и исполнитель заданий требуют следующего согласованного изменения. Принятое задание не выдаётся за выполненный парсинг.

Операции первого шага:

| Операция | Вход | Выход |
| --- | --- | --- |
| `POST /v1/jobs` | `job_id`, `mode=discover`, `source_id=cbr_press`, `requested_level=content`, `policy_version` | `202`: `job_id`, `status=queued`, ссылки на состояние и результат |
| `GET /v1/jobs/{job_id}` | ID задания | `200`: ID, состояние, время создания/обновления, структурированная ошибка при наличии; `404` для неизвестного ID |
| `GET /v1/jobs/{job_id}/result` | ID задания | Результат только после успешного выполнения; пока он не готов — `409` с явным кодом; неизвестный ID — `404` |

Пути и значение `cbr_press` приняты в составе первого шага. На этом шаге допустимо только `queued`, это ограничение закреплено CHECK в БД; фиктивного успешного обработчика нет. Перечень состояний для полного исполнения (`queued`, `running`, `succeeded`, `failed`) и правила захвата, восстановления и повторов `running` согласуются перед добавлением исполнителя. `policy_version` сейчас сохраняется как ссылка запроса, не доказывает наличие реализованной source policy и не разрешает сетевой доступ.

Одинаковый `job_id` с тем же нормализованным валидированным запросом возвращает существующее задание; с другим запросом — `409`. Уникальность обеспечивает PostgreSQL одной атомарной операцией. Повтор не перезаписывает состояние или результат. Ошибки имеют общую форму `error: {code, message, retryable}`; неверный запрос — `422`, недоступная БД — `503`. Ответ `202` выдаётся только после фиксации задания в БД. После перезапуска API сохранённое `queued` доступно для чтения; автоматическое возобновление выполнения этим шагом ещё не подтверждается.

Согласованный стек: FastAPI, Uvicorn, Psycopg 3; без ORM. Проверены Python 3.13.15, FastAPI 0.156.8, Uvicorn 0.54.0, Psycopg/binary 3.3.6, HTTPX 0.28.1 для тестов и PostgreSQL 16.15. Прямые версии записаны в `parser_service/requirements*.txt`, фактические транзитивные — в `constraints.txt`. Установка с constraints в новое временное окружение и `pip check` прошли. Это подтверждает проверенную комбинацию, не все версии Python/ОС. Официальные документы, прочитанные в текущем чате: https://fastapi.tiangolo.com/tutorial/testing/, https://uvicorn.dev/, https://www.psycopg.org/psycopg3/docs/basic/transactions.html, https://www.postgresql.org/docs/16/sql-insert.html.

Конфигурация явно требует DSN, сервисный Bearer token, предел тела HTTP-запроса и таймауты подключения/SQL; значения по умолчанию не заданы. Токен проверяется до чтения тела, размер ограничивается по фактическим байтам потока, включая запрос без Content-Length. Команда запуска в README привязана к loopback. Это граница локального шага, не утверждённое развёртывание/TLS/сетевая политика. Сетевых запросов к ЦБ не было. DB-проверки выполнены в отдельной БД `kib_parser_test` временного контейнера PostgreSQL с tmpfs и случайным loopback-портом; рабочая БД и её роли/миграции не менялись.

Разделение файлов: основная модель написала API, конфигурацию, SQL-миграцию, команду миграции, зависимости и документацию; помощник `parser_contract` — только `repository.py`; помощник `parser_tests` — только `tests/test_jobs.py` и `tests/test_api.py`. Помощник `parser_review` провёл независимое статическое ревью без правок. Все помощники запущены с запрошенными `gpt-5.6-sol`, reasoning `low`, применяли Agent Skills и Ponytail. Главная модель прочитала фактические изменения и сама выполнила итоговые проверки.

Подтверждённые проверки: 19 unittest-тестов прошли без пропусков на реальном PostgreSQL. Проверены одинаковые/конкурентные submit, конфликт payload, сохранность при пересоздании API, неверные запросы, auth/size boundary, ошибки БД, неизвестный и незавершённый результат. Deferred constraint trigger воспроизводит ошибку COMMIT: API возвращает 503, записи нет, реальное соединение закрыто. Тест выявил утечку в исходном использовании Psycopg context manager; внешний finally с close её исправил. Главная модель повторила suite с `-W error::ResourceWarning`, все 19 тестов прошли.

Отдельная HTTP-проверка через настоящий Uvicorn подтвердила auth, submit, повтор, конфликт, чтение того же задания после остановки и повторного запуска процесса, а также NOT_READY. Для неё создана только тестовая runtime-учётная запись: SELECT/INSERT разрешены, UPDATE/DELETE фактически отвергнуты. Явная команда `python -m parser_service.migrate` успешно выполнена только на тестовой БД. `compileall` прошёл. Сохранено известное предупреждение Starlette 1.9.0 об устаревании HTTPX в TestClient; оно не подавлялось и не относится к runtime API.

Эти результаты подтверждают только приём и хранение заданий. Исполнение, source-policy, безопасная загрузка, текст/даты ЦБ, версии материалов и Go/LangGraph-интеграции не проверены этим шагом. Коммита, push и закрытия блока не было.

Go: явные ошибки, `context.Context`, стандартный `testing`/`httptest`, небольшие функции и конкретные структуры. Пример уже существующего стиля: `Fetch(ctx context.Context, src postgres.SourceConfig) ([]domain.NewsItem, error)`. Это пример стиля, не утверждение достаточности старого интерфейса для нового контракта.

## Проверки и критерии приёмки

Агент и помощники могут подготавливать и самостоятельно выполнять код и тесты для парсера и интеграций по прямому разрешению пользователя от 21 октября. Результат подтверждается фактическим выводом запуска; блок закрывается только явным решением пользователя.

- Повтор feed/job, tracking-вариант URL и конкурентное сохранение не создают лишний материал/версию. Исправленная статья сохраняет прежнюю версию; 304 не создаёт новую.
- Отсутствующая/некорректная дата не превращается в текущую; точность до дня не выдаётся за точное время.
- Запрещённое получение тела не выполняет запрос; запрещённое хранение не сохраняет body. Результат содержит причину ограничения.
- Redirect на private IP, DNS rebinding, oversized/сжатый body и неподдерживаемый MIME отвергаются. Тесты не используют реальные внутренние endpoints.
- На fixtures выбранного источника извлекаются ожидаемые заголовок, дата, текст и ссылки; partial/ошибка не считаются успехом.
- Сбой до/после сохранения и рестарт не теряют дальнейшую обработку; повтор не удваивает доставку.
- Поиск ограничивается заданным бюджетом, не выдаёт access error за no_hits и передаёт URL в тот же pipeline. Без credentials сетевой search отключён явно.
- Пользовательский pilot на согласованном корпусе фиксирует пропуски discovery, качество текста, даты, дубли, задержки, ошибки и расход поиска. Численные цели выбираются по требованиям демо и наблюдениям, не выдумываются заранее.

Предварительные команды для Go-части из каталога `backend` после подготовки соответствующего кода (их может запускать агент). Команды Python-парсера будут определены вместе с окружением и файлами проверок:

```sh
go test ./internal/ingest/... -count=1
go test ./internal/storage/postgres/... -count=1
go test ./... -count=1
go build ./cmd/worker ./cmd/server
```

DB integration-проверки потребуют отдельной тестовой БД и уточнённой команды; обычный запуск тестов не должен менять рабочую БД. Команды здесь не выполнялись.

## Правила изменения объёма

Всегда: сохранять provenance и ошибки, минимально расширять существующий код, перед кодом согласовать ближайший шаг. Перед реализацией применить Ponytail.

Согласовать до изменения: зависимости и pins, миграции, публичный контракт, источники, поисковый provider, лимиты и retention. Граница отдельной компоненты утверждена; дополнительные сервисы, браузер и LLM не добавляются по инициативе агента.

Нельзя: выходить за разрешённый scope запусков, обходить доступ, выдумывать даты/факты/метрики, считать документ согласованным или блок закрытым автоматически.

## Ближайшее решение

Пользователь поручил продолжать после первого проверенного шага и отдельно согласовал следующий шаг устойчивого исполнения на тестовых данных. Он реализован и проверен ниже. Статус завершения блока автоматически не меняется. Следующее решение — сетевой обработчик ЦБ и его source-policy/ограничения; этот шаг не начинается автоматически. Глобальные версии материалов и обе интеграции ещё не реализованы. Интервалы, поисковый провайдер и дополнительные источники остаются открытыми.

### Проверка источника перед следующим шагом — 21 октября 2026

Прочитаны официальные страницы [RSS](https://www.cbr.ru/development/RSS/), [о сайте](https://www.cbr.ru/about/), [пользовательского соглашения](https://www.cbr.ru/user_agreement/) и [технических сведений](https://www.cbr.ru/about/tech/). RSS-каталог прямо указывает ленту пресс-релизов. Ограниченный GET с проверкой TLS фактически получил `https://www.cbr.ru/rss/RssPress`: HTTP 200, `application/rss+xml`, 71457 байт. Это разовая проверка, не работа адаптера и не оценка покрытия.

HTML одной ссылки из ленты (`https://www.cbr.ru/press/PR/?file=639281939787093652PNP.htm`) получен с HTTP 200, `text/html; charset=utf-8`, 33404 байта. В просмотренной странице заголовок находится в `h1`, основной текст — в `.landing-text`, видимая дата — в `.news-info-line_date`; RSS содержит guid, link, description с HTML и pubDate с часовым поясом. Значимый параметр `file` нельзя удалять из URL. Это наблюдение одной страницы, а не универсальность правила извлечения. Не считать description автоматически teaser или полным текстом для всех записей.

`robots.txt` фактически получен: запрещены `/search/`, `/Content/SaveToPdf/Page*` и три конкретных PDF-адреса; просмотренные RSS/press URL не перечислены в запретах. Проверенная статья содержит `robots=nofollow` и ссылку «Сохранить в PDF» на запрещённый маршрут. Такая ссылка не должна становиться скачиваемым вложением или обходом запрета; внешние ссылки и скрипты не исполняются. robots не заменяет условий использования.

Страница «О сайте» содержит разрешение на воспроизведение со ссылкой на первоисточник и одновременно отдельную оговорку о коммерческих целях и уведомлении пресс-службы в описанном там сценарии включения ссылок в структуру ресурса. Пользовательское соглашение требует ссылку при цитировании. Зафиксировано содержание страниц, а не юридический вывод о допустимости конкретного продукта. Выбор ЦБ не считается безусловной лицензией для коммерческого использования; режим live-сбора/хранения нужно определить отдельно. Полные RSS/HTML получены только во временные файлы для чтения, в продуктовую БД и корпус fixtures они не добавлялись.

### Второй небольшой шаг — согласован, реализован на тестовых обработчиках

Добавлено устойчивое выполнение **одного** задания и сохранённый результат прохода. Механизм проверен на контролируемом обработчике и явно искусственных JSON-снимках материалов, а не на разборе настоящих RSS/HTML. Подставного успешного production-worker нет. Самостоятельный CLI с настоящим сетевым источником подключается после согласования source-policy и сетевой конфигурации. Планировщик остаётся в Go worker; нового расписания в Python нет.

- Вход исполнения — сохранённое `queued` либо просроченное `running` задание `discover/cbr_press/content` с `policy_version`.
- Переходы: `queued → running → succeeded|failed`. Захват атомарный, с `FOR UPDATE SKIP LOCKED`, случайным токеном владения, временем окончания lease и счётчиком попыток. Предел попыток и длительность lease задаются явно, без чисел по умолчанию. Терминальные задания повторно не исполняются.
- После сбоя lease допускает повторный захват. Сохранить результат может только текущий владелец с действующим lease; запоздавший обработчик не перезаписывает результат нового владельца. Exactly-once исполнения не обещается. При исчерпании попыток задание получает диагностируемый `failed`, а не застревает навсегда.
- Результат и конечное состояние фиксируются одной транзакцией. Ошибка получения/чтения RSS — ошибка всего задания. Ошибка одного HTML item сохраняется у него; остальные материалы не теряются. `succeeded` означает завершённый проход; отдельное `result_status=complete|partial` отражает полноту.
- Снимок результата: `job_id`, `result_status`, `items[]`, `incomplete_fields[]`; у item — внешний ID/URL, заголовок, описание, текст и способ извлечения, происхождение, время получения, статус `full|partial|metadata_only|unavailable`, недостающие поля, структурированная ошибка и ссылки на вложения. PDF не читаются; разрешённость live-вложений определит будущая source-policy, модели валидируют только HTTP(S)-форму URL, не право обращения к адресу. Число сохраняемых элементов ограничивается явной конфигурацией; усечение даёт `partial` с `incomplete_fields=['items']`, а не полный успех. Это не лимит сети/памяти внутри будущего обработчика. Отсутствующий `fetched_at` сохраняется как null, добавляет неполноту item и даёт `partial`.
- Точная дата с часовым поясом сохраняется как `published_at`; если достоверно известен только день — отдельный `published_date` и `date_precision=day`; неизвестная дата остаётся null. `published_at_source` может обозначать проверенное поле источника даже при нераспознанной дате; это не утверждение, что дата известна. `zoom:last-modified` не становится автоматически датой публикации/обновления материала.
- Это неизменяемые снимки результата задания. Глобальная идентичность `material_id/version_id`, дедупликация между заданиями и история исправлений — отдельный P2; нельзя выдавать snapshot за уже реализованное хранилище версий.
- `GET job` показывает состояние и безопасную ошибку; `GET result`: `queued/running → 409 RESULT_NOT_READY`, `succeeded → 200` с сохранённым снимком, `failed → 409 JOB_FAILED` со структурированной причиной, неизвестное задание → `404`. Повторный POST того же запроса возвращает актуальное состояние сохранённого задания и не перезапускает его. Требуется расширить текущую схему `JobResponse` и CHECK в БД.

Проверки до интеграции источника: конкурентный захват; процесс прекращён после захвата; восстановление после lease; отказ запоздавшему владельцу; исчерпание попыток; атомарность результата/состояния; повтор POST терминального задания; сохранность результата после рестарта; feed-level против item-level error; неизвестная/дневная дата; PDF только ссылками. Fixtures и обработчик тестов не подаются в production API как реальные новости.

Изменённые файлы: основная модель — `executor.py`, `result_models.py`, `api.py`, `migrate.py`, новая `0002_execution.sql`, документация; помощник `parser_contract` — только `repository.py`; помощник `parser_tests` — только три файла tests; `parser_review` выполнил независимое статическое ревью без правок. Использованы выбранные `gpt-5.6-sol`, reasoning `low`, Agent Skills и Ponytail. Новых библиотек не добавлено, исходная `0001_jobs.sql` не изменялась.

Мигратор хранит применённые файлы в `parser.schema_migrations`: bootstrap 0001 остаётся повторяемым, последующие DDL и запись в журнале атомарны; session advisory lock сериализует миграторы. Повторный запуск фактически сообщил `already current`, сохранённое queued-задание проверено тестом. Миграции выполнены только на отдельном временном PostgreSQL, рабочая БД и её права не менялись. HTTP-роли нужны SELECT/INSERT на jobs; отдельной worker-роли — SELECT/UPDATE. Ни API, ни исполнитель не нуждаются в DDL/DELETE/доступе к backend-таблицам.

Параметры `execute_once`: `lease_seconds`, `max_attempts`, `max_items` обязательны и не имеют defaults. Lease не останавливает зависший callback и не продлевается heartbeat; при истечении он запрещает сохранение. До подключения сети нужны отдельные таймауты и отмена внутри обработчика. Обработанные обычные ошибки терминальны; `retryable` описывает характер ошибки и не означает автоматический повтор. Попытки сейчас ограничивают восстановление прерванного процесса. Возврат из finish происходит после COMMIT; ошибки БД/lease не переписываются вторым завершением.

Проверки, выполненные главной моделью: **39 unittest-тестов без пропусков прошли на настоящем PostgreSQL** с `-W error::ResourceWarning`; `compileall` прошёл. Среди них конкуренция, crash/reclaim, исчерпание попыток, устаревший токен, atomic finish при ошибке COMMIT и закрытие соединения, даты/partial/ограничение items, API-состояния и неизменность результата при повторном POST.

Три найденных случая воспроизведены отдельными падающими тестами и исправлены: строгая выдача ISO-дат из JSONB через FastAPI; finish, ожидавший неизменённую блокировку строки до expiry (теперь сначала lock, затем отдельная проверка DB clock); полный результат без fetched_at (теперь partial без выдуманного времени). В известном предупреждении Starlette о TestClient/HTTPX изменений нет; оно не подавлялось.

Дополнительная проверка через отдельные процессы: настоящий Uvicorn принял queued-задание; отдельный Python-процесс с явно тестовым callback сохранил complete-снимок; GET result вернул его; после остановки/запуска API вернулся идентичный снимок. Повторный проход не исполнял terminal-задание. Реально проверены отдельные тестовые роли: API не может UPDATE, worker не может INSERT/DELETE. Все тестовые записи/роли находились только во временной БД. Это не подтверждает извлечение публикаций ЦБ.

Источники реализации: [PostgreSQL SELECT / SKIP LOCKED](https://www.postgresql.org/docs/16/sql-select.html), [блокировки](https://www.postgresql.org/docs/16/explicit-locking.html), [транзакции Psycopg](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [строгая валидация Pydantic](https://docs.pydantic.dev/latest/concepts/strict_mode/) и [validators](https://docs.pydantic.dev/latest/concepts/validators/). Проверенный стек и версии зависимостей прежние. Коммита, push и закрытия блока не было.

### Третий небольшой шаг — сетевой адаптер ЦБ, предложение от 22 октября

**Уточнение пользователя:** ближайший запуск относится к некоммерческому прототипу хакатона. Это уточняет сценарий; оно не утверждает коммерческую лицензию или бессрочное хранение. Предложения реализации и проверочного профиля ниже ещё требуют согласования перед кодом. На этом этапе изменена только спецификация, новый код и тесты не запускались.

**Результат шага:** отдельный Python worker для одного сохранённого задания вызывает настоящий CBR-handler и передаёт его снимок в существующий `execute_once`. Планировщик остаётся в Go. В этом изменении backend, deploy, compose и рабочая PostgreSQL не меняются; сетевой pilot выполняется на временной тестовой БД и убирается вместе с ней. Это не развёртывание регулярного сбора.

**Доступ и конфигурация.** Одна версия CBR-policy явно описывает разрешения на получение и сохранение текста и совпадает с `request.policy_version`; неизвестная версия не запускает сеть. Числа и разрешения загружаются явно, без разрешающих defaults. Полные HTML/RSS используются транзитно; в снимок попадают очищенный текст, metadata и происхождение. Полный raw HTML не записывается в БД, fixtures или логи. Тексты пилота хранятся только в удаляемой тестовой БД; рабочий retention остаётся отдельным решением.

**Минимальный сетевой контур — предложение.** Только GET по HTTPS к точному `www.cbr.ru`, порт 443. Разрешены `/robots.txt`, ровно `/rss/RssPress` и публикации под `/press/`; значимые query-параметры сохраняются. `userinfo`, IP вместо hostname, управляющие символы, backslash и неоднозначные URL отвергаются. Никаких произвольных URL из пользовательского запроса, внешних доменов, `/search/` и `/Content/SaveToPdf/`. Redirect в первом варианте возвращает явную ошибку, автоматического перехода и повторов нет. Это уже, чем будущий общий safe-fetch, и достаточно для проверенных 21 октября HTTPS-адресов; при встрече реального redirect контракт обсуждается отдельно.

DNS возвращает проверяемые A/AAAA: если хотя бы один адрес не глобальный публичный, запрос отклоняется. Соединение устанавливается с конкретным проверенным sockaddr без второго DNS lookup; TLS проверяет сертификат исходного hostname, SNI и HTTP Host сохраняют его. Proxy-переменные окружения не используются. На входе/ответе не передаются cookies, секреты и произвольные заголовки. `Accept-Encoding: identity`; любой иной Content-Encoding отвергается без распаковки. Размер потока проверяется независимо от Content-Length, разрешённые MIME ограничены RSS/XML и HTML по назначению запроса.

Обычный `socket.getaddrinfo()` не имеет параметра timeout, поэтому одного socket timeout недостаточно для обещания общего сетевого срока. Предлагается отдельный короткоживущий процесс для сетевого GET: timeout включает DNS, TCP, TLS, заголовки и тело; родитель прекращает/дожидается процесса при истечении срока. Межпроцессный результат ограничен конфигурацией и содержит только проверяемые metadata/bytes, без pickle внешних объектов. Это процесс внутри Python-компоненты, а не новый сервис. Общий budget задания включает ожидание между запросами и проверяется также между стадиями разбора. Разбор ограничен размером входа; жёсткая отмена CPU-разбора этим вариантом не обещается. Сохранение по истёкшему lease по-прежнему запрещено.

Перед live-захватом source-specific worker получает неблокирующий session advisory lock для `cbr_press`; если источник занят, задание не захватывается. Lock удерживается до завершения прохода и освобождается при закрытии соединения, не создавая долгой SQL-транзакции. Каждый GET, включая первый, предваряется настроенной паузой: это ограничивает частоту и между разными процессами, последовательно владеющими source lock. Новый брокер, таблица расписания и миграция для этого не нужны. Общее API исполнения остаётся пригодным для тестовых обработчиков; реальный CLI использует только согласованный source wrapper.

**Robots и HTML.** `robots.txt` читается тем же ограниченным клиентом и разбирается из уже полученного текста, без скрытого сетевого вызова helper. Недоступность или запрет не обходятся: запрещённый RSS даёт безопасную ошибку задания, запрещённая статья — ошибку item. Robots не считается лицензией. `nofollow` не превращает страницу в crawler: ссылки не обходятся; PDF только сохраняются как допустимые ссылки, но не скачиваются. Кнопка SaveToPdf не считается вложением.

Из RSS берутся guid, URL, title/description, категории и pubDate. Ограничение items применяется **до** получения HTML; пропущенный хвост отражается как `partial`. RSS description не объявляется полным текстом. Для HTML используются только source-specific `h1`, `.landing-text` и `.news-info-line_date`; script/style/навигация не попадают в тело. Нет ожидаемого блока, тело пусто, вернулась страница ошибки или повреждённая разметка не позволяет определить границу — явная неполнота/ошибка, без fallback ко всему HTML. Примечания и существенные таблицы сохраняются текстом. Полнота проверяется на fixtures адаптера, не универсальной эвристикой длины.

Валидный RSS pubDate с timezone даёт `published_at`; fallback HTML с одним днём даёт `published_date`. Нет надёжной даты — unknown/null; текущим временем её не заменяем. Не выдумываются event/effective dates. Ошибка RSS даёт failed всего задания; ошибка одной публикации даёт unavailable/partial item, остальные результаты сохраняются. При исчерпании budget после прочитанного RSS возвращаются уже собранные материалы и `partial`; до получения пригодной ленты — диагностируемая ошибка задания. Неизвестные ошибки не раскрывают exception text, URL query или секреты.

**Предлагаемые файлы и проверки.** Основная модель: policy/config, CBR-handler, worker entrypoint, интеграция с существующим executor, документация. После фиксации интерфейсов помощникам выделяются отдельные вспомогательные `.py` сетевого клиента и HTML-извлечения и файлы тестов; каждый файл имеет одного исполнителя. Модели помощников — ранее выбранные `gpt-5.6-sol`, `low`, с Agent Skills/Ponytail. Порядок внутри действующего P1: fixtures и падающие проверки → код → проверки DNS/TLS/bytes/deadline/robots → ограниченный pilot. Новые зависимости не предлагаются: stdlib XML/HTML/HTTP/SSL/socket/multiprocessing; их достаточность должна подтвердиться тестами, иначе ограничение выносится пользователю.

Минимальные проверки: запрещённые URL/IP и mixed public/private DNS; отсутствие повторного resolve; корректные SNI/Host и отказ плохого сертификата; игнорирование proxy; отказ redirect/Content-Encoding; oversized/chunked/no-length; зависший DNS и медленное тело прекращаются с cleanup процесса; source lock/межзапросная пауза; robots fail-closed; XML DTD/entities не обрабатываются; fixtures text/table/date/attachments и HTML error; max_items не вызывает лишних fetch; per-item errors и partial; полный POST → live worker → GET result в отдельной тестовой БД. Тестовая XML/HTML-разметка явно искусственная; отсутствие скачивания PDF проверяется, а не предполагается.

**Профиль только для одного проверочного live-запуска — предложение, не рабочие значения и не SLA:**

| Ограничение | Предлагаемое значение |
| --- | --- |
| Публикаций в одном задании | максимум 3 |
| Размер RSS или одной HTML-страницы | максимум 1 MiB каждого ответа |
| Суммарный объём ответов, включая robots | максимум 4 MiB |

## Проект ИИ-парсера на LangChain — 22 октября 2026

Статус этого раздела: **проект спецификации для согласования**. Пользователь выбрал
ИИ-подход и LangChain и запросил контракт/спек. Это не подтверждает предложенные
ниже Crawl4AI, владельца импорта, API v2, модель или новые лимиты. Ранее написанный
CBR-handler и его проверки сохраняются; backend/deploy сейчас не меняются.
Единственный план остаётся `harness/plan.md`, второй план не создаётся.

### Назначение и границы

Одна способность: получить публикации из явно разрешённых точек входа и вернуть
проверенные кандидаты новостей для загрузки в БД и последующей оценки Jev.
Контракт провайдера: [news-data-contract.md](news-data-contract.md).
Внутренние части: discovery → fetch/clean → LLM extract → validation → durable result.
Go-импорт и Jev — потребители этого контракта, их реализация не входит в данный шаг.

Пользовательский эффект: новые разрешённые сайты подключаются преимущественно
конфигурацией, а не обязательным новым CSS-parser. Обещания универсальности нет:
качество проверяется на разных шаблонах, неизвестная структура даёт partial.
Первый вертикальный срез: extract одного разрешённого URL → результат задания →
идемпотентный импорт. Автономный deep research/поисковый провайдер, PDF pipeline,
генерация бизнес-отчётов, кластеризация событий и self-modifying code не входят.

### Вход и HTTP-граница — предложение

Сохранить существующий `/v1/jobs` без изменения семантики старых запросов/ответов.
Новый `/v2/jobs` и GET состояния/результата принимают отдельную версию контракта:

```json
{
  "schema_version": "parser_job.v2",
  "job_id": "example-extract-1",
  "mode": "extract",
  "source_id": "registered-source-id",
  "urls": ["https://example.org/news/example"],
  "policy_version": "approved-policy-version"
}
```

URL здесь иллюстративный, не источник для live-запуска. source_id — доверенный реестр,
policy разрешает каждый URL. Клиент не задаёт произвольные browser/LLM параметры,
headers, credentials, model или системный промпт. Настройки выбирает сервер.
Для discover — mode=discover, без urls; RSS/разделы и разрешённая глубина обхода
в source config. Два вида запросов — tagged union, дополнительные поля запрещены.
Размер тела и число URL ограничены явной конфигурацией до загрузки/LLM.

Те же auth/202/idempotency/status/lease принципы, но отдельные request/result schema.
Одинаковый job_id с тем же запросом не расходует бюджет повторно; другой запрос
даёт conflict. Ответ результата: job_id, result_status=complete|partial,
items=[NewsCandidate], incomplete_fields, безопасные ошибки отдельных попыток.
Пустая лента complete отличается от неполученной/неразобранной failed.
При пригодных item и ошибках соседних — succeeded/partial. При невозможности получить
вход или недоступности LLM для всего прохода — failed, не «успешно найдено 0».

### Получение и извлечение

1. Получить ограниченный список ссылок из source config/RSS/страницы раздела.
   Если LLM выбирает ссылки, она возвращает только ID уже наблюдаемых кандидатов.
   Не использовать придуманные URL как доказательство или разрешение на загрузку.
2. Проверить source policy/robots, публичные адреса и сетевые лимиты. Для обычного
   HTTP повторно использовать проверенный транспорт там, где его policy допускает.
3. Для browser/Markdown предложен self-hosted Crawl4AI (Playwright под ним), без
   второго обязательного Selenium/ручного Playwright stack и без Crawl4AI Cloud.
   Разрешение browser распространяется на navigation, redirects, iframes и subresources:
   изоляция/egress проверяется отдельно, текущая SafeFetcher policy этого не даёт.
   Нельзя запускать произвольные инструкции/JS, полученные от модели/страницы.
   Никакого обхода robots403, CAPTCHA, отключения TLS или stealth по умолчанию.
4. Получить основную область документа и нормализованный текст/Markdown; убрать
   boilerplate, но сохранить таблицы, сноски, даты и ссылки. Фильтрация не считается
   доказательством полноты. Не обрезать первые N символов без отметки truncation.
5. Разделить длинный документ по структурным блокам с overlap и стабильными block_id;
   limits/chunking policy обязательны. Проверить все запланированные части или вернуть
   partial с перечислением пропущенных. Сопоставлять/удалять повторы claims по evidence.
6. LangChain prompt → модель через командный gateway → Pydantic schema. Ответы страниц
   — недоверенные данные, не инструкции; extraction chain не получает tools/секреты.
   Вход содержит явно отделённые блоки документа, его ID и правила unknown/evidence.
   Модель предлагает поля, claims и ссылки на блоки, но не пишет в БД.
7. Строго проверить JSON, даты, evidence/цитаты/ID и запрещённые дополнительные поля.
   Несогласованные факты отмечать, не исправлять догадкой. Summary не выдаётся за body,
   forecast/announcement не превращаются в состоявшееся событие.
8. Сохранить проверенный снимок существующим lease-fenced finish. Go импортирует
   сохранённый результат идемпотентно; importer может повториться после сбоя без LLM.

### Модель, конфигурация и бюджет

`langchain-openai.ChatOpenAI` предложен как транспорт к Chat Completions API
организаторов; это не выбор модели OpenAI. Основной/резервный URL и точные model IDs
сохранены в `hackathon-llm-access.md`. Секрет только runtime env/secret store.
Никакой передачи ключа в page context, model prompt, трассировки и логи.

Нужен capability smoke выбранной модели: обычный completion, затем отдельно
json_schema/tool calling. Не обещать поддержку native strict schema по одному лишь
слову compatible. При поддержке использовать явный structured-output method;
иначе JSON-инструкции + локальный Pydantic parser. Repair только с явным пределом
вызовов, иначе EXTRACTION_INVALID. Не переключать модели/endpoint автоматически
после неясного сетевого исхода: запрос мог уже быть оплачен.

Обязательные явные конфиги: source policy, модель, prompts/schema revision, число
публикаций, время fetch/job/LLM, bytes/page/job, browser concurrency, input/output
tokens, число chunk/LLM calls/repair, retry policy и storage policy. Старый профиль
CBR (45с без LLM) не автоматически подходит браузеру и моделям. Lease обязан
соответствовать новому budget; никакие новые числа этим spec не утверждаются.

По инструкции организаторов общий лимит команды 500руб/сутки, сброс03:00МСК.
Локальный limiter контролирует собственные calls/tokens и резервирует job budget;
он не знает расход остальных участников без общего учёта/данных gateway. Нельзя
обещать точный рублёвый остаток без проверенных тарифов и командного ledger.
Budget exceeded — явная остановка, не цикл повторов или переключение модели.
Записывать доступные token usage, latency и безопасный error code, не секреты и
полные корпоративные документы; стоимость unknown, если тарификация не подтверждена.

### Проверки и критерии приёмки

- Искусственные HTML разных шаблонов: title/date/body/tables/footnotes, отсутствие
  CSS-specific обязательного адаптера; menu/ad/error page не становятся full news.
- Неизвестные даты/null, timezone и день; поломанный JSON/extra fields, выдуманная
  цитата и неправильный block/document ID отвергаются. Prompt injection в документе
  не вызывает инструменты или изменение policy. Форматный успех не равен semantic pass.
- Длинный материал: нужный факт в конце не теряется молча; неполный chunk pass даёт
  partial; копии overlap не дублируют claims. Ошибка одной статьи сохраняет остальные.
- Blocked/private URL и redirect/subresource, robots denied/403, TLS ошибки,
  медленный browser/LLM и лимиты завершаются диагностируемо, процессы закрываются.
- Mock LLM проверяет budget reservations/retry/repair/exceeded, сохранённый job после
  рестарта и отказ stale lease. Старые 68 тестов не заменяются и не ослабляются.
- Интеграция на отдельной временной БД: повторная доставка не создаёт новую новость,
  изменение текста создаёт revision, старый body не затирается неудачным fetch;
  Jev DTO получает текст и разрешённые company evidence. Никаких production SQL.
- Отдельный ограниченный live smoke через gateway и разрешённый источник с заранее
  согласованным бюджетом; отчёт фиксирует реальные вызовы/ошибки, без выдуманного успеха.
  Предыдущий CBR robots403 не считать решённым подключением Crawl4AI.
